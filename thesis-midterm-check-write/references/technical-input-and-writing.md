# 技术输入 → 阶段事实 → 中期写作

## 事实状态优先于模板范本

技术资料中的“功能总览 / 实现映射 / 测试方案 / 预期效果 / 后续建议”不等于同一日期真实完成进度。应建立内部证据表，每行包括 `FACT-ID`、模块、来源、文档状态、实际验证证据、可写入中期检查的口吻、待确认项。

如技术文档记录某个 STM32 的采集子模块设计、4G MQTT 上传、短信报警和云端数据库：
- 已列“实现”的代码/模块，不自动等于已完成正式整体联调；
- 文档中“测试用例/目标值”是计划，不能写成实测通过或自称达到目标；
- “云端存储按平台部署”意味着待部署，不可写成云平台已完成；
- “2G 覆盖风险”不等于本项目已实际出现短信失败；
- 项目中未提的 LoRa、太阳能、AI 识别等不得从其他已填范本复制进正文。

## 推荐过程

1. 读技术资料和用户本轮真实状态说明；针对关键进度先辨别来源是“文字设计”还是“实物/截图/日志/源码”。
2. 读 `schedule.json` 了解当前中期节点原定目标；不要把原计划当完成率。
3. 读 `progress.json` 里截至检查日的已确认记录。若只有 draft，可以写成待确认，不能把状态改成 confirmed。
4. 先叙述可证实进展，再说明尚未完成事项，保留一定毕业设计真实工作量，避免大段宣传性内容。
5. 问题与措施必须配对：问题来源、影响、具体措施、验证证据或测试办法。尚未发生则用风险表达。
6. 教师意见以拟稿呈现，分配适中篇幅给进度、优点、缺点、措施；不写表格外独立“存在问题与改进建议”栏目。
7. 三块都要足够具体，删去无内容的“极大提升”“非常先进”“高质量完成”等填充语。

## 稿件与实际进度冲突

如果技术文档版本日期晚于中期检查日期，不能倒推该系统功能在中期已完成。先记录冲突，使用具证据时间的里程碑，未知则拟成待核实稿。不在中期表里汇报属于未来的部署或实验成绩。
