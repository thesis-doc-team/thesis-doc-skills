# thesis-midterm-check-write｜毕业设计中期检查记录表生成 Skill

## 0. 绝对边界（首次执行优先阅读）

**唯一正式文书：**《毕业论文（设计）中期检查记录表》的**官方 DOCX 副本填充件**。AI 不是教师/学校，不代签、不代章；指导教师意见只能生成可供教师审阅的拟稿；学院意见默认空白。

> 用户描述可能同时出现“写开题报告 / 写任务书 / 中期检查表”，但本 Skill 对应的是**当前上传的官方中期检查记录表**。默认不进入其他文书的工作流；若用户确实要任务书/开题报告，交由对应独立 Skill 处理。

**规则优先级：** 用户当次明确要求 ＞ 当次官方空白模板的固定结构/栏目 ＞ 本项目技术资料（事实及状态）＞ 同项目可追溯持久资产 ＞ 已填中期检查参考范本的写法 ＞ 常识/推断。内容冲突必须留痕，不能暗改官方表。学校/用户可能另给新版 DOCX：必须先重新审计、重建专用定位锁，不沿用旧坐标写入。已上传的官方文件优先，内置副本仅在用户未另指定时使用。

**禁止：**
- 新建 Word 表格模仿官方版式、重画表格、改页边距/纸张/字体字号/行距/边框/合并关系/固定栏目/签名栏/页码，删除官方现有空段以换取“好看”。
- 从范本继承其他人的姓名、班级、课题、通信模块、时间、进展、导师口吻或结论；只继承可复用的写作结构。
- 把技术文档的功能描述、✅状态或“预期测试方案”直接断言为中期已完成且通过测试；不能自动认定云端、传感器或系统联调已真实验收。
- 填写学院结论、教师签名/盖章、没有依据的检查日期，或把 AI 的教师意见拟稿冒充指导教师的真实评价。
- 增加独立“参考文献”“周计划”“已知问题与改进建议”“技术方案”“附录”等官方模板不存在的栏目。
- 借中期检查任务生成任务书、开题报告、论文正文、技术手册或 HTML。**不重写任何上游技术文档。**

## 1. 一个项目＝一个资产包（数据 + 成品 + 运行区）

### 1.1 项目根路径，而非 Skill 目录

```text
<PROJECT_ROOT>/
├─ project-assets/                       # 数据：跨全部文书 Skill 的持久资产
│  ├─ project.json                       # 身份/用户真实填写的人员字段
│  ├─ facts.json                         # FACT-xxx、证据来源、实施状态
│  ├─ references.json                    # REF-xxx、URL/类型/真实核验状态
│  ├─ schedule.json                      # 唯一项目级周计划（draft/confirmed）
│  ├─ progress.json                      # 本 Skill 可选扩展：PROG-xxx 中期进展快照
│  └─ activity.jsonl                     # 修改原因、引用、正式成品的审计记录
├─ deliverables/                         # 成品：对用户可交付、持久保留，按文书类型一个子目录
│  ├─ taskbook/                           # 任务书 Skill 自行负责
│  ├─ technical-document/                 # 技术文档 Skill 自行负责（MD/HTML）
│  ├─ opening-report/                     # 开题报告 Skill 自行负责
│  └─ midterm/                            # 本 Skill 生成的最终 DOCX（文件带 -vN 版本号）
└─ .skill-tmp/                            # 运行区：仅本次流程使用，之后删除
   └─ thesis-midterm-check-write/
      └─ <run-id>/                        # 有独立所有权标记；不能清理别人目录
```

`project-assets/` 的**基本 schema_version=1** 与用户提供的 `thesis-taskbook-write v1.1` 兼容：保持 `project_id`、`REF-xxx`、`FACT-xxx`、项目周计划 `plan.id` 不变。**不创建另一个同名资产库，也不把项目资产放进 Skill 安装目录。** `progress.json` 是可选、向后兼容的额外文件，不要求已安装的任务书 Skill 支持它。详见 `references/shared-project-assets-contract.md`、`references/progress-asset-extension.md`。

### 1.2 资产生命周期（必须）

1. 识别 `<PROJECT_ROOT>` 与稳定 `project_id`。先 `status`；如果目录已初始化且 ID 一致，继续复用；不一致拒绝串项目。不存在时才 `init`，不得覆盖既有材料。
2. **先读再写** `project.json / facts.json / references.json / schedule.json / progress.json（若有）`，检查证据与时间范围。`schedule.json` 代表**原定/共享计划**，不能当成实际完成证明；已确认和草稿状态严格分开。
3. 同项目事实依 `FACT-xxx` 复用；参考论文依 `REF-xxx` 复用；进展由 `PROG-xxx` 记录时间与证据。新事实/新增论文/真实进度有可追溯依据才可写入资产；更新旧条目要 `--replace --reason` 并产生审计记录。
4. 文书的正文是本轮专属文稿；**不能为了复用把这份中期检查全文存进 `facts.json`**。稳定资产保存原子事实和来源，正文只在本次临时输入与最终 DOCX。
5. 生成后 `record-use --doc-type midterm` 登记成品路径、SHA256 和**实际用到的** `REF-ID`；没有在正文列文献并不妨碍文献作为背景证据登记。若引用库实际未用，可为空，不虚报。
6. 任意成功或失败状态都清理**本轮有所有权标记**的 `.skill-tmp/thesis-midterm-check-write/<run-id>/`；绝不能删 `project-assets/`、模板原件、用户资料、已交付文档（含各历史 `-vN` 版本）或别的 Skill 临时目录。必要失败摘要写入最终反馈，不保留无意义截图/缓存。

### 1.3 成品版本意识（-vN，支持长时间迭代）

- 成品文件名自带版本号：`deliverables/midterm/<课题简称>-中期检查记录表-vN.docx`。重新生成时新建 `-v2`、`-v3`…**永不覆盖、永不删除历史版本**；本轮执行汇报同样带 `-vN`。
- 每个版本验收后**单独** `record-use`（不同路径、不同 sha256），`activity.jsonl` 自然成为该项目成品的变更史；历史版本不重复登记、也不撤销。
- 历史 `-vN` 版本与 `project-assets/` 一样属于永不删除项；`.skill-tmp` 清理只针对本轮自己的运行目录。

## 2. 官方模板硬约束与可填位置

当前内置模板为用户提供的 **“附件 6：塔里木大学毕业论文（设计）中期检查记录表”** 的未经改写副本：`assets/official-midterm-template.docx`。其 SHA256 和字段定位见 `assets/template-lock.json`；工具仅接受该审计过的版本。官方模板是**1 张 6 行 4 列的底层表格**（多处合并单元格）、A4 纸、学院签名及日期栏，表格外另有附件名和标题。不得将看似四列的合并格重复填写。

| 官方位置 | 可填字段 | 处理原则 |
|---|---|---|
| 表头日期 | `inspection_date` | 仅本轮有真实日期时填入，未知保持“年 月 日” |
| 第 1 行 | `student_name`、`class_name` | 未知保留空白；不得继承样本人物信息 |
| 第 2 行 | `title` | 本项目真实题目，仅填合并的题目区域 |
| 第 3 行 | `progress_paragraphs` | **完成进度**；学生自述至少 200 字，兼含下一步安排 |
| 第 4 行 | `issues_paragraphs` | **存在的问题及整改措施**；至少 200 字，问题和整改逐项对应 |
| 第 5 行 | `teacher_opinion_paragraphs` | **指导教师意见**至少 200 字；必须声明为拟稿；签名日期不动 |
| 第 6 行 | `college_opinion_paragraphs` | 默认完全留空；用户真实明确授权才填文字，签章不动 |

**填字≠改格式：** 脚本只在官方原有空白段落插入文字、新文字按原表相邻段落样式使用宋体中文/Times New Roman 英文、12pt/1.5 倍行距；不删除/新增表格、行、格、原有段落，不碰固定标题、表格边框、页眉页脚及签章行。正文自然换页属于 Word 正常流动，**页数不作为强行压缩的指标**；不允许为“保持三页”缩字体或破坏模板。段落数超过该模板的原空白占位时，先减少冗余分段而非破坏结构。更多见 `references/template-boundary-and-layout.md`。

## 3. 文本逆向：求同存异，形似优先，事实真实

本次四份已填中期检查样本的**共同结构**：进展描述已完成模块/论文准备 + 下一步计划；问题与整改并列对应；教师意见概括研究价值和阶段进展，再评价优点、风险和整改建议。写法可采用“分层分点”或“段落叙述”，不要求项目一定有“硬件+软件+论文”三分法；必须根据技术事实判断。

存在冲突时：**官方模板与字数要求高于样本**。范本部分条目的内容/字数、题目换行、落款方式和阶段成熟度不一致，以官方规范优先；范本多数一致但官方未规定的表达习惯可沿用。不要继承样本中“已经实现云平台”“准确率达到某值”的假定。详见 `references/genre-reverse-engineering.md`。

### 3.1 先形成事实与状态矩阵，再写段落

从技术资料抽取：`功能/模块`、`支持它的章节/文件`、`技术文档声称的状态`、`是否有实测或用户明确确认`、`能用什么谨慎动词`。区分：
- `已实际完成且有证据`：写“已完成/已实现”，**测试通过**还需要测试日志、照片、现场记录或用户明确确认；
- `技术文档列为已实现，但无独立验收证据`：写“技术资料显示已完成相关模块设计/程序实现”，不要虚构长稳测试；
- `已设计或拟实现`：写“已形成方案、正在调试、下一步拟开展”；
- `待部署/拟扩展`：只能列后续计划或风险；
- `来源冲突/未知`：不擅自选一边，作为待核实项并在执行汇报披露。

**中期检查是“某个时间点的阶段事实”，不等于技术文档的最终项目状态。** 若只提供整体技术方案，允许撰写**待核实草稿**，但必须在执行汇报明确哪些完成进度尚缺用户确认；不可把猜测写成既定实绩。

### 3.2 三个正文栏目写作要求

**完成进度（≥200 字）**：开头说明目前阶段与项目目标；按技术主线交代已做工作（可用 1.硬件/2.软件/3.论文 或自然段）；适度点出真实测试；收束于与 `schedule.json` 一致的**下一步计划**。同一任务不重复写；不要把原定周计划说成实际完成进度。

**存在的问题及整改措施（≥200 字）**：先按真实证据列出 2—5 个有针对性的问题，随后分别给出可实施的整改动作及验证方法；问题若只属于风险/待验证，则写成“仍需验证的风险”，不能断言已发生。至少涵盖与当前技术相关的关键链路与论文材料完成度，但绝不机械照搬某样本的通信模块。

**指导教师意见（≥200 字）**：教师视角，对课题价值、当前进度、明确优点、尚存不足、整改建议、后期时间安排形成闭环。只能作为**待审核建议稿**，不得写“教师已同意/已签字”；最终用词由导师本人确认。学院意见默认不生成。**不得补写官方表外独立章节**。

字数检查按剔除标点/空白后的中英文/数字有效字符计数，三块各至少 200，建议写 230—320 字以留出差额。不为参考样本“少于200字”而违反官方要求。

## 4. 参考文献与来源规则（仅作为事实支撑，不新增栏目）

本官方表没有“主要参考文献”栏，**没有任务书的至少10篇要求**。中期检查不主动插入参考文献列表，也不把“论文综述”写成独立章节。若需要查证技术背景、论文研究与整改单据：

- 学术论文首选 **中国知网 CNKI、万方数据、维普**；也可用高校学位论文库、期刊/出版商官网、IEEE、ACM、ScienceDirect、Springer、DOI/Crossref 等可追溯来源；
- MCU/通信/芯片的具体技术规范优先厂商官方手册及可信文档；**CSDN 可作为开发经验和排障补充**，但必须标记为博客/网页，不能冒充论文或据此捏造论文元数据；
- **先用项目 `references.json` 已核验且相关的 REF-ID，缺失才补检索**。核对作者、题名、刊物/年份、DOI或平台记录页面等真实字段，记录 URL、核验时间、来源类型和与本课题的相关性；无法检索就写 `verified=false`，不要臆造；
- 中期记录的事实可由技术文档直接支撑，**不强制为了引用而联网**；只有需外部研究/规范支撑时才检索。`references.json` 不是本份表格的正文目录。

阅读 `references/citation-policy.md`。

## 5. 标准执行顺序

1. **盘点输入**：本轮技术 MD / 手册 / 代码证据、官方空白 DOCX、可用已填范本、当前项目身份、人员信息和时间。需补实质性里程碑时优先核查用户本次证据，不凭推测填充。个人敏感字段不从别的样本猜。
2. **确定项目包**：先读取 `project-assets/`，初始化缺失文件仅在无历史时进行；检查项目 ID 不串台，读取文献、技术事实、计划与中期进展快照，记录本轮将使用的 ID。按需补充带来源的事实/论文/阶段记录（有证据才写）。
3. **锁定原模板**：`inspect_template.py` 只读盘点；保存原件 SHA；发现官方新版与 `template-lock.json` 不符，**停用旧版填充坐标**并重新适配新模板，绝不强灌。
4. **逆向范本并求同存异**：只提取表达习惯、分段方式和篇幅；差异依官方＞证据＞合理常识判断，涉及真实进展时不由比例多数投票决定。
5. **草拟写作**：制作带来源的状态矩阵，确认“完成／未完成／仍待验证”的边界，写出三个≥200字栏目。教师意见声明为拟稿；个人信息与日期未知时留白。严禁把来源技术文档的“预期测试结果”写成既有成果。
6. **组装输入**：在本轮临时目录保存本轮文书独有草稿 JSON，调用 `project_assets.py compose` 仅验证 ID、复用项目计划与人员信息，形成临时填充输入；该命令**不会由共享资产自动写正文**。
7. **原版填充**：调用 `fill_midterm.py`，从官方模板**原样副本**写入允许空白段落，保存到 `deliverables/midterm/<课题简称>-中期检查记录表-vN.docx`（新版本新文件，不覆盖历史版本；或用户指定路径）。
8. **双门禁**：`validate_midterm.py` 自动验证固定内容、格数、段数、签章、Word样式包、三段字数与填充内容；随后进入**截图验证分析（Screenshot Verification Analysis，交付前硬性环节，缺一不可）**：
   1. **截图**：Word 兼容工具逐页输出图片/PDF，只存本轮运行目录，不进交付目录；
   2. **逐张分析**（缺一张即未完成）：文本溢出、表格跨页、孤页签名/日期、印章栏、字形缺失、不当大片空白、字号/断行/错字；
   3. **留痕汇报**：执行汇报固定填写截图引擎/工具、截图张数（=页数）、实看张数、逐张结论 PASS/WARN/FAIL 与问题清单、返工复检次数、WPS 实测边界声明。
   红线：未逐张分析不得宣称验收通过、不得登记 record-use；无法截图时如实报“截图验证分析未完成”；有缺陷先改**正文措辞/段落分配**后重新填充复检，**不得通过删除/缩改官方框架“修图”**；截图是验证手段不是交付物，结论写入执行汇报后随本轮中间文件清理。
9. **归档与汇报**：仅验收通过的成品 `record-use --doc-type midterm`（每个 `-vN` 版本单独登记）；说明已复用/新增的资产 ID、技术完成度证据级别、待核实字段、是否实际打开过 WPS，以及结构/逐页检查结果。用户负责最终验收。
10. **安全清理**：即使失败也使用 `finally` 逻辑清理本轮 `run-id` 所有中间文件；若清理受阻，如实报告路径而非扩大删除范围。

详细门禁：`references/quality-gates.md`；安装与执行：`README.md`。

## 6. 快速运行（Codex / Claude Code / Python）

```bash
# 这里 PROJECT_ROOT 为真实毕业设计项目根目录，不能写成安装 Skill 的目录。
python -m pip install -r requirements.txt
python scripts/project_assets.py init --root "$PROJECT_ROOT" --project-id "$PROJECT_ID" --name "$PROJECT_NAME"
python scripts/project_assets.py status --root "$PROJECT_ROOT"
python scripts/project_assets.py workdir --root "$PROJECT_ROOT"
# 记录输出的 WORKDIR 和目录末尾 RUN_ID；以下文件都只存入 WORKDIR。
python scripts/inspect_template.py assets/official-midterm-template.docx --json "$WORKDIR/template-inspection.json"

# AI 先阅读技术资料与共享事实：只在 WORKDIR 写本次专属 midterm-draft.json
# 如需新增事实/文献/进展，再 merge（已存在记录不得偷偷覆盖）。
python scripts/project_assets.py compose --root "$PROJECT_ROOT" --draft "$WORKDIR/midterm-draft.json" --out "$WORKDIR/midterm-input.json"
python scripts/fill_midterm.py --template assets/official-midterm-template.docx --data "$WORKDIR/midterm-input.json" --out "$FINAL_DOCX"
python scripts/validate_midterm.py --template assets/official-midterm-template.docx --file "$FINAL_DOCX" --data "$WORKDIR/midterm-input.json" --report "$WORKDIR/qa-structure.json"
# 逐页渲染与肉眼复核后，才可登记成品。
python scripts/project_assets.py record-use --root "$PROJECT_ROOT" --file "$FINAL_DOCX" --doc-type midterm --ref-ids "$ACTUALLY_USED_REF_IDS"
# 无论成功/失败都必须清理本轮受控临时目录；不删除共享资产和最终 DOCX。
python scripts/project_assets.py cleanup --root "$PROJECT_ROOT" --run-id "$RUN_ID"
```

`$ACTUALLY_USED_REF_IDS` 可以为空，**不能为了表示“引用过”随便登记 ID**；若中期检查无实际引用研究背景，仅记录 `facts/progress/schedule` 的真实使用于执行汇报。逐页渲染可使用 `python /home/oai/skills/docx/render_docx.py "$FINAL_DOCX" --output_dir "$WORKDIR/render"`，或按可用平台工具执行。若没在 WPS 客户端实际打开，只能说“兼容渲染检查已完成，WPS 未实测”。

## 7. 失败与用户验收

- 字数不达标、原模板结构/hash不符、数据来源未核实而被写成已完成、教师真实意见被冒用、固定签名日期改动 → **FAIL**；不报告正式通过。
- 真正可用的进展证据不足 → **可产待核实草稿并给出清晰清单**，不得假装完成证明充分。
- 外部论文未能检索/验证 → 不假造；该表无参考文献栏，能从技术资料真实写作则不以“10篇未满”强行阻止。
- 文书生成成功、结构验证通过但未实际逐页目视复核 → **不能宣称已完整验收**。
- 用户可修改 Skill/范本/资料；**用户负责最终验收**，Agent 负责执行、尽可能自检与如实汇报。

**最终目标：官方模板原样、文章写法形似、阶段事实可靠、项目资产一处维护、成品可追溯、中间文件不遗留。**
