# 与 project-technical-doc V5 合并时的接口建议

> 本文件供后续 Skill 合并参考，当前**不直接修改或重打包用户原有的 project-technical-doc**。

## 角色划分

```
用户项目源码/资料（只读）
   └─> project-technical-doc（上游）
       ├─ 项目技术文档.md   ———> thesis-taskbook-write（下游）
       └─ 用户展示.html          ├─ 文献检索和事实任务化
                                ├─ 原样官方模板 DOCX 填充
                                └─ 任务书.docx + 执行汇报
```

原上游 Skill 的 MD + HTML 双产物要求**仅适用于其独立触发的技术文档任务**。本 Skill 不能因此附带生成 HTML，也不能反向改写上游技术 MD。

## 共同维护的项目资产层（V1.1）

两个 Skill 不再只交接一次性的技术 MD。每个项目固定使用 `<PROJECT_ROOT>/project-assets/`，其协议见 `shared-project-assets-contract.md`：

- `facts.json`：上游技术文档 Skill 可登记有来源的技术事实；下游核对后读取，不重新凭空解析项目全貌。
- `references.json`：任务书实际核验与使用的文献登记成稳定 `REF-ID`，后续开题报告 Skill 直接择优复用，无需每次重新录入同一篇论文。
- `schedule.json`：任务书拟定的项目级周计划，后续开题报告 Skill 应先读取，再按其文体展开。若正式安排变化，有理由地更正同一个计划基线，避免两份文书周次冲突。
- `activity.jsonl`：各 Skill 共同追踪新增、更新与被最终文书使用的 ID。

共享资产是可持续维护的**事实与计划**，不是两套 Skill 互相覆盖模板或内容的授权。其他 Skill 将来只要遵循同一文件协议，就可以共同维护。

## 共用与隔离

可共用：技术事实证据登记格式、已实现/未验证/仅资料声明状态、执行报告中的输入与未完成项、只读不覆盖项目资料原则。

必须隔离：
- 上游以技术事实描述为目的，正文可含模块、流程、数据表；任务书以**安排毕业设计任务与计划**为目的，没有理由复制所有技术章节。
- 上游可能规定没有“已知问题与改进建议”等独立章节；本 Skill 只依据任务书官方栏目，**不加任何自创栏目**即可。
- 上游技术 MD 的文内项目引用不等于本 Skill 的**学术参考文献核验结果**；两者证据用途不同。
- 上游 Markdown/HTML 排版规则与下游 Word 模板**互不传递**；下游只由官方 DOCX 决定版式。

## 合并推荐方式

保留两个可单独触发的 Skill，提供上层路由器，按用户意图选择：

- 用户说“梳理项目技术文档并生成展示网站” → `project-technical-doc`。
- 用户说“根据技术 MD 填写官方任务书” → `thesis-taskbook-write`。
- 用户说“先技术文档，之后写任务书” → 两者**先后串行**执行，上游交付原技术 MD，下游读取那个 MD，之后填 Word。绝不合并成混杂的输出要求。

这样未来开题报告、论文、答辩材料还可以各自增加独立技能，而不使任务书 Skill 越界。**每个 Skill 都应清理自己生成的中间文件；不得清理共享资产和其他 Skill 的运行目录。**
