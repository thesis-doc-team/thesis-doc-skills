# 技术资料 → 任务书：证据抽取与任务化写作手册

## 必读顺序

1. 用户本次提供的技术文档：标题、场景/目标、功能列表、总体架构、关键技术、模块职责、系统流程、测试、实施状态与限制。
2. 如用户直接提供源代码而没有技术文档：只读确认 README/依赖/入口/关键业务逻辑；可调用上游 `project-technical-doc` 先整理技术 MD，本 Skill 自身**不输出**额外技术文档。
3. 如用户还附多个旧任务书：先逆向语言结构，不把它们作为当前技术事实来源。
4. 已引用或有线索的论文：另外进行可追溯检索，不能凭技术文档出现某论文标题就直接认定出版详情真实。

## 一张内部证据映射表

| 项目事实类型 | 在任务书中的转换 | 缺证据时的行为 |
|---|---|---|
| 场景/使用者/设备类型 | 简洁课题总述 | 不猜客户及部署行业 |
| 主要功能 | 按功能族概括为学生需实现的模块任务 | 没有资料不增加功能 |
| 技术方法/平台 | 选择必要的技术载体、通信与处理机制 | 不填想当然的硬件/数据库/云服务 |
| 模块间数据流 | 写成系统集成、接口与联调要求 | 不造不存在的控制闭环 |
| 测试用例/测试计划 | 写成拟开展的检查与验证任务 | 不写“全部测试已通过” |
| 已完成/待开发状态 | 研究目标与任务边界，必要时中性表达 | 不虚构开发进度或成果指标 |
| 项目资料提到的论文/标准 | 作为检索线索，另查权威来源 | 核验不通过不进入正式引用 |

## 写作深度原则

- **确保“导师能看出做了什么/准备做什么”**：写作用途、模块、关键实现、验证任务，但不展开开发手册的全部字段、源码函数、错误码等细节。
- 技术任务有层级：总体设计 → 数据/业务核心 → 接口/通信/存储 → 界面/反馈 → 集成与测试。取舍随项目变化，不强制 Web/数据库/硬件齐全。
- 语气“设计、完成、实现、测试、验证、撰写”，避免营销口号与“国际领先”“绝对可靠”等无依据评价。
- 若技术文档是静态代码审阅，写成“应完成系统联调测试”可以；但不得以“已测试证明”替代验收证据。
- 内容可因真实复杂度自然增加，不设绝对字数上限，也不为与样本页数相同而压缩。

## 进度校验

- 周次范围为 `[1, N]`，每段两端包含；检查不重复、不跳周，阶段描述与实际项目吻合。
- 开题、文献、核心开发、联调、最终论文/答辩等大阶段应合理覆盖；具体分段由项目和用户安排决定。
- “30 周”若仅来自往年样本，不能自动认为新一届也是 30 周；以本次指定的总周数为准。
- 用户提供的真实日期与周数若互相矛盾，记录冲突并提出确认，不应为凑数偷偷改日期或周数。

## 缺失信息表述策略

- 个人资料/签名：可以留白（不写【待填写】影响版式）；在执行汇报列为待用户补齐。
- 学校官方固定要求未满足（参考文献不够、意见不足字数、排版超框）：不声明通过。
- 与官方模板冲突的用户新要求：明确列出冲突，由用户最终决定是否正式授权更改模板。
