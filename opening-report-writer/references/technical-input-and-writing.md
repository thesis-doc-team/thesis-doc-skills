# 当前技术资料 → 可追溯事实 → 开题文本

优先从用户本次发送的技术文档提取“应用场景—目标用户—实际模块—技术架构—进程/接口/数据—技术约束—拟验证方案”；对重要句子做带 `FACT-ID` 的来源表，标注文件/章节、证据等级、可用口吻及尚未证实事项。示例或此前其他项目不作为事实。

| 来源状态 | 开题报告可写 | 不可写 |
|---|---|---|
| 源代码/测试记录明确有证据 | 已有模块实现可作为开发基础，具体已验证指标可引用 | 未经整机测评就写“整体已完成且稳定” |
| 技术文档文字声明“已实现” | “资料显示已有…设计/实现基础” | 无测试证据的“已通过稳定性测试” |
| 方案设计、拟实现目标 | “拟采用/预计实现/计划验证” | “已实际达到…” |
| 市场/文献外部观点 | 仅在论文/官方页面确实支持时引述并上标 | 把泛化的市场数据伪装成项目实测 |
| 未知或相互冲突 | 标注“待确认”并在执行汇报列明 | 套用范本或常识补齐数字/型号 |

## 各节落地动作

- **背景**：从实际使用场景出发，聚焦当前技术方案为何必要；不能仅堆概念。
- **研究现状**：论证当前存在的研究路线、优劣与本题区别，每个外部结论有实际对应来源。
- **任务和可行性**：每项写清输入—处理—产出及测试方法；软硬件/资源条件不可虚构。
- **关键技术**：问题、约束、解决路径和拟验证办法成对出现。
- **条件**：说明已有资源与缺失条件，不把可购买说成已具备。
- **进度计划**：仅从一个 `schedule.json` 形成“第X周--第Y周”文本；不同文书复用同一计划，不将计划变成“已实现”。

若技术文档边界禁止问题分析/改进建议，开题报告第4节仍必须写**研究拟解决的关键问题与方法**；这属于开题论证，不等于重写上游技术文档或擅加“已知问题与改进建议”独立章节。
