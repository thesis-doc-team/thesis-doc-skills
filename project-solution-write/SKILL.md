# project-solution-write｜项目介绍与工程实施方案双文档 + 项目介绍 HTML 生成 Skill

## 0. 绝对边界（执行前优先阅读）

**本 Skill 是项目方案编写 Skill，不是项目开发 Skill。只负责三份正式成品：两份独立 Markdown，以及一份由《项目介绍与功能说明.md》派生的单文件 HTML 介绍页。**

- **《项目介绍与功能说明》**：面向阅读、展示与了解项目的用户，讲清场景、目标、功能、交互与必要使用条件；不泄露逐步开发细节。
- **《项目介绍与功能说明》HTML**：介绍 MD 的可视化表达，用于离线浏览与展示；只复用介绍 MD 的内容，不引入工程实施细节，也不是用户项目的正式前端系统。
- **《工程实施方案》**：面向开发者，给出可复现的技术路线、软硬件设计、协议、数据模型、模块、步骤、排障与验证方法；不得把无来源假设表述成已实现或已实测。

默认同时生成两份 MD 与介绍页 HTML；用户明确只要其中某一份时只生成指定范围。**不得擅自执行代码开发、采购、接线、部署、运行测试或生成用户项目的正式前端系统、完整业务源码仓库、DOCX、PPT、商业计划书、技术文档逆向报告等第三类成品。** 可以在实施方案中写出必要的结构体/接口/命令示例，但不据此创建真实工程或宣称已执行。**项目介绍 HTML 属于文档可视化能力，不等于开发用户项目的正式前端系统。** 用户仅要求逆向总结或编写其他文书时，本 Skill 不启动文档生成，应交给相应任务或 Skill。**与项目技术文档的分工**：已有真实实现、需要“技术文档 + 用户展示 HTML”时交给 `project-technical-doc`；本 Skill 只产出规划/方案类双文档与由介绍 MD 派生的介绍页，不产出技术文档、用户项目前端系统、DOCX 或源码。

### 0.1 不允许出现的文档内容（强制）

正式成品（两份 MD 与项目介绍 HTML）均不得出现独立或变相章节：

- `工程实施交付说明`、`付费交付说明`、`收费建议`、`免费/付费区别`、`销售建议`、`商业转化`、`如何使用本文件`；
- `已知问题与改进建议`、`后续优化建议`、`后期扩展建议`、`可增加功能`、`其他建议`、`作者总结`、`AI 的建议`；
- 给用户/Agent 的工作汇报、Skill 使用说明、资料清单、生成过程说明、免责声明长文；
- 与项目功能无关的高级技术堆砌或将“未来可选扩展”伪装成用户已确认需求。

**重要边界**：工程实施方案内部可以写“实施前提与未确认条件”“技术方案比较与选型依据”“异常与排障”，它们是实现本项目的必要技术内容，不得改写成泛泛的建议章节。与 thesis-doc-suite 六件套同一“变相章节”边界：即使换名——“存在的问题”“问题与改进”“不足与优化”“改进建议/方向”“优化建议/方向”“风险与对策/分析/评估”“未来展望/技术展望”“后续规划/计划”“升级建议/计划”“技术演进”“未来工作”“发展规划”等——独立成章仍属越界，`validate_docs.py` 直接判 ERROR。两份文档不放“免费”“付费”“收费”等商业标签；此区分仅作为 Skill 的内部职责控制。向用户的执行汇报放在聊天回复或独立运行报告，不混入正式成品。**介绍 HTML 同样不得出现 GPIO/引脚表、电气接线、协议帧、代码、API 密钥、部署命令、收费说明、后续改进建议或工程实施交付说明；它只做介绍 MD 的可视化，不承担实施方案的表达职责。**

### 0.2 不得重复曾经出现的误判

- 用户写“人体检测”，**不能自行假定**是区域存在检测、姿态/步态/跌倒检测或摄像头视觉识别；这些会根本改变传感器与算法，先问。
- 用户写“LoRa 点对点”，不能默认必然**单向**。结合显示“远端数据”等迹象主动推导两端数据流；若方向关系未定且影响核心功能，问一条聚焦问题。
- “本地交互测试”可能是 OLED 菜单，也可能是无硬件 Mock 测试；先看上下文及验收目标，歧义重大时才问。
- 不因用户只提“环境监测”就擅加风速、土壤、粉尘、火焰等指标；先列明确项，再对关键缺项问询或将推荐默认标为待确认。
- 不默认每个 STM32 都要 F407/FreeRTOS/数据库/自建云平台；不默认每个 AI 终端都要 STM32 与 GPIO。
- 不把源码包含某功能、文档标记✅、Mock 数据或测试预期写成真实硬件验收通过。

### 0.3 规则优先级

本轮用户明确要求与已确认功能/约束 ＞ 用户明确指定的现有技术方案/实物/源码事实 ＞ 可核实的技术资料（官方数据手册、SDK/接口文档、法律与频段约束）＞ 项目级已确认资产 ＞ 参考案例中的方法与结构 ＞ Agent 推导的合理默认设计。

源码与 README 冲突时保留证据差异，不能静默替用户修正事实。用户提供的原文只用于本项目，不把其密钥、具体人物/学校或项目专有配置写入通用范本。

## 0.4 启动即执行的必填信息门禁（V1.2.1 起，优先于技术设计）

**即使用户只说“使用这个 Skill / 开始 / 帮我做个项目方案”，也必须主动开启需求收集对话，不得保持沉默或直接虚构项目。** 第一轮先从本轮消息、当前对话中用户明确提供的内容、指定的项目文件以及已经确定归属的项目资产中，提取以下两项**必需输入**：

1. **项目题目**：明确的项目名称；不能只用“新项目”“某系统”“项目名”等占位词。
2. **功能需求**：至少能够列出项目真正要实现的功能及基本行为；只有项目名称、行业领域、无意义占位或空泛口号时视为缺失。若功能虽已列出但存在会改变技术原理的重大歧义，按第 2.2 节澄清。

**任一必需项缺失，即停止正式写作和工程选型**，必须向用户发出简短、直接、可一次性回答的询问：

- **题目、功能均缺失**：一次询问“请提供项目题目和想实现的功能（可直接按自己的话列出）”；同时附上可选的设计侧重四选一，不强制要求用户提供完整技术规格。
- **只缺题目**：只问项目题目；已有功能保持不变，并可在同一条消息附上尚未确定的设计侧重。
- **只缺功能**：只问项目需要实现的功能/使用行为；已有题目保持不变，并可在同一条消息附上尚未确定的设计侧重。
- **两项均已有**：不得重复索取，只按第 2.2/2.3 节决定是否还需一次关键澄清或设计侧重选择。
- **已有项目继续修订**：先读取该项目已确认题目和功能资产；若齐全则直接继续，不把历史项目的内容误用到新项目。

这两项是不可省略的**信息完备性硬门槛**。用户说“直接生成/不要问”只能跳过**可选**偏好问询（默认为均衡）或普通技术参数，**不能跳过缺失的项目题目或功能**；必要时只问缺失字段。Agent 不能凭空给用户定题目，也不能从项目名杜撰具体功能；若用户明确授权代拟题目/共同构思功能，先把拟定结果反馈给用户确认，再进入正式方案。对于已有资料中明确写出的题目和功能，可视为提供过，不必强迫用户重新输入。

**用户启动时的聊天措辞**见 `templates/initial-intake-message.md`；读取结构化输入时可运行 `scripts/check_input.py` 做缺失项初检（脚本不能替代 Agent 对功能歧义和语义充分性的判断）。输入收集与决策仅发生在对话或项目内部运行资产，**不得生成第三份正式 MD，也不得把“请提供题目/功能”的提示写入两份成品正文**。

## 1. 一个项目＝一个资产包（数据 + 成品 + 运行区）

### 1.1 工作区结构

```text
<PROJECT_ROOT>/
├── project-assets/                          # 持久数据层，跨 Skill 复用
│   ├── project.json                        # 稳定 project_id / 项目题目与状态
│   ├── facts.json                          # 可追溯事实 FACT-xxx（已有则原样兼容）
│   ├── references.json                     # 技术来源 REF-xxx（已有则原样兼容）
│   ├── schedule.json                       # 已存在则读取；不可从中推断已完成
│   ├── requirements.json                   # 本 Skill 增量资产：功能、状态、验收
│   ├── decisions.json                      # 本 Skill 增量资产：选型与取舍
│   └── activity.jsonl                      # 修订与成品使用记录（已有则兼容）
├── deliverables/
│   ├── project-introduction/
│   │   ├── <项目简称>-项目介绍与功能说明-vN.md
│   │   └── <项目简称>-项目介绍与功能说明-vN.html   # 由同版本介绍 MD 派生
│   └── implementation-plan/
│       └── <项目简称>-工程实施方案-vN.md
└── .skill-tmp/
    └── project-solution-write/
        └── <run-id>/                       # 仅本轮草稿、报告和检查记录
```

- **不把项目数据存到 Skill 安装目录**；参考范本/规则在安装包内只读。
- 若其他 Skill 已维护 `project-assets/project.json/facts.json/references.json/schedule.json`，**不得重建、覆盖或降级**；`requirements.json`/`decisions.json` 是可选的附加文件，不改变旧资产 schema。
- 已确定 `project_id` 不得跨项目复用，技术事实逐项注明来源、状态与时间。
- 成品始终加 `-vN`，版本递增、不覆盖、不删除历史版本；用户明确指定的外部目标路径优先但不能覆盖已有成品（除非用户明确授权修改特定原件）。介绍 HTML 与同版本介绍 MD 共用 `-vN`；介绍 MD 改动后必须重新生成 HTML，HTML 视觉调整不得反向改写介绍 MD 或工程实施方案。
- 运行完成或失败，安全清理**本轮有所有权标记**的临时目录。不能删除 `project-assets`、用户上传文件、历史成品或其他 Skill 运行区。

详见 `references/project-assets-contract.md` 和 `references/cleanup-and-versioning.md`。

## 2. 输入识别、目标偏好与澄清门禁

**第 0.4 节的项目题目/功能完整性门禁始终先于本节的模式识别和设计目标选择；两项缺失时先提问，不能因为第 2.3 节允许“均衡拟定”就直接写作。**

### 2.1 首先判断任务模式

| 模式 | 输入材料 | 本 Skill 行为 |
|---|---|---|
| A 规划设计 | 项目题目 + 功能清单/功能树 | 明确功能→推导方案→双文档 |
| B 基于既有方案写作 | 题目 + 功能 + 真实技术文档/部分既有参数 | 尊重真实器件、接口、软件结构；不能私自重构成理想化新项目 |
| C 基于代码资料写作 | 用户**明确提供**的源码目录/压缩包 | 只读检查调用路径、接口、真实已接入状态；资料不足时只能谨慎引用，必要时调用专门 code-understand Skill |
| D 仅单文档 | 用户只要求介绍 MD 或实施 MD | 只写指定文件；仍须遵循事实/边界/质量规则 |

### 2.2 严禁“过度脑补”与“过度问询”两个极端

**仅当不同回答会实质改变**核心任务定义、感知原理、硬件架构、部署环境、成本约束或验收目标时，主动提出**至多 1～3 个聚合的关键问题**。不把每个串口、ACK、阈值、滤波窗口、按键消抖拆成一轮轮选择题。用户已有答案不重复问。用户暂时没有回复且需继续工作时，给出最合理的**明确标注为拟定的技术基线**，不能冒充已确认。

**主动推断的普通决策**：足够用的 MCU、可共用的 I²C、GPIO/串口分配、UART 驱动收发模式、周期节流、状态机、缓存策略、开发/测试顺序。需在工程实施方案说明关键选型理由，不把全部细节丢回给用户。

**典型必须澄清**：

- “人体检测”究竟测存在、运动/摔倒还是视觉？
- “无线通信”是单向上报、双方交换数据还是远程控制？在有远端数据显示等充分上下文时先自行分析。
- “环境监测”究竟要求哪些指标？已有具体温湿度/粉尘/风速时不重复问。
- “本地测试”是物理按键诊断还是软件 Mock 开关？
- “移动设备”是否有电池、室外暴露、断网长期运行等硬约束？

读取 `references/requirements-and-question-gate.md`。过程记录 `REQ-xxx` 的确认状态，不得把 `assumed` 偷改为 `confirmed`。

### 2.3 设计目标选择门禁（V1.1 新增，必须执行）

**新项目进入规划设计前，优先明确一次设计侧重：成本优先 / 性能优先 / 功能优先 / 均衡方案。** 这是一次简短偏好选择，不是让用户承担硬件选型工作；已从用户需求或已有项目资产明确的偏好不得重复询问。若用户仅提供项目功能且未表达偏好，Agent **必须主动给出以下简短选择**（可和真正重大的需求歧义合并在一轮，避免来回多问）：

> 这个项目你更希望往哪个方向设计？**① 成本优先**（满足必需功能前提下尽量低成本）／**② 性能优先**（侧重响应、精度、容量、稳定性等关键性能）／**③ 功能优先**（让已要求的功能更完整、体验更充分，不擅增功能）／**④ 均衡方案**（成本、性能、功能、实施复杂度综合权衡）。没有特别偏好可选④。

- 用户选定后只记录一次；**不得**继续把主控、传感器、通信模式、任务周期拆成多轮选择题。即使选了偏好，仍由 Agent 主动完成技术判断、候选方案比较和推荐方案落地。
- 用户明确要求“直接生成”“无需提问”或无法获得选择时，采用**均衡（proposed）**，在聊天反馈中说明该假设；不可伪称用户已选。
- 用户给出明确预算上限、已有器件、必须性能指标时，**先按硬约束过滤方案**；偏好不得覆盖硬约束。若预算和最低功能客观冲突，明确说明冲突与影响，不通过暗删功能凑预算。
- **成本优先**：同时考虑一次性器件/加工/安装成本、API/授权/网络等持续费用、实施与维护成本；价格、供应和时间必须有来源，未知时只做相对级别比较或标待询价。
- **性能优先**：选择对本项目实际有意义的性能指标，如精度、响应延迟、采集速率、并发量、功耗、通信可靠性、启动速度；不得把“更贵/频率更高”直接等同更高性能。
- **功能优先**：提高**已确认功能的覆盖深度、交互完整性与异常行为**，必要的支撑机制允许优化；**不能**自行添加摄像头、云端、App、联网等新的产品功能。
- **均衡方案**：优先选所有必需项合格、总体成本和复杂度适中、可开发可验证的稳定方案。
- 可由用户补充“预算上限、关键性能指标、最重要的既有功能”三个**可选**约束；除非缺失会改变核心可行性，否则不逐项索要。

实际权衡遵循 `references/optimization-and-tradeoff.md`，进阶探索见 `references/priority-driven-exploration.md`；首次选择的聊天措辞见 `templates/priority-choice.md`，内部候选记录使用 `templates/optimization-matrix.md`。偏好不是第五类输出文档，**仅在工程实施方案的必要选型章节呈现结论和依据，介绍文档不得出现评分/技术成本表**。

### 2.3.1 选择后必须产生真正的设计差异（V1.2 强化）

- 不能只在开头写“成本优先/性能优先/功能优先/均衡方案”，后文却对任何选项都照搬同一套设备和软件架构。
- 将目标翻译为本项目的**可观察决策准则**：成本至少分析总拥有成本；性能选择与目标场景相关的瓶颈指标；功能比较已确认功能的正常/异常闭环；均衡比较综合负担与关键指标余量。
- 先依据必要功能、合规/电气安全、既有器件、预算上限和最低性能过滤候选，再对**真正不同的** 2～3 条技术路线做同口径比较。不能制造虚假的型号差异或给无证据的定量评分。
- 内部每项关键选择记录：`需求/硬门槛 → 候选与证据 → 选定目标如何影响取舍 → 选择理由 → 放弃的优点/付出的代价 → 方案中具体改变的模块/参数 → 可验证指标`。正式实施文档只保留必要内容。
- 如果各方向经过核算确实得出**同一最合适架构**，允许相同结果，但必须说明性能/成本/功能边际收益不足以更换技术路线；不得人为制造差异。
- 不确定的市场价格、功耗、延迟或准确率只能标为待询价/待测试；关键不确定性应给出验证动作和决定是否更换候选的条件，不能把估算当实测。
- 用户可自愿补充一个**次优先目标**作为同等可行候选的裁决依据；非必要时不要为权重或量化预算额外发起多轮询问。


### 2.4 需求应被转换为可验收行为

每个一级/二级功能都建立内部要求矩阵（模板：`templates/requirement-matrix.md`）：

`REQ-ID → 场景与参与者 → 触发/输入 → 处理/状态 → 输出/数据去向 → 异常/边界 → 验收行为 → 状态及来源`。

在开始写实施方案前检查：是否还存在可能选错技术路线的重大歧义？若没有，即使未确认每项细枝末节也可继续。普通技术参数用默认值加明确依据/验证条件。

## 3. 逆向共性：功能→物理量/事件→硬件与软件职责

### 3.1 以四类匿名化案例反推方法，而非复制项目事实

参考 `assets/reference-samples/README.md`。至少先读 A（环境监测）和 C（LoRa 双向节点）；若是人体姿态/可穿戴场景再读 B；若是树莓派、语音、Web/AI 场景读 D。**示例是方法样本，不是用户新项目的硬件真实性证据。** 不能让新项目自动继承样本的型号、阈值、页数、时钟频率、IP 地址或功能。

### 3.2 每个模块必须先回答五个问题

1. **做什么**：使用者真正需要感知/控制/观看/触发的行为；拒绝把名称等同技术原理。
2. **测量/处理什么**：物理量、事件、音视频、文本、状态或协议数据；若需要算法，列出算法输入/输出。
3. **谁负责**：传感器内置算法、MCU、成熟 4G/LoRa DTU、Linux 进程、浏览器、第三方 API、云平台各自责任。
4. **通过什么连接**：硬件引脚/电气电平/总线/射频或 HTTP/WS/MQTT/ZMQ 等，必须含发送和接收方向。
5. **怎么证明可用**：可观察输出、真实测试方法与已知约束。

### 3.3 选型顺序不可倒置

`业务场景 → 功能行为 → 数据/物理量 → 用户设计侧重与硬性约束 → 核心检测方法或算法 → 可行候选技术路线 → 成本/性能/功能/复杂度权衡 → 外设/计算/供电预算 → MCU/Linux 主机选择 → 模块接口与架构 → 具体参数/引脚 → 测试验收`

当设备原有芯片被用户指定时，以现有硬件约束反向核算能否完成；不足时说明具体瓶颈，不直接替换既有器件。

### 3.4 通用设计决策

- **资源先行**：列 UART/I²C/SPI/ADC/DMA/GPIO、RAM/Flash、频率、音视频与网络、供电峰值等。先判断“够用与否”，再讨论性能冗余。
- **成熟模块复用**：4G DTU 可承接联网和 MQTT；LoRa UART 透传可承接射频；DMP/传感器自带算法可降低 MCU 算力压力；浏览器承担显示、音频播放/TTS；Linux 后端承担调度与 API。**每次核实实际产品规格与接口，不得想象能力。**
- **优先简单实现**：低速感知可用裸机 `Tick + Init/Process/Tick`；长阻塞/多并发/硬实时才综合考虑 RTOS；Linux 多媒体场景不强制 STM32。
- **规范数据路径**：驱动→数据接口（值、有效性、时间戳）→业务算法/显示/上报；必要时统一快照；绝不把失效旧值当实时新值。
- **协议双向核对**：发送端字段与接收端解析器必须兼容，尤其无效占位、LF/CRLF、多帧粘连、半帧、超时、重发与数据时效。
- **算法适用性**：阈值、回差、滤波、状态机、时间确认按实际业务风险选择；简单并不等于可无证据宣称准确率。
- **测试先行**：有硬件时先验独立模块；无硬件时 Mock 可验证上层数据流，**直写算法输出不等于测试算法本身**。

详见 `references/design-reverse-engineering.md`、`references/embedded-hardware-and-firmware.md` 和 `references/linux-ai-and-web.md`。

## 4. 文档一：《项目介绍与功能说明》严格内容规范

正式文件仅可包含与项目本身相关的内容。使用 `templates/introduction-outline.md` 的**适用**章节，不必为凑齐章节而写不存在的场景。

**推荐结构**：标题/版本/依据 → 目录 → 项目简介 → 场景及目标 → 功能介绍（对用户功能树逐项对应）→ 交互或运行流程 → 系统组成概览（只写类别/协作）→ 项目特点（如有事实支持）→ 使用条件或必要限制 → 功能展示/验收场景（仅用户可观察结果）。

**不得写入**：MCU 逐脚定义、CubeMX 设定、协议详细帧结构、API JSON、代码目录、实现源码、详细施工步骤、复杂异常状态机、成本核算、后续升级/优化建议、商业收费说明。

措辞按事实状态区分：只有方案时用“设计支持/计划实现/预期”；有源码但无实测时用“源码包含相应逻辑”，不自称“已稳定运行”。不做抽象营销词堆砌，不复制新项目未要求的功能。

详见 `references/introduction-writing-boundary.md`。

## 4.5 文档三：《项目介绍与功能说明》HTML（v1.3.0 新增）

HTML 是介绍 MD 的可视化表达，**不是第三套项目事实，也不是用户项目的正式前端系统**。它只读取同版本的《项目介绍与功能说明.md》，不得读取或摘录《工程实施方案.md》。

### 4.5.1 硬性要求

- 单文件 HTML：CSS 与 JavaScript 内嵌，双击即可离线打开；不依赖 CDN、远程字体、在线图标、外部图片或远程脚本。
- 内容一致：项目名、功能、流程、场景、系统组成、验收场景必须能在介绍 MD 中找到来源；允许标题简化、分组、摘要和排版调整，不得改变原意、补充未确认功能或虚构数据。
- 动态适配：功能 3/6/10+ 个、流程 3/6/10+ 步、场景 1/多个、系统组成若干项均可正常排布；缺失章节隐藏，不用空卡片或编造内容填补。
- 统一视觉：固定使用 `templates/project-introduction.html` 的配色、卡片、暗色场景面板和 1000/750/500 响应断点；不得每个项目重新设计一套风格，也不得把示例项目的“4 个货位/重量数值”固化进模板。
- 内容边界：不出现 GPIO/引脚表、电气接线、协议帧、代码、API 密钥、部署命令、收费说明、后续改进建议或工程实施交付说明。

- 安全：所有 Markdown 文本转义后写入；禁止把用户文本交给 `innerHTML`；禁止内联事件处理器、`javascript:` 链接、`eval` 与表单。

## 5. 文档二：《工程实施方案》严格实施规范

正式文件以 `templates/implementation-outline.md` 为结构基线，**按照项目类型适配**。不要把 STM32 的 GPIO 表强塞进纯 Linux/AI 系统，也不要把 WebSocket、云平台、数据库加入没有这些需求的单片机节点。

### 5.1 必须覆盖的实施要素（适用者全部覆盖）

1. **已确认功能、优化侧重与实施基线**：用户明确要求、成本/性能/功能/均衡的已选或拟定偏好、不可妥协约束、最小工作闭环；不引入未经授权的独立功能。
2. **候选路线与可解释选型**：对真正影响方案的主控/软件平台/通信/关键传感器等决策，比较通常 2～3 个可实施方案，说明成本（含长期费用）、关键性能、既有功能满足度、实施风险与验证难度；**先剔除违反硬约束的候选，再按偏好择优**。没证据的价格或性能不写精确数字，比较表只放实施方案。
3. **系统数据流和职责分工**：物理链路/数据方向、模块层级、实时状态、正常与异常流程。两端/多端通信必须画出每端各自行为。
4. **软硬件与资源核算**：具体器件（备选 vs 已确认）、供电与电平、接口占用、I²C 地址与冲突、UART 参数、DMA、定时器、内存、系统负载；纯软件项目转为计算资源、服务、网络与端口核算。
5. **接线/配置**：确定器件封装/模块接口后给 GPIO/外设表；未知时给**条件性接线表**与待核对手册，不能虚构已确认引脚。Linux 场景明确系统版本、依赖、服务与进程连接。
6. **固件/软件架构**：程序目录、每模块输入/输出、公共驱动或服务、数据结构/状态机/调度周期/并发边界、真实与模拟数据路径。
7. **协议/API 契约**：含至少正常包、无效/超时包、双端解释、数据校验和重连/错误处理；云服务的凭证与合法性由后端/模块负责，不把 secret 写进正文或代码示例。
8. **业务逻辑**：阈值和去抖、模式/按键、声音/图像/AI 动作（视项目）、告警联动与设备故障下系统行为；仅实现既定需求。
9. **分阶段实施**：准备/独立模块/主数据流/交互与通信/系统联调/稳定性，逐阶段输出可观察物和明确验收门槛；顺序根据依赖调整。
10. **测试、排障与技术来源**：测试条件、操作、预期/已测证据栏、数据有效性、断线/断网/旧数据处理、手册来源；无法验证则明示待验证，不能写 PASS。

### 5.2 技术准确性红线

- 传感器的**具体型号**和官方手册必须匹配测量命令、寄存器、波特率、CRC/校验与换算公式。名称相近（例如 SHT3x 与 SHT4x）不能直接复用协议。
- 串口 DMA 配置和**实际执行路径**不同的情况必须区分（例如 DMA TX + 单字节中断 RX）。
- 物理接口必须区分 TTL UART、RS232、RS485；若 RS485 无 DE/RE GPIO，必须核对是否使用自动方向收发器，不能凭空编 DE/RE 引脚。
- 不能以“MCU 已经调用发送函数”证明 LoRa 对端收到、MQTT Broker 收到或云端物模型存储成功；逐级定义链路证据。
- 软件测试桩必须区分原始输入模拟、算法输出模拟和端到端实机测试。
- 外部 API、音乐音源、TTS、ASR、LLM 供应商的能力、权限和稳定性须核实；不得假设非官方、未授权的音乐播放地址永久有效。
- 对关乎安全的检测（例如摔倒、火焰、森林火灾），不得用未经验证的简单阈值宣称专业可靠。
- 安装/部署命令与工具版本若未经运行，仅能标“拟用步骤”；不能写“本机已成功”。

### 5.3 文本边界

正文只允许**实现该项目必须掌握的技术细节**。不得出现项目收费/付费/交付包装、Skill 操作、销售策略或独立的“已知问题与改进建议”。

**可以**写：必要的待确认实施条件、明确参数、测试/排障步骤、技术源链接和限制。

**不可以**写：没有关联的硬件扩展、通用“后续可增加 AI/4G/APP”等提议、对用户的个人建议、面向产品营销的解释。

详见 `references/implementation-writing-boundary.md`、`references/protocol-and-validation.md`。

## 6. 来源、状态与引用

根据输入建立内部证据矩阵，状态至少区分：

| 状态 | 含义 | 允许说法 |
|---|---|---|
| `confirmed` | 用户明确确认需求/约束 | “本项目要求……” |
| `proposed` | 本 Skill 为规划工作拟定 | “实施基线采用……（拟定）” |
| `code_present` | 代码中存在实际函数/调用路径 | “源码存在……逻辑” |
| `declared` | README、现有技术文档中的描述 | “资料声明……” |
| `mock` | 模拟数据/Mock 流程 | “模拟环境可验证……” |
| `tested` | 有对应真实测试日志、记录、观测或用户确认的证据 | “在×条件下已验证……” |
| `unknown` | 冲突或欠缺证据 | “尚需核对……；此项不作既有事实断言” |

- **事实与规划必须分开**。技术文档标为“功能已实现”只证明文档如此声明；源码中存在函数也不一定被主程序调用；测试计划不是测试报告。
- 若用户提供源码，先明确已实际调用/未接入/空回调/`#if 0`/Mock 配置，不能凭 README 宣称已验证；只读取用户明确给出的目录或文件。
- 具体产品规格、协议、法律、服务价格/政策若会影响方案，优先核对厂家、标准、官方开发者文档；查不到就标条件，不编造网址、参数或供应商承诺。
- 项目引用资料在 `project-assets/references.json` 复用（若已有），最终工程文档只保留与实现真正有关的原始参考资料；公开介绍文档不强制技术引文列表。
- Agent 推理出的具体数值（周期/阈值/波特率）要标**默认值**或**待实测确定**，不能混入“用户指定参数”。

详见 `references/facts-and-source-policy.md`。

## 7. 双文档一致性与边界门禁

写正文之前先在运行区生成 `requirements-matrix.md`、`decisions.md`、`design-freeze.md`（内部草稿，不是交付文档）。逐条对齐 `REQ-ID`：

- 每个**已确认**一级/二级功能在介绍文档能找到对应行为；在实施方案能找到实现责任、关键流程与验收；两份不允许互相矛盾。
- 介绍文档只写**做什么、何时发生、用户能看到什么**；实施方案写**为什么选、怎么接、怎么写、怎么调、怎么验证**。
- 统一项目名、功能术语、型号的确认状态、时间/阈值和版本；默认参数在介绍中不必展开，但不能与实施矛盾。
- **设计目标追踪**：内部记录 `optimization.priority` 的用户确认/拟定来源、可选 `secondary_priority` 与具体目标指标；实施方案必须表现“硬约束→候选差异→选定原因→舍弃代价→实施变化→测量验收”的闭环。仅写偏好标签但没有可定位的技术选择属于 FAIL（人工工程质量门禁）；公开介绍不出现成本/性能/功能权重评分。任何优先级都不可违反安全、功能底线、既有资料及用户明确的预算/性能硬门槛。
- 未经明确确认的新功能不能进入“必做项”；技术基础设施（看门狗、错误处理、日志）可作为**实现必需的内部机制**，不得暗中变成产品功能扩展。
- 若输入技术资料与新方案矛盾，用户要求“复现既有方案”时保持原方案并备注技术风险，不偷偷替换成更理想架构；用户要求“重新规划”时按新方案写，并在内部决策记录区别于现有实现。
- **写前冻结**：`design-freeze.md` 固化术语/默认值、页面映射、数据结构与配置布局、协议字段、状态枚举与优先级、资源/接口、失败分支、测试追溯；两份草稿的跨文档引用以冻结表为唯一来源。冻结后改动须先登记，再一次性同步所有受影响章节并复检；禁止边写边定造成连锁返工（见 `references/design-freeze-and-consistency.md`）。
- **三份成品一致性**：介绍 MD 与介绍 HTML 的项目名、功能、场景、默认值和状态名必须一致；HTML 只引用介绍 MD，不引用工程实施方案；实施方案可以补充实现细节，但不得引入介绍 MD 未覆盖的用户可见功能或改变已确认行为。
- **HTML 专属边界**：介绍 HTML 不出现 GPIO/引脚表、电气接线、协议帧、代码、API 密钥、部署命令、收费说明或后续改进建议；无内容区块隐藏而不是编造（见 4.5 节）。

运行 `scripts/validate_docs.py` 检查两份 MD 的格式、越界章节、需求覆盖与章节完整性；运行 `scripts/validate_intro_html.py` 检查介绍 HTML 的离线单文件、内容边界、功能一致性与场景标注。两个脚本都是**静态初检**，人工仍必须逐章节审阅技术可实施性、引用与一致性，并在有浏览器时做桌面/移动视觉检查。质量门禁详见 `references/quality-gates.md` 与 `references/html-quality-check.md`。

## 8. 标准执行顺序

### 分批写入与一次终检（硬性，禁止一次性整篇生成）

- **介绍 MD 至少 4 批**：`00-meta` → `01-overview` → `02-scenarios` → `03-features` → `04-system-workflow` → `05-boundaries-demo`；功能很多时把 `03-features` 再拆成 `03a`/`03b`。每批写入 `$WORKDIR/batches/introduction/*.md`，一批落盘后再写下一批。
- **实施 MD 至少 4 批**：范围/基线 → 架构/数据流 → 选型/资源 → 接口/连接 → 软件架构 → 核心功能 → 协议/数据 → 调度/可靠性 → 阶段实施 → 测试验收 → 技术依据；每批写入 `$WORKDIR/batches/implementation/*.md`。
- **禁止一次性倾倒整份文档**：只有 `00-meta.md` 写项目一级标题，其余批次只写 `##`/`###` 章节；不得用一个超大写入调用生成整份介绍或整份实施。
- **组装后才做 HTML**：全部介绍批次落盘后运行 `scripts/compose_markdown.py` 组装 `draft-introduction.md`；组装成功后才用 `generate_intro_html.py` 生成 HTML。实施批次同样先组装再校验。
- **一次终检**：两份草稿组装完成后运行 `validate_docs.py` + `validate_intro_html.py` + 人工一次性复核；写作中途不反复全文重检。终检问题只修受影响批次、重新组装；介绍 MD 改动后重新生成 HTML；不推倒全部草稿。
- 执行汇报注明介绍/实施各分几批、每批包含哪些章节与一次终检结论。详见 `references/batch-writing.md`。

1. **启动与必填项收集（硬门禁）**：无论用户是否已写项目资料，都先按第 0.4 节从当前消息/已有对话/对应项目资产提取题目和功能；缺任一项即**主动询问且暂停本次正式生成**。不得生成占位项目，也不得先做硬件选型；可用 `scripts/check_input.py` 做结构化初检。
2. **识别模式与状态**：A/B/C/D；判断是否为拟实施方案或基于真实代码的方案，对每条需求标 `confirmed/proposed/unknown`。
3. **重大歧义与设计目标门禁**：仅在题目与功能均具备后，只对会导致方向错误的重大歧义提问；同时让用户一次性选择成本优先、性能优先、功能优先或均衡（已选不重复问）。用户要求直接执行时均衡拟定。不逐轮穷举技术细节。
4. **目标驱动的候选探索与择优**：依次执行资格过滤→根据选定侧重明确优先指标→探索 2～3 条有实质差异的候选→同口径对照→明确选择与代价→记录对硬件/协议/模块/阶段验收的具体影响。若只存在一条有效方案，则说明不可替代的硬约束和待验证前提，不制造无意义候选；参照 `references/priority-driven-exploration.md`。
5. **建立功能与证据矩阵**：功能→输入/输出→物理量/算法→接口/双端数据流→验收；已有真实代码则标文件、函数与证据状态。
6. **逆向/核对参考**：按项目类型阅读 `assets/reference-samples/` 的 A/C 或 B/D，提取方法，不抄案例事实；对关键硬件/服务能力核实官方资料。
7. **完成工程决策并追踪偏好影响**：硬件或计算平台、外设/进程、数据分层、通信协议、状态机与最小闭环；将每个关键默认值、各候选资格、选中/放弃理由、取舍代价、影响的实施章节和拟测指标记入 `decisions.md`，确保“用户偏好→选型结果→实施细节→验收项”可追溯。
7.5 **设计冻结（写正文前）**：在 WORKDIR 生成 `design-freeze.md`，冻结术语/默认值、页面/交互映射、数据结构与配置布局、协议字段与空值语义、状态枚举与优先级、资源/接口、失败分支、测试追溯；冻结表是两份草稿的唯一跨文档来源。冻结后若改动任一项，必须先在变更记录中登记，再一次性同步所有受影响章节并重跑校验（见 `references/design-freeze-and-consistency.md`，模板 `templates/design-freeze.md`）。禁止边写边定造成连锁返工。
8. **先写项目介绍（分批 → compose）**：按 8 节批次规则逐批写入 `$WORKDIR/batches/introduction/`，每批落盘后再写下一批；全部落盘后运行 `compose_markdown.py --kind introduction` 组装 `draft-introduction.md`。套用 `templates/introduction-outline.md` 的适用部分；检查描述准确、完整且易懂，不出现接线/API/售价/执行指南。
8.5 **生成介绍 HTML**：以组装后的 `draft-introduction.md` 为唯一内容源，运行 `scripts/generate_intro_html.py` 生成同版本单文件 HTML；运行 `scripts/validate_intro_html.py` 检查离线单文件、内容边界、功能一致性与场景“未实测”标注。仅要求重做 HTML 时复用已确认的介绍 MD，不重新规划项目。
9. **再写工程实施（分批 → compose）**：按 8 节批次规则逐批写入 `$WORKDIR/batches/implementation/`，全部落盘后运行 `compose_markdown.py --kind implementation` 组装 `draft-implementation.md`；套用 `templates/implementation-outline.md` 的适用部分。给出实际可执行细节、阶段门禁、失败分支和验收；不得仅凭宏/库名称推断功能已验证。
10. **三份成品审阅与自动校验**：交叉比对介绍 MD、介绍 HTML 与实施方案的功能/术语/默认值/状态；检查协议双端、数据失效/时效、资源冲突、用户边界与“无建议章节”；分别运行 `validate_docs.py` 与 `validate_intro_html.py`。有浏览器时补做桌面/移动截图检查。失败先修文档，再完整复检。
11. **版本成品与汇报**：保存两份独立 UTF-8 `.md` 与同版本单文件 `.html`，均带 `-vN`，不覆盖历史。在聊天中按 `templates/execution-report.md` 列出三份成品路径、文档覆盖、采用的关键默认值、来源/实测状态、HTML 静态与视觉检查结果；最终验收由用户决定。
12. **安全清理**：仅删除本轮生成的运行区临时文件；保留用户源资料、稳定资产与历史成品。

## 9. 快速运行（Claude Code / Codex / Python）

首次只输入“调用 project-solution-write”时，**先按 `templates/initial-intake-message.md` 主动问项目题目与功能**；不要运行工作区初始化或文档校验来代替问询。收到资料后可用下述结构化初检；缺项时状态为 `NEEDS_INPUT`，立即以聊天消息询问、停止正式生成。

```bash
python scripts/check_input.py --input templates/input-example.json
# 真实执行时使用从当前用户资料/项目已确认资产提取的输入 JSON；不要直接使用示例数据。
# 将整个 Skill 目录安装到支持 SKILL.md 的本地 Skills 路径；这里仅给出工具调用示例。
# 项目目录必须与 Skill 安装目录分开。
python scripts/project_workspace.py init --root "$PROJECT_ROOT" --project-id "$PROJECT_ID" --title "$PROJECT_TITLE"
python scripts/project_workspace.py status --root "$PROJECT_ROOT"

# 建本轮运行区（带所有权标记 .owned-by-project-solution-write），输出 WORKDIR 与 RUN_ID
python scripts/project_workspace.py workdir --root "$PROJECT_ROOT" --project-id "$PROJECT_ID"

# Agent 在 WORKDIR 内形成：requirements-matrix.md、decisions.md、design-freeze.md、
# batches/introduction/*.md、batches/implementation/*.md、draft-introduction.md、draft-introduction.html、draft-implementation.md
# 介绍与实施均先分批落盘，禁止一次性整篇生成
# 需要跨轮复用的功能/决策资产经 write-asset 落库（持 .asset-write.lock、原子写、activity 留痕）
python scripts/project_workspace.py write-asset --root "$PROJECT_ROOT" --project-id "$PROJECT_ID" \

# 全部批次落盘后组装（介绍先组装再生成 HTML；实施独立组装）
python scripts/compose_markdown.py \
  --parts-dir "$WORKDIR/batches/introduction" --out "$WORKDIR/draft-introduction.md" \
  --kind introduction --title "$PROJECT_TITLE" --report "$WORKDIR/compose-introduction.json"
python scripts/compose_markdown.py \
  --parts-dir "$WORKDIR/batches/implementation" --out "$WORKDIR/draft-implementation.md" \

# HTML 与介绍 MD 共用 -vN；介绍 MD 改动后重新生成，视觉调整不得反向改写 MD

python -m unittest discover -s tests -v
```

## 10. 失败、待确认与用户验收

- **FAIL**：在题目或功能缺失时仍擅自生成项目方案、缺失用户明确功能、违反明确成本/性能/功能侧重的必要硬约束或完全不按已选偏好做选型、技术路线与用户确认需求相矛盾、伪造测试、把模拟值当实测、出现禁止章节、两份 MD 或介绍 HTML 混入彼此内容、介绍 HTML 出现实施层细节/虚构数据/外部依赖/功能与介绍 MD 不一致、明显非法或错误的电气连接/接口协议。
- **WARN**：关键器件具体规格、对端协议、外部 API、部署环境尚未核实；HTML 静态检查出现 WARN、缺少可选章节或未做浏览器视觉验收；作为实施前提或验收条件逐项列明，不冒充已确认。
- **PASS**：核心需求覆盖，功能链路可实施，文档边界分明、引用与状态真实，两份 MD 与介绍 HTML 的静态检查通过且已做人工工程逻辑审阅。PASS 只代表**文档质量门禁**，不代表系统已实机运行，也不等于浏览器视觉验收已完成。
- 用户可修改参考规范与要求，Agent 应重执行本次文档并报告所做修订；不未经请求额外生成第三份正式报告。

**最终原则：先理解真实需求，再根据用户选择的成本/性能/功能/均衡侧重探索候选路线，独立确定符合硬约束的最优适用方案；介绍只讲项目，介绍页只复述介绍，实施只讲落地；不臆造、不越界、不堆砌、不遗漏真实功能。**
