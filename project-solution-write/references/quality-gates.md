# 双文档质量门禁：PASS / WARN / FAIL

## G0 启动输入完备性（先于 G1-G6）

- 新用户只启动 Skill 时，已主动询问项目题目、功能需求（一次性收集）。
- 项目题目和功能至少各有明确的用户输入/明确引用的已有项目资料；未提供时不得产生正式两份 MD，也不进入技术选型。
- 标题缺失只问题目，功能缺失只问功能；既有项目有确认记录时不重复问。设计侧重缺失可合并在同轮询问，但属于可选偏好；用户要求直接生成时只默认均衡，不能捏造题目和功能。
- 结构化可运行 `scripts/check_input.py` 初检；Agent 还必须人工判断功能是否空泛到无法定路线。

## G1 需求真实性

- 已确认的用户一级和二级功能被逐项覆盖，不改变关键名词的原意。
- 用户重大歧义先澄清；Agent 独立决定普通技术细节并标拟定与适用条件。
- 没有把“LoRa 节点”自动等同单向、把“人体检测”自动等同存在检测。

## G2 工程可实施性

- 未指定设计偏好时已经向用户提供成本/性能/功能/均衡四项选择（用户要求直接执行时按均衡拟定）；已指定时不重复问。
- 已选偏好在实施方案有**明确的技术影响**：至少一处主要方案取舍体现当前侧重，形成 `优先目标 → 候选差异 → 选择依据 → 舍弃代价 → 方案落地 → 可验收指标`，不能只贴“成本优先”标签而不改变选型判断。若最终方案对不同偏好相同，必须解释同解的硬约束或边际收益。
- 关键候选路线已经过硬约束过滤；必要时有精简的成本/性能/功能完整度/工程难度对照，并说明最终选择与不选其他方案的原因。
- 任何优化都不删减必需功能、不虚构性能或市场价格；评分只能作为辅助，不抵消安全、兼容或用户硬预算底线。
- 写正文前已完成设计冻结（`design-freeze.md`）：术语/默认值、页面映射、数据结构/配置布局、协议字段、状态枚举与优先级、资源/接口、失败分支、测试追溯均已固化；冻结后变更已同步所有受影响章节并复检。
- 静态 `validate_docs.py` PASS 只是初检；人工复核按“双文档一致性→协议双端→配置/资源→失败分支→需求覆盖”一次完成，不得用边写边改代替冻结。

- 类型正确：STM32 工程核算 GPIO/外设、接口、电平、供电；Linux/Web 工程核算软件服务、进程、音视频与网络。
- 设备选型理由能回溯到需求与物理量/算法，不为堆硬件而选更高规格。
- 所有通信均有发送者、接收者、帧/请求格式、有效/无效/断流处理与送达判断。
- 代码层实现描述有 Init/Process/Tick 或服务/状态机等职责，数据有效性、异常恢复和真实验收路径清楚。
- 真实芯片命令/换算/CRC/SDK 服务能力需有可靠原始来源；未经核实标条件。

## G3 介绍文档边界

- 正确章节：简介、场景/目标、功能（用户树逐项对应）、流程、概览、使用条件与预期效果。
- 无逐脚接线、代码/API JSON、调试命令、巨大硬件选型表、供应商报价/方案评分、收费文字。
- 没有增加独立“后续优化/扩展/已知问题与改进建议/工程实施交付说明”。

## G4 实施文档边界

- 有具体硬件/软件实现、接口/协议、数据、调度、开发阶段与验收；仅保留对本项目真正适用的技术层。
- 没有营销、定价、付费免费区别、Agent 说明、无关建议或扩展。
- 文档的技术设计和用户确定的真实既有方案不能静默冲突。

## G5 证据状态与测试

- 区分拟实施、资料声明、源码路径、模拟数据、真实运行证据。
- 不用测试计划当已通过结果；不编造数据、指标、真实云端连通性或供应商权限。
- 逐项检查最小闭环 + 异常、断网/失效、远端帧解析、音频回声/自动播放等适用问题。

## G6 文件和生命周期

- 两个 UTF-8 独立 MD，有目录、清晰标题层级，文件名带 `-vN`，不覆盖历史。
- 双文档术语和项目题目一致；没有样本项串项目。
- `design-freeze.md` 仅存在于本轮运行区，不进入 `deliverables/`；清理运行区时随草稿删除，成品只保留两份 MD 与派生 HTML。
- 分批写入：介绍/实施各至少 4 批，每批落盘后再写下一批；全部批次落盘后 `compose_markdown.py` 组装，随后一次终检；执行汇报注明批次数与终检结论。少于 4 批必须在汇报中说明理由，禁止一次性整篇生成。
- 执行 `scripts/validate_docs.py` 并查看结果；自动检查不等于人工技术验收。
- 项目资产未被覆盖或错误迁移，本轮临时文件已清理且用户资料未删。

## G7 项目介绍 HTML 可视化

- 介绍 HTML 只读同版本介绍 MD，不读取工程实施方案；页面中的项目名、功能、场景、系统组成、验收场景均能在介绍 MD 找到来源。
- 单文件离线：CSS/JS 内嵌，无 CDN、远程字体、在线图标、外部图片或远程脚本；可双击直接打开。
- 内容边界：无 GPIO/引脚/电气接线/协议帧/代码/API 密钥/部署命令/收费/后续建议；无虚构数据或实测结论。
- 动态适配：功能 3/6/10+、流程 3/6/10+、场景 1/多个、长标题/长描述均正常；缺失章节隐藏，不出现空卡片。
- 响应式：桌面/平板/手机无横向溢出；关键断点 1000/750/500；长文本有 `overflow-wrap`；浮动标签在小屏隐藏。
- 安全：用户文本转义；无 `innerHTML`、`eval`、内联事件处理器、`javascript:` 链接或表单。
- 场景示意只使用介绍 MD 的验收场景表，固定标注“验收场景 · 预期结果 · 未实测”。
- 生成器 `scripts/generate_intro_html.py` 与校验器 `scripts/validate_intro_html.py` 存在且通过；静态 PASS 不等于浏览器视觉验收，有浏览器时补截图检查，无则如实说明。

**FAIL**：任何 G0-G4 重大违规/事实造假/文档越界，或 G7 的内容边界/离线/安全硬失败。**WARN**：资料不足、设备/服务待实物核实、无法执行某项测试、HTML 静态 WARN 或未做浏览器视觉验收。**PASS**：结构/覆盖/工程逻辑检查通过，介绍 HTML 静态与内容一致性通过（不代表系统实际已验收，也不代表视觉验收已完成）。


## G8 探索推荐与候选资产门禁（V1.4.0）

- 只有专业/技术关键词即可推荐，不要求预先有项目题目和功能；专业/技术/题目信息可混合，不要求用户选入口。
- 每批新候选 ≤10；对历史全部项目包括 rejected 做语义去重，不凑数；拒绝不会删除记录，明确恢复沿用旧 ID。
- 每个项目分别生成 MD、DOCX、HTML，仅包含名称、概述、核心功能简述，不出现推荐理由、评分、工程细节或其他建议。
- 三份从同一结构化内容生成，数量/标题/说明必须完全一致；缺失任一文件失败，不得报成功。
- 功能更新保留旧版本与 stable ID；只在用户明确确认题目和功能后转 confirmed。
- 该门禁只作用于探索阶段；正式方案的原有 G0-G7 完全保留。
