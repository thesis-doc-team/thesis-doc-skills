# 《工程实施方案》文本边界与深度

**唯一读者目标：** 能据此采购/连接/配置/开发/联调/验收，而非看一份营销介绍。标题和章节使用工程语言，不包含对作者、收费、技能、交付包装的议论。

## 章节深度判据

- 技术选择必须有依据：需求如何导致模块选择；为什么不需要复杂芯片/RTOS/自建云；既有器件和约束是否继承。
- 接口要能落地：电平和电源；GPIO 引脚/复用；采样/协议/端口；错误处理。若实物型号未定，不提供虚假的“最终引脚锁定”。
- 数据要能复用：结构体/字段/单位/有效性/时间戳；业务使用者是谁。
- 通信要能双端匹配：帧与解析器一致，缺失字段、超时、断连、旧数据以及 ACK 是否启用及原因。
- 算法要有输入与输出：状态机/阈值/确认时间，含误判和验收条件；不得凭空给精度或性能结论。
- 开发路径要分阶段：每阶段前置条件、完成事项、观测办法、通过标准；错误案例能按链路定位。
- 对第三方接口要核实：API/SDK/具体型号、合法权限与环境限制，不可编造文档网址。

## 不允许的边界越出

- 成品正文不出现“本付费文档”“交付说明”“给学生的建议”“商业价值/定价方式”“可扩展的额外功能”。
- 不为了篇幅硬塞不适用的领域：无数据库不列库表，无 RTOS 不画任务优先级，无云平台不堆云服务设计。
- 不把全部技术参数设置为待确认后结束：Agent 必须先作合理选择，只有确实依赖实物的关键参数可留条件。
- 不把工程方案写成“通用建议清单”：明确针对该功能的模块、数据流、时序和验收。

## 设计阶段与源码阶段

拟实施文件写“拟采用/设计为/验证目标”；已有源码仅可写“源码实现了……调用路径”，已编译或已测试必须另有证据。对现有实际方案要保留实现事实，不偷偷将其替换为理想方案。对确定错误的技术规范，应给可核查依据和阻断风险说明，不把错误当既有合理默认。
