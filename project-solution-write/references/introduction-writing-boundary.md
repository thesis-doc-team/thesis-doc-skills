# 《项目介绍与功能说明》文本边界

**唯一读者目标：** 快速理解项目是什么、为何有用、提供什么功能、如何交互、有什么使用条件。围绕用户功能树逐项介绍，力求结构清楚、准确直观，不写空泛宣传。

## 正文结构

1. 项目简介：定位和用途，不能伪称已真实交付。
2. 应用场景与目标：来自用户描述/合理约束，未知不写假故事。
3. 功能模块：保持用户原始一级/二级功能覆盖，说明触发、输出和体验。
4. 使用/交互流程：可以有流程图，但不写代码/协议帧。
5. 系统组成概览：用“感知、控制、显示、通信、云端”等逻辑层说明协同，不列 GPIO 引脚。
6. 项目特点：仅与功能直接相关，不能新增功能。
7. 使用条件与限制：网络/传感器/服务依赖的必要说明，简洁。
8. 功能展示/验收场景：用户可观察的行为，明确“预期”与“已验证”。

## 严禁

- `工程实施交付说明`、价格、收费、分层销售、交付策略、读者购买指南；
- “未来可增加”“下一步建议”“已知问题与改进建议”等附加章节；
- CubeMX/引脚、代码目录、数据库表结构、具体 CRC、API 请求与响应完整 JSON、调试命令；
- 把方案目标写成实时准确率、联网成功或长期稳定已实测通过；
- 把“介绍文档”写成“技术方案”的压缩版，泄露成套具体实现细节。

允许必要术语，例如 LoRa、STM32、TTS，但只到用户理解项目所需程度。

## HTML 表达边界

- HTML 只读取同版本的介绍 MD，**不读取工程实施方案**；页面内容必须能在介绍 MD 中找到来源。
- 允许标题简化、分组、摘要和图文排版；不得新增功能、指标、实测结果，不得把示例项目的业务数据（如四个货位、24 件、60.0 kg）当成本项目数据。
- 不出现 GPIO/引脚/电气接线/协议帧/代码/API 密钥/部署命令/收费说明/后续改进建议。
- 使用固定视觉模板与响应式断点；缺失章节隐藏而不是编造；场景示意固定标注“验收场景 · 预期结果 · 未实测”。
- 详见 `references/html-visualization-rules.md`、`references/html-content-mapping.md`、`references/html-quality-check.md`。
