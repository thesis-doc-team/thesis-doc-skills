# 推荐阶段的简要文案与三格式规则

## 唯一对外正文结构

每个候选项目都只出现：

1. **项目名称**：清楚准确、适当反映应用，不为吸引眼球编造“首创/高精度/实测”等宣传。
2. **项目概述**：一小段描述系统服务什么场景、解决什么事情、整体工作思路；不是工程架构方案。
3. **核心功能**：若干功能名 + 每项 1～2 句具体、可理解的行为说明。不得只列“智能检测”“云平台”等空泛词。

不写“推荐理由”“推荐指数”“适合人群”“难度打分”“成本打分”“技术选型对比”“方案论证”“后续扩展/改进建议”“收费/交付说明”；不写具体 GPIO、接线表、协议帧、完整 API、调度周期或工程实施步骤。专业、技术、资源、兴趣、能力可以用于后台筛选，但不要额外生成这些字段作为正式候选文档章节。

## 生成形态

- 每个项目独立一个 Word DOCX、一个 Markdown、一个离线 HTML，**一项目=一组三文件**。
- Word 使用 A4、规范中文字体、可打印，文字内容与 MD/HTML 一致，不强制页面数。
- HTML 保留原介绍页面的蓝白科技卡通视觉语言，但不是把智能仓储的货位交互复用到不相关项目；无联网/CDN/外部脚本，内容输出进行 HTML 转义。
- 同一结构化 JSON 输出三份文件，所有版本的功能条目数、顺序、标题、描述一致；HTML 不提供虚构实时数据演示。
- DOCX 使用 **C 版杂志编辑版式**：A4、Noto Serif/Sans、暖橙/奶油底、2 列概述条、3 列功能表、橙色页脚；支持 3–15 功能与长文本自然分页。实现见 `render_candidate.make_docx`，规范见 `candidate-docx-magazine-style.md`；不得把 C 示例的老人拐杖业务文字固化进模板。
- DOCX 如需生成时，应安装 `python-docx`。如果环境缺包，**本批次未完成，明确报错而不是静默缺 Word 交差**。
- 生成后进行程序检查与必要的 Word 渲染、人工视觉抽查；程序 PASS 不代表可读性/技术可行性已人工验收。

## 阶段边界

推荐只解决“这是什么项目、会有哪些功能”。正式项目被用户明确确认后，才能把项目概述与确认功能作为需求输入，调用原有工程实施方案 Skill 流程。推荐阶段**不生成完整的项目介绍与功能说明、完整介绍 HTML 或工程实施方案**。

## 毕设/课程设计候选的功能-场景-规模专向

在通用三格式规则之上，面向毕业设计/课程设计的候选还必须满足以下约束。不满足的候选应由 `scripts/validate_discovery.py --purpose graduation_capstone` 拦截或警告：

1. **功能下限**：每个候选核心功能不少于 7 条；具体数量由题目发散研究决定（通常 8–12 条，最多 15 条）。先按用户/场景/对象/物理量/交互/告警/通信/配置/异常/数据等维度发散，再合并剔除不可验证项，不要用 7 条同类“采集 X”凑数。
2. **功能闭环**：每条功能描述必须包含一个具体的触发→行为→可观察闭环。反例：“温度监测”——正例：“采集空气温度并每 5 秒刷新 OLED 显示；超过 45℃ 时蜂鸣器鸣叫，低于 40℃ 自动解除。”
3. **场景锚点**：overview 必须出现至少一个具体场所或用户类型（如“温室大棚”“宿舍楼道”“家庭厨房”“实验室货架”）。不能只写“环境监测”而不交代应用场景。
4. **模块化与单板可验证**：硬件描述默认使用市面上常见的传感器/通信模块（如 HX711、SHT40、ESP8266、HC-SR04、DS18B20 等）。**不得要求用户自绘 PCB、手工焊接、设计数模电路**。所有验证应在单块开发板或小装置上可独立完成；不依赖实验室大型设备、多点架设或云服务器集群。
5. **禁止假大空**：不得出现“大规模部署”“全自动生产线”“城市级”“完全覆盖”“首创”“世界一流”等无工程依据的修饰；不得把候选写成“智慧城市治理平台”“全自动无人仓库”等超纲项目。
6. **技术边界**：区分“学过”与“必须用”；profile 中不保留 `budget`、`timeframe` 字段——不作为推荐输出，只通过 `constraints` 表达规模/模块偏好。
7. **题目向上泛化**：题目只写“应用场景 + 核心能力”，不把单一作物、病害、算法名或具体型号写进题目。过窄的例子：“基于 STM32 的番茄叶片病斑识别系统”“基于 YOLO 的…”；泛化后：“面向温室大棚的环境监测与预警系统”“面向宿舍楼的进出管理与安全提醒系统”。过宽的例子：“智慧农业综合管理平台”；收窄后：“面向温室大棚的环境监测与预警系统”。具体对象/算法/型号放在 overview 或功能里，不放在题目里。

**功能发散研究法**：先按“用户 / 场景 / 对象 / 物理量 / 交互 / 告警 / 通信 / 配置 / 异常 / 数据”十个维度列出候选功能；再合并同类、剔除超边界或不可验证项；保留 7–15 条完整闭环功能，至少覆盖采集、显示、告警、通信、配置、异常、统计中的 4 类。不要用 7 条同类“采集 X”凑数，也不要为了数量硬加与场景无关的功能。
