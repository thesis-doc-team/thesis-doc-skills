# 需求解码与提问门禁（反向归纳）

## 零、第一次调用必须主动收集题目和功能

本规则的提问门禁不等于“用户缺信息就放弃”：**Skill 被调用时必须主动启动收集流程**。先在用户本轮消息、已有项目上下文、用户指定资料及正确归属的项目资产中寻找已明确的项目题目和功能；只有未提供时才询问。

| 已有信息 | 本轮必须采取的动作 |
|---|---|
| 无题目、无功能 | 主动同时询问题目和功能；可一次附带成本/性能/功能/均衡四选一 |
| 有题目、无功能 | 只问功能清单和具体使用行为，不重复问题目 |
| 无题目、有功能 | 只问项目题目，不重复问功能 |
| 二者已有、含重大歧义 | 问少量真正改变技术路线的关键问题 |
| 二者齐全、无重大歧义 | 按设计偏好门禁决定是否追问侧重，然后进入工程设计 |

标题只写“新项目/项目名/待定”或功能只有“功能待补”视为缺失。不能拿其他项目案例的题目或功能代替。即使用户说“立即生成”，也不能凭空写出题目或核心功能；用户授权代拟时先给拟定内容供其确认。具体措辞见 `../templates/initial-intake-message.md`。

## 一、两种失败模式

- 直接替用户假设：把“人体检测”解释为区域存在，实际需要计步、行走和摔倒；把“本地测试”解释为按键菜单，实际需要编译宏 Mock；把“LoRa 节点”解释为只发送数据，实际节点还接收并显示远端数据。
- 把选择全部交回用户：把 ACK、消抖、上传周期、串口分配等日常工程问题拆成几十个单选题。这会降低设计价值，也增加交互成本。

## 二、提问决策树

1. 用户提供的描述是否能推出**多个本质不同的实现目标**？
2. 不同解释是否会影响**感知原理、主要硬件、软件架构、使用者行为、预算、现场安装、验收方法**？
3. 上下文、已有资料或项目资产能否已经消除歧义？
4. 若仍有重大差异，集中问 1～3 个能决定路线的问题；否则自行选默认方案并解释条件。

关键问题通常优先级如下：**用途/任务对象 > 关键输入输出 > 必须支持的行为 > 部署/供电 > 既有硬件约束 > 可靠性要求**。普通采样频率等默认值不作为阻断条件。

## 三、设计目标偏好（同一轮集中选择）

即使功能很清晰，也要确保用户有机会表达成本、性能、功能或均衡的设计倾向。尚未指定时**主动给出四项简短选择**（措辞见 `../templates/priority-choice.md`）；如果用户要求直接生成或不想选择则默认均衡（仅标拟定）。不把这一步扩展为多轮问答；选定后将偏好解释为候选路线和可测量指标，而不是仅在文档标题贴标签。

- 成本优先：不牺牲已确认的功能和最低质量，降低采购+运行+开发/维护总成本。
- 性能优先：突出业务相关且可验证的精度、响应、吞吐、功耗、可靠性等指标。
- 功能优先：提高已确认功能的完整性与使用体验，不得自动新增用户未要求功能。
- 均衡方案：以可行性为硬门槛，综合成本、性能、功能、复杂度。

已有器件、预算、明确指标是比选型偏好更严格的约束。详细步骤见 `optimization-and-tradeoff.md`。

## 四、功能解码检查

- 名词必须落地成动词：环境监测→测哪个值、何时采样、如何展示、越限做什么；无线通信→哪一端发、哪端收、接收后做什么。
- 区分**产品功能**与**实现机制**：用户要求“按钮切页”是功能；KEY 消抖 20ms 是实现机制。后者 Agent 可自主决策。
- 从用户功能隐含必需的组件可以主动补全，例如传感器错误处理、连接状态显示、健康检查；但不能擅自把它们扩展为新的收费功能或可见模块。
- “报警”要先区分告警触发源、告警手段、消音是否影响判断；如果这些选择会影响真实使用才问，其他采用工程合理默认。

## 五、需求状态记录

| 字段 | 允许值/解释 |
|---|---|
| `id` | REQ-001 等唯一标识 |
| `name` | 用户原始功能名称，尽量保留 |
| `status` | confirmed / assumed / unknown |
| `origin` | 本轮用户、已有资料、推导、引用资产 |
| `interpretation` | 功能的精确定义 |
| `acceptance` | 可观察的验收动作 |
| `why_question` | 只有 unknown 且重要时写明为何会改变路线 |

**严禁把 Agent 的 assumed 写回项目资产成为 confirmed。** 用户改口时更新对应 REQ-ID 的解释与决策，保持审计记录，而不是创建一个并行的冲突定义。

## 六、直接示例

原始需求：“LoRa 无线通信、本地显示、按键短按切页”。如果已有资料显示页面分别展示本机/远端数据，则主动推导本端接收能力，不必追问是否需要 ACK。若用户只说“一端向另一端发送”且没有要求远端回传，则可先采用单向主动上报的拟实施基线。关键是保留用户明确的通信角色，不擅自追加远程控制。
