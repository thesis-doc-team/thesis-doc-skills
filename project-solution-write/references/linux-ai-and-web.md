# Linux / Web / AI 交互终端实施规则

## 一、先确认计算形态

树莓派/Linux 语音镜、IoT 网关与网页系统不强制 STM32。根据浏览器/音视频/AI 需求核算 CPU、内存、GPU/视频输出、声卡、网络、供电及开机自启。用户已有计算平台时保留，除非资源不足且有明确证据。

## 二、三方职责必须分明

- 前端：时钟、卡片、交互状态、媒体播放队列、TTS、WebSocket 展示；不得持有服务端密钥。
- 后端：统一入口、唤醒/会话状态、AI 意图与白名单动作、天气缓存、音乐提供方适配、服务监控与 WS 广播。
- 音频进程：音频设备、录音/VAD/ASR、心跳。不要让音频进程直接操作前端 DOM 或系统 shell。

## 三、会话、音频与消息约束

语音唤醒如有 15s 窗口，定义从**何时开始计时**、回答后怎样续期、告别语怎样 dismiss、处理中和播报中是否超时、晚到响应如何丢弃、`request_id/session_id` 幂等策略。文本旁路必须复用语音识别后的业务入口，不创建平行逻辑。

前端播放器和浏览器 `speechSynthesis` 分别管理；音乐与 TTS 之间定义音频焦点；浏览器 autoplay/中文声库必须在目标机器验证，不以 API 存在宣称有声播放成功。

## 四、外部服务与安全

高德天气、音乐 API、ASR/LLM、WS 等属于可变外部依赖；引用官方能力、验证可用返回字段，提供超时、缓存、降级和错误反馈。模型输出 action 必须白名单并验证结构；禁止模型指令直接执行 shell 或任意 URL。网络密钥仅存服务端配置，不进前端产物或日志。

音乐必须使用合法授权播放的音源；非官方接口不作为永续稳定保证。

## 五、服务治理与部署

`/api/health` 区分服务活着与外部依赖降级；天气/第三方服务失败不应整体重启。进程重启需限定次数、退避与故障记录。明确 systemd/容器中哪种为当前基线，避免无必要叠加。

实施方案必须包含部署环境、基本命令（前提清晰）、可观测日志、最小 API 测试、服务恢复与人工检查项目；未执行的命令只作为预期步骤。
