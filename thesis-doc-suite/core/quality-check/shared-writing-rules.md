# 跨文书共用写作与验收规范（规范版）

> 本文件汇总已在六个 Skill 中验证生效的共用硬规则，作为规范来源供全部现有与新增 Skill 引用。各 Skill 的 SKILL.md 中同名规则与本文同源；体裁细节（字数、栏目、缩进数值）以各 SKILL.md 为准。

## 1. 教师意见拟稿统一规范（跨文书共用写法）

意见栏一律是**供指导教师审定的拟稿**，不是教师真实评价：

- **不代签、不写签署日期、不写"优秀/良好"等等级评价**；签名与年月日保持官方空白。
- **五要素逻辑链**一段成文：
  1. **主体与选题**：`该生围绕<课题名/技术栈关键词>选题，…`
  2. **能力（或能力与阶段进展）**：`能够查阅并整理<领域1、领域2>等相关文献，对国内外研究现状有较为系统的把握；`
  3. **文书质量**：`<本文书>结构完整、条理清晰，引用文献真实可查，写作规范；`
  4. **针对性**：`能够结合选题分析<具体缺口/风险1>、<具体缺口/风险2>，…`（**必须来自本次实际写出的内容**）
  5. **收束**：`…最终评价以指导教师审定为准。`（任务书"同意下达任务书并按计划开展课题工作"；开题"建议开题并按计划开展课题工作"；综述"建议按计划进入毕业设计下一阶段工作"；中期"建议按整改意见继续推进下一阶段工作"）
- **红线**：不夸大（"世界一流、完全解决"）；不虚报（拟开展的工作不写成已验证）；不只替换项目名照搬范本句式。
- 字数门槛：任务书下达人意见 ≥50 字；开题/综述教师意见 ≥50 字（一般 120～220 字收放）；中期 ≥200 字。

## 2. 事实状态词汇（跨文书统一）

| 状态 | 允许口吻 | 禁止 |
|---|---|---|
| 已实际完成且有证据 | "已完成/已实现"；"测试通过"须有真实测试证据 | 无证据称"实测通过" |
| 资料声明/设计 | "设计文档规定/系统方案包括/设计为/计划采用" | 写成已实现 |
| 示例/默认值 | "示例/默认配置" | 当作实际运行数据 |
| 待确认/缺证据 | "待确认/待验证" | 杜撰细节填补 |

技术资料的"✅已实现"或"测试方案"不得自动升格为"已测试通过/已完成"；中期检查是**时点阶段事实**，不等于技术文档的最终项目状态。冲突事实保留双方并标注，不私自选边。

## 3. 实质性分页门禁（页数不是目标）

- 官方空白模板的页数**仅是参考**；成品页数按当次内容自然排布，**不得为凑足或压缩到某个页数而增删事实、稀释或堆砌文字**。
- 硬性 FAIL 只有两类：①为凑/压页数增删事实或破坏官方固定版式；②最后一页只剩签名/日期或整页空白（孤页）且未先通过调整可填正文措辞/段落分配消除、也未如实报告。
- 孤页修复只允许动可填正文；不缩字号、不改行距/页边距/表格框架"修图"。

## 4. 截图验证分析（Screenshot Verification Analysis，交付前硬性环节）

固定三步，缺一不可：

1. **截图**：渲染器对每页输出 PNG（必要时加 PDF 全览）；截图只存本轮 `.skill-tmp/<skill>/<run-id>/`，不进交付目录。
2. **逐张分析**（缺一张即未完成）：文本截断/溢出/重叠、表格断裂/边框错位、首行缩进与居中真伪、上标引文、长 URL 悬挂、签名/日期/附注、孤页、字体替代、乱码。
3. **留痕汇报**：执行汇报固定填写截图引擎、截图张数（=页数）、实看张数、逐张结论 PASS/WARN/FAIL 与问题清单、返工复检次数、WPS 实测边界声明。

红线：未逐张分析不得宣称排版/视觉验收通过、不得登记 `record-use`；无法截图时如实报"截图验证分析未完成"；脚本预检 OK ≠ 视觉 PASS。**量测先于定性**：判定溢出/错位/截断 FAIL 前必须有量测数据（如 scrollWidth vs 视口宽），目测截图的溢出结论不作数——窄窗口截图可能只是被裁切的伪象。**截图查重**：逐张分析前先做截图哈希查重，两张"不同状态/页"的截图字节级相同 = 拍摄失败（状态未切换/未翻页），必须重拍。**WPS 边界**：只有真正用 WPS 打开过才能写"WPS 已验证"，否则写"未在 WPS 客户端实测，需用户进一步复核"。

## 5. 成品版本与覆盖保护

- 成品 `-vN` 版本化，新版本新文件，**永不覆盖、永不删除历史版本**；任何输出路径已存在即改用下一个 N。
- **最终版本唯一（执行内缺陷修复回收）**：一次执行只交付一份最终版本；执行内发现缺陷时，修复重建的修正版改名为本轮应交付的版本名，删除最初有缺陷的一份（先删后改名，同号配套文件一起换）。缺陷稿不是历史版本，回收不违反上条"永不覆盖、永不删除"；尽量在运行区构建+校验通过再落交付目录，失败稿不进交付区、不占版本号。
- 结构保真（OOXML 前后对照）、事实真实、格式检查（DOCX 可打开 ≠ 成功）三者都过才算生成质量达标；**最终验收属于用户**，Agent 只负责执行、自检与如实汇报。

## 6. 通用检查顺序

结构检验（脚本）→ 事实与文体检验 → 截图验证分析 → 资产登记（record-use）→ 清理（cleanup）→ 执行汇报。任何硬门禁失败不得掩盖；WARN/FAIL 必须在执行汇报列明。

## 7. 分批写入与一次终检（写入阶段硬规则）

**任何长内容（MD 正文、HTML 内容、DOCX 各栏正文、逐次记录）禁止一次性整篇生成。**

- **分节分批写入**：先写骨架（章/栏目/条目标题与要点提纲）并落盘，再逐节成文——每节用独立的写入动作落盘，一节定稿后再写下一节；单节内容多时再分 2～3 批追加写入。
- **落盘后再续写**：一批内容没有写入文件之前，不开始下一批；不把多节合并成一次超长写入。
- **定点修订，不推倒重写**：中途发现已定稿内容有误，只定点修订该处并在执行汇报留痕；不因后文调整回炉重写全文。
- **一次终检**：全部内容落盘后做**一次且仅一次**端到端终检（结构、事实、格式、字数/分页门禁）；终检问题定点修正后即交付，写作过程中不反复全文重查。
- 执行汇报注明分几节/几批写入与一次终检的结论。

各 Skill 的具体写入单位（章/七项/主章/指导次数/正文栏目）以其 SKILL.md 同名规则为准。
