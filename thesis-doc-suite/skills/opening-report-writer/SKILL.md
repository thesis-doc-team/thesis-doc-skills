# opening-report-writer｜毕业论文（设计）开题报告生成 Skill

## 0. 绝对边界（首次执行优先阅读）

**唯一正式文书**：塔里木大学《毕业论文（设计）开题报告》的**官方空白 DOCX 原样副本填充件**。上游 `project-technical-doc` 提供的技术 Markdown 是事实输入，不是本 Skill 需要重新生成的成品。本 Skill 不修改源码、不写技术手册、任务书、中期检查表、毕业论文、答辩 PPT 或 HTML。

**规则裁决顺序**：用户本轮明确要求及其当前正式学校规定 ＞ **当前锁定的官方空白模板的固定格式与栏目** ＞ 当次真实技术文档、测试证据和同项目共享事实 ＞ 已核验且适用于本课题的真实论文/规范 ＞ 内置脱敏范本的写法 ＞ 常识推断。**内容真实性不通过“多数范本都这样写”投票决定。** 新学校模板与当前锁文件不符时停用旧坐标，先审计和授权适配；禁止强行写入或偷偷更换模板。

**禁止**：
- 用已填参考范本当正式模板；重新画 Word 表格；修改官方空白模板原件，或擅自更改成品中固定封面栏目、说明文字、表格结构、页边距、页码、教师审阅意见**标签**/签名/日期（意见栏只填**拟稿正文**，且不代签、不写签署日期、不冒充教师已审定）。
- 将旧范本的人名、题目、模型、指标、论文、日期、周计划或实施结果带入新课题；仅借鉴文体组织与适当的标题层次。
- 让 CSDN 冒充正式论文；只凭搜索摘要编造文献；把设计目标、尚未执行的测试方案写成“实测通过”。
- 未经核查就称 Word 视觉验收通过；为了压缩页数改字号/行距/页边距，或删除必要事实凑篇幅。
- 在 `deliverables/` 留下过程 JSON、渲染 PNG/PDF、日志、临时下载文件；删除其他 Skill 的项目资料、共享资产或历史版本。

## 1. 一个项目 = 一个资产包（数据 + 成品 + 运行区）

```text
<PROJECT_ROOT>/
├── project-assets/                       # 跨 Taskbook / Opening / Midterm / Tech 文书共享的数据
│   ├── project.json                       # schema_version=1；稳定 project_id 和用户确认身份
│   ├── facts.json                         # FACT-xxx：来源、状态、证据
│   ├── references.json                    # REF-xxx：正式来源、链接、核验信息
│   ├── schedule.json                      # 唯一周计划：draft / confirmed
│   ├── progress.json                      # 其他 Skill 的可选中期进度；本 Skill 不要求存在
│   └── activity.jsonl                     # 变更、引用、最终成品登记记录
├── deliverables/
│   ├── technical-document/               # 上游自行维护
│   ├── taskbook/                          # 任务书 Skill 自行维护
│   ├── opening-report/                    # 本 Skill 正式交付（每组 -vN 三文件）
│   └── midterm/                           # 中期检查 Skill 自行维护
└── .skill-tmp/
    └── opening-report-writer/
        └── <run-id>/                      # 本轮所有中间物，带所有权标记；完成后删除
```

**资产工作顺序**：
1. `project_assets.py status --root <PROJECT_ROOT>`，确认 project_id 匹配，旧库先读后写；不存在时才 `init`。**不在 Skill 安装目录初始化项目包。**
2. 读取同项目 FACT、REF、唯一 schedule（及存在的 progress）；本次新提取且能溯源的 FACT/REF 才执行 `merge`；同一 REF-ID 不重复插入，已有条目改动必须 `--replace --reason` 留审计。`schedule.status=draft` 不能冒称已确认；计划并不等于实际进度。
3. 论文数据库中的“记录存在”不等于“正文论点获证实”；每次实际引用仍必须核对摘要/内容支持范围。正文 `[1]` 仅为本次排版号，不代表长期 REF-ID。
4. `workdir --root` 建本轮运行区，正文 JSON/检查报告/检索记录和渲染图都在其中。成品为 `<课题简称>-毕业设计开题报告-vN.docx`，跨次重生成递增 N、**绝不覆盖删除合格历史版本**；执行内缺陷修复的改名回收见第 5 节"最终版本唯一"。
5. 结构与逐页验收通过后对该版本 `record-use --doc-type opening-report` 登记实际使用的 REF-ID、成品 SHA256；写执行汇报与文献台账。之后 `cleanup --run-id` 只清本轮有所有权标记的运行区。成功失败均应尝试安全清理，不能扩大清理范围。

详见 `references/shared-project-assets-contract.md`、`references/intermediate-cleanup-policy.md`、`references/integration-contract.md`。**不能跨调用中期检查 Skill 的 `compose` 或填充脚本**；只共享资产，不共享文书生成坐标。

## 2. 官方空白模板硬约束（不得更改）

官方原件：`assets/official-opening-report-template.docx`。其原始 SHA256 固定在 `assets/template.sha256`，结构审计在 `assets/template-lock.json` 与 `references/official-template-invariants.md`。**用户再次提供的空白官方模板与当前内置原件哈希一致**。不得把 `assets/reference-samples/` 的范本替换进 `--template`。

| 固定区域 | 允许填写 | 保持不变 |
|---|---|---|
| 封面 | 本项目经确认的题目、姓名/学号/学院/专业/班级/导师/职称/时间（缺失留白） | 校名、栏目标签、线条、版面及官方署名 |
| 填表说明 | 不可填 | 全文、七项要求、≥3000字和≥10篇说明 |
| 正文两行表格第1行 | “开题报告正文”提示后的原留白书写区域；允许清除同区未使用的空占位段落 | 表格行列、边框、正文说明、学生签字及日期 |
| 正文两行表格第2行 | **填写指导教师审阅意见拟稿**（≥50字，见"教师意见拟稿统一规范"） | 指导教师审阅意见标签、导师签名、年月日，均留给本人 |

**新增文字显式样式**：正文 10.5pt（五号）中文宋体、西文 Times New Roman、1.5 倍行距、段前段后 0；普通正文（含周计划）首行缩进 **420 twips≈21pt/约2汉字**；标题保持独立且避免孤立于页尾；参考文献 1.5 倍行距，**显式左对齐 + 420 twips 悬挂缩进**，绝不让两端对齐拉伸长 URL，文末 `[n]` 只出现一次。引文必须是真正的 `w:vertAlign=superscript`，不是普通基线字符。

生成工具只能修改成品 `word/document.xml` 中允许的写入节点，官方模板原件及成品的其余 ZIP 部件不应变更。任何 SHA/固定锚点差异立即 FAIL。**页数不是目标**；自然分页，不因页数压缩事实。最后一页若只有签字或日期、整页空白则视为分页失败，优先调正文冗余、分段/措辞，不动官方固定框架；实在无法修复要如实报告。

详见 `references/template-boundary-and-layout.md`。

## 3. 范本逆向：已填匿名参考 + 求同存异 + 防串用

1. **先看官方** `assets/template-lock.json`（只对固定结构负责），再看 `assets/reference-samples/README.md` 与 `samples-manifest.json`。当前打包的完整脱敏已填范本只有 **SAMPLE-A** 一份，位于 `assets/reference-samples/sample-a-smart-interaction-anonymized.docx`，配有 SHA256；其他此前已读范本的共性与差异记录于 `references/genre-reverse-engineering.md`，**不把未脱敏原稿放进压缩包**。
2. 内容编写前必读 `references/anonymized-sample-usage.md`、`references/genre-reverse-engineering.md`；有必要再只读 SAMPLE-A DOCX，学习段落展开、任务分项、现状评述、字数比例和章节过渡。`references/sample-style-audit.json` 是对示例**显式格式属性**的实测，**不能反向修改官方模板**。
3. 可复用的是**背景→动机→目标→文献现状→研究任务→关键问题/办法→资源条件→技术路线/进度→文献**的论证逻辑。不能借用示例的课题、人物、完成状态、图表、指标、链接、引文或具体周次。
4. 原样格式以官方空白模板为最高依据；常见标题与行文相近时采用稳定预设；范本差异若官方没有规定，可参考出现比例及合理写法，但**任何会改变真实技术判断的差异应回到项目资料核实**，不能猜。
5. 每次维护匿名范本运行 `python scripts/check_reference_example.py`；更新样本需重新脱敏、更新 SHA/manifest 和回归测试。**匿名示例不可写入 `facts.json`、`references.json`、`schedule.json`。**

详见 `references/genre-reverse-engineering.md`、`references/anonymized-sample-usage.md`。

## 4. 内容标准与文献规则（只写开题报告）

学校填表说明明确七项内容，**没有强制规定七个正文章题的逐字名称**。为稳定复现，默认统一章题如下：

1. `1 课题研究立项依据`：`1.1 课题背景`、`1.2 研究目的和意义`（不回退旧范本的“课题来源”）。
2. `2 国内外研究现状及分析`：按国内外研究成果/路线组织，逐项分析与本项目关联，不做文献标题堆砌。
3. `3 课题任务要求及实现预期目标的可行性分析`：任务、预期目标与技术/资源/实施可行性。
4. `4 重点研究的问题及解决思路`：每个关键问题交代原因、具体方案、拟验证办法，可分点，**不写中期问题整改**。
5. `5 完成课题所需工作条件及解决办法`：已有开发环境、必要资源、缺口与获取/替代方案。
6. `6 工作方案及进度计划`：技术路线、阶段成果、验证节点；周区间统一 `第X周--第Y周：任务`（单周 `第X周：`）。按共享 schedule 周次/顺序编写，未知时标为暂定。
7. `7 主要参考文献`：至少10篇真实可核验来源，正文与文末一一对应；**其中中文文献占比 ≥60%（硬性，判定与检索口径见下）**。

以上**七个一级标题是本 Skill 默认预设，而非伪称学校逐字规定**。当用户提供更高优先级的正式字面标题规范时，需显式授权 `allow_custom_heading_titles=true` 并重检。一般情况下二级标题在项目适用范围内可以适当增减，但官方七项不能缺。**正文汉字 ≥3000（排除文献和封面）**；不以重复套话凑字数。

**先查资产文献，缺口才补搜**。优先 CNKI 中国知网、万方、维普、学位论文库、IEEE、ACM、期刊/出版商官网、Crossref/DOI、官方标准/RFC；CSDN 可作工程操作或排障的辅助网络来源，标明真实类型，默认不超过2项、不得冒充正式学术论文。每项核对作者、题名、载体、年份、DOI 或可访问 URL 及适用论点，不捏造卷期页码或实测。缺少10篇真实核实资料则不能以正式合格文书报 PASS。`references.json` 的 `REF-xxx` 是稳定库 ID，正文号码按**本次首次引用顺序**排列。输入正文以 `[[cite:1]]` / `[[cite:1-3]]` 等标记，生成器输出 Word 真上标；文献 `text` 字段不得自带 `[n]`。

**中文文献占比 ≥60%（硬性）**：本次文献表里中文文献（以**正式发表的正文主要语言**判定：中文期刊论文、国内学位论文、中文专著/标准；中文译本按原著语种计）占比不低于 60%（10 篇至少 6 篇、15 篇至少 9 篇）。检索期就按**约 65% 收**（留余量：终检剔除未核验/重复条目后重新点数仍不得跌破 60%）：中文库（知网/万方/维普/国内学位论文库）先检索成池，再以外文补前沿与国外对照；执行汇报写"中文 X / 总 Y = Z%"。中文池确实稀缺时（检索留痕：库/检索词/命中量）**不为凑比例伪造中文文献、也不静默降比例**，如实向用户报告并请其决定（接受低比例/扩检索词/换来源）。

技术事实先做状态矩阵：`VERIFIED / DECLARED / DESIGN / PLANNED / UNKNOWN`。开题是拟开展课题的论证，不是把一份项目技术文档伪写成已做完、已测试。技术文档说“有测试方案”≠“通过测试”。详见 `references/technical-input-and-writing.md`、`references/literature-policy.md`、`references/content-writing-guide.md`。

### 教师意见拟稿统一规范（跨文书共用写法）

教师意见栏一律是**供指导教师审定的拟稿**，不是教师真实评价；签名与年月日保持官方空白，不代签、不填签署日期、不写“优秀/良好”等等级评价。

**五要素逻辑链**（一段成文，本栏≥50字，一般120～220字收放）：

1. **主体与选题**：`该生围绕<课题名/技术栈关键词>选题，…`
2. **能力**：`能够查阅并整理<领域1、领域2>等相关文献，对国内外研究现状有较为系统的把握；`
3. **文书质量**：`开题报告结构完整、条理清晰，引用文献真实可查，写作规范；`
4. **针对性**：`能够结合选题分析<具体缺口1>、<具体缺口2>，进而阐明本课题的技术路线与待验证事项；`（缺口/路线必须来自本次实际写出的内容）
5. **收束**：`建议开题并按计划开展课题工作。`（**不加"最终评价以指导教师审定为准。"等元话语尾巴——画蛇添足**，判别法：这句删掉后意见无信息损失、更完整，就是多余句，删）

**红线**：不夸大（“世界一流、完全解决”）；不虚报（拟开展的工作不写成已验证）；不只替换项目名照搬范本句式——评价必须指向本次文书实际写了什么；不写教师签名、签署日期或等级。范本反向规则与正例对照见 `references/genre-reverse-engineering.md`。不写"（本栏为拟稿）""…审定为准"等元话语（fill/validate 对 `本栏为拟稿`/`供教师审定拟稿`/`供指导教师审定`/`教师审定为准` 报错，“审定结果为准”等插字变体同拦——**禁语以意图为准：正确处置是删尾巴收于实质句，不得插字绕过**）。

## 5. 标准执行顺序（完整任务一次走完）

**分项起草、分批写入（硬性，禁止一次性整篇生成）**：七项内容逐项起草并写入本轮 `报告内容.json`——立项依据 → 研究现状 → 任务与可行性 → 重点问题 → 工作条件 → 进度计划 → 参考文献，一项成文落盘后再写下一项；教师意见拟稿单独作为最后一批。**禁止一次性生成全部七项**。全部落盘后 `build_report.py` 一次性填充，第 7 步双重验收即**唯一终检**，写作中途不反复全文重检；终检问题定点修订后交付。执行汇报注明分几项/几批写入与一次终检结论。

**并引写法与校验器预检（防"验收器口味"在最后一步才暴露）**：

- **并列多文献引用优先合并或分隔，不禁止连排**：推荐 `[[cite:6,12,15]]` / `[[cite:6-7]]`（渲染为上标 `[6,12,15]` / `[6-7]`），或标记间插顿号 `[[cite:6]]、[[cite:12]]`；`[[cite:6]][[cite:12]]` 连排同样渲染为合法上标，不禁止但排版上不推荐。校验只拦**相邻同号** `[n][n]` 的重复编号，异号并排不判错；成稿后自查一遍同号连排再交付。
- **动笔前先摸校验器**：分项起草前先过一遍 `check_report.py` 的断言清单，或先用"≥10 条真实核验条目＋极简正文（build 前置校验要求 ≥10 条；少于 10 条被 build 拒绝属预期）"的最小样例跑一次 `build_report.py` → `check_report.py` 冒烟，确认引用渲染与校验行为后再写长文。校验器本身过宽/过严时按硬约束遵守并在执行汇报注明，不为绕过校验而歪曲内容。

**最终版本唯一（每次执行只交付一份最终版本）**：

- 无论中途修复几轮，本次执行结束时 `deliverables/opening-report/` 只保留一份最终成品（同号三件套：DOCX + `执行汇报-vN.md` + `文献核验台账-vN.md`）；过程稿、缺陷稿不与最终版并存。
- **缺陷修复改名回收**：合格成品交付后才发现问题时，修复重建得到新号文件（如 v2），随即将其**改名为本轮应交付的版本号**（如 v1，先删缺陷稿再改名，同号三件套一起删旧换新）；执行汇报注明修复轮次与回收操作。"永不覆盖、永不删除"保护的是合格成品版本史，执行内缺陷稿不是历史版本；若缺陷稿曾 `record-use` 登记，回收后以最终定名文件 `--replace --reason` 补登记。
- 跨次执行不受影响：因内容变更或用户要求重新生成时，仍递增产出 `-v2`、`-v3`…并各自登记。

1. **确认输入和身份**：本次真实技术 MD/DOCX/PDF、当前官方空白模板、项目根及 project_id；个人信息未知留白，不从匿名范本猜。阅读并复用既有 `project-assets`；同 ID 才能操作。
2. **锁官方模板并逆向范本**：运行 `python scripts/inspect_template.py`、`python scripts/check_reference_example.py`；读官方锁文件与样本清单、范本逆向规则；项目类型不符时只学抽象写法。
3. **提取事实/来源与区分状态**：本轮在自己的工作区建立“项目事实→技术文档具体章节/证据→可写口吻”的矩阵。识别设计、声明、实测、计划；与共享事实冲突时留痕，不静默覆盖。
4. **核验文献并映射论点**：先复用 `references.json` 核实且适用的 REF，必要时补充正式检索。按实际正文首次引用顺序编号；生成本轮持久化文献核验台账，未核验条目不能冒充已核实。
5. **撰写七章草稿与教师意见拟稿**：至少3000汉字，研究现状来源对应、预期目标可验收、问题与解决思路成对、条件与周计划一致；按"教师意见拟稿统一规范"写 `teacher_opinion`（≥50字）；使用 `references/report-json-contract.md`、`templates/input.schema.json` 构造本轮 `报告内容.json`，存 `.skill-tmp/opening-report-writer/<run-id>/`，不是公共事实仓库。
6. **原版填充（两段式出片：先运行区、后交付区）**：`python scripts/build_report.py <本轮报告内容.json> --output <本轮运行区>/<课题简称>-毕业设计开题报告.docx`——先构建到 `.skill-tmp/opening-report-writer/<run-id>/`，**不直接写交付目录、不带 -vN**；定稿版本号在第 8 步交付时才确定，失败稿不进交付目录、不占版本号。
7. **双重验收（对运行区构建件）**：先运行 `python scripts/check_report.py <运行区构建件.docx> --json <本轮报告内容.json> --output-report <本轮结构校验.json>`，再运行 `python scripts/render_visual.py --file <运行区构建件.docx> --outdir <本轮render/>`。后者转换链依次探测 soffice（LibreOffice）→ Word COM → WPS COM，亦可 `--pdf` 直通本机已转换的 PDF；PNG/预检需 PyMuPDF，生成所有页 PNG/PDF 和孤页＋**任意页空白页**预检（空白页＝整页无正文，仅页码/页眉/页脚亦算；命中进 `problems` 硬阻断并退出码 2——成品不得出现空白页，先对照官方空白原件定性再修复）；**Agent 必须逐张真正打开并记录每页 PASS/WARN/FAIL**。预检 OK≠视觉 PASS。未能渲染时必须说未完成视觉验收，不能报完全通过。校验 FAIL 时定点修订 JSON 后在运行区重建复验，不产生版本号。
8. **记录与交付（验收通过才落交付区）**：把运行区通过验收的构建件复制为 `deliverables/opening-report/<课题简称>-毕业设计开题报告-vN.docx`（N=交付目录已有最大版本号+1；预检目录，禁止覆盖历史文件），并写 `执行汇报-vN.md`、`文献核验台账-vN.md` 放入同目录，**本轮恰好三项**；历史版本保留。仅合格成品使用 `project_assets.py record-use` 登记实际引用的 REF-ID。过程 JSON、截图、PDF 和日志不进入成品区。交付后才发现缺陷时按上文"最终版本唯一"改名回收。
9. **清理运行区**：`project_assets.py cleanup --root <PROJECT_ROOT> --run-id <run-id>` 仅删本轮拥有的临时目录；无论成功/失败都做安全清理并如实报告。最终验收只由用户判断，不由 Agent 代替确认。

**截图验证分析（三步硬门禁）**：截图（逐页渲染）→ 对所有图片检查封面、正文字距/缩进、上标、分点、长 URL/文献悬挂、页末章题、签字孤页、字体缺失 → 按 `templates/execution-report.md` 记录每页图号、检查结论、返工轮数。不能因为生成脚本无报错就跳过视觉检查。最终成品只有三项，不交付截图/检索缓存。

## 6. 交付门禁与失败处理

- **G1 事实真实性**：本项目技术资料与稳定 FACT 引证一致，不从范本套技术型号，不混淆已实现/拟实现/拟测。
- **G2 官方模板**：官方原件 SHA、封面固定栏目、2行1列表格、正文说明、签字栏与审阅意见标签/签名/日期、非文档 XML 部件均保护；审阅意见书写区只含 ≥50 字拟稿。原件和成品的可填写区域边界清楚。
- **G3 正文字体和结构**：七章、≥3000汉字；每个正文段落宋体/Times New Roman五号、1.5倍，**首行缩进420 twips**，标题独立；周次使用 `--`，引用是真上标。
- **G4 文献**：≥10条真实文献，正文编号存在且对应；基线单次编号、1.5倍行距、左对齐、悬挂420 twips，**不启用 Word 自动重复编号**。如文献真实性无法核实，不得为了过程序检查把 `verified` 强行标 true。
- **G5 视觉分页**：结构检查与逐页截图分析均完成，无孤立签字/空白页、文本溢出或长 URL 异常拉伸。页数自然产生，不为达到预设页数而作弊。
- **G6 生命周期**：共享资产与项目 ID 无串用，历史 `-vN` 全保留，文献与周计划先复用，成品登记并清理本轮临时目录；输出目录只有每版正式三项。

`PASS` 需要机器结构检查、实际文献核验、逐页截图评审都完成。`WARN` 是可用草稿但有待确认信息、未实测 WPS 或部分限制；`FAIL` 是官方固定结构改变、引用伪造、重要格式错误、必需内容缺失或孤页等。**WARN/FAIL 必须在执行汇报列明，不得写成已通过。** 详见 `references/quality-gates.md`。
