# 已填写范本的逆向规则（匿名参考，不是官方模板）

> **角色说明：** `assets/official-opening-report-template.docx` 是用户授权的**唯一官方空白格式框架**，任何情况下不能被参考范本替代。`assets/reference-samples/sample-a-smart-interaction-anonymized.docx` 源于用户最早提供的**已填写样本**，经过姓名、学号、导师、时间和项目标题脱敏，用作文章组织、行文详略及层次模式的示范。示例稿中的项目技术、统计数字、进度周次、引文和书目不得作为本次项目的证据或直接复用。

## 1. 谁决定什么：不可颠倒的层级

1. **官方模板原件**：封面、学校说明、字样、页面、节、表格、签字区域、行距要求，绝对优先。
2. **当前项目技术文档 + 经确认的 project-assets 事实/周计划**：决定新文书写什么；共享资产只有证据确凿且相关才复用。
3. **经过本轮核验的论文/标准/官方网站**：决定研究现状和参考文献能引用什么。
4. **匿名已填写范本**：仅帮助决定「怎样铺陈、怎样组织段落、怎样设置论证层级」，为弱约束、可被上级覆盖。

发生冲突时：**绝不让示例修改官方模板或提供新项目事实**。例如示例 `1.1 课题来源` 与本 Skill 默认 `1.1 课题背景` 不一致，继续用默认标题；示例周次 `第1周-第2周` 不合规范，新文档仍用 `第1周--第2周`；示例声称“系统已验证”而技术文档无实测时，必须写成拟验证。

## 2. 逆向提取的结构与论证套路

| 位置 | 范本显示的组织规律 | 迁移到新项目的表达规则（不要复制范本内容） |
|---|---|---|
| 第一部分：来源/背景 | 从领域大趋势 → 真实场景痛点 → 现有方法局限 → 本课题定位 | 用「背景—问题—课题选择」3～4段，研究对象、平台和条件来自本项目文档 |
| 目的和意义 | “具体要做什么”与“工程价值/应用意义”分开 | 目的写可观察结果，意义写可预期价值；不要在开题报告里假装工作已经完成 |
| 国内外研究现状 | 国内/国外分别组织，先归纳技术方向，再谈典型成果、限制与空缺 | 每个实质论断以当次真实文献核查为依据，至少做跨文献综合而非堆作者/市场数值 |
| 任务与可行性 | 任务逐项列明，随后按软件、硬件、技术条件分析 | 先任务—接口/数据流—可测结果，再分析环境条件、第三方依赖、风险及验证措施 |
| 关键问题及解决思路 | 先识别难点，再针对难点逐项匹配解决路线 | 每项用「具体问题 → 原因/约束 → 拟采取方法 → 可验证证据」四环，严禁泛泛宣传语 |
| 工作条件 | 拆分硬件条件、软件条件与解决方法 | 严格区分已具备/需采购/可替代/待确认；没有条件不许写“已具备” |
| 工作方案与计划 | 以周次列表形成连续的实施路线 | 先给实施步骤，再给周计划；周次必须以共享 schedule.json 基线为准，范本时间表不可迁移 |
| 文献 | 按正文引用、文末对应 | 只参考「编号—书目信息」格式；真实出处一律当次核验或按已核验共享 REF-xxx 复用 |

### 2.1 可复用的段落骨架

- **背景引入段**：`相关技术/领域发展趋势（有来源）→ 目标用户/场景变化 → 原有方案不适配之处`。
- **课题落点段**：`基于上述需求，本课题拟面向【对象】，采用【经技术文档确认的技术】构建【目标系统】，重点解决【关键问题】`。
- **目的段**：`拟实现【可验收功能】，验证【可观察的技术机制或指标】；研究成果服务于【明确应用场景】`。
- **现状综合段**：`某类研究侧重【X】（引文）；另一类强调【Y】（引文）；但对【本课题真实范围内的约束】论证仍不足，因此拟采用【当前技术路线】`。
- **任务项**：`（1）任务名称：输入/资源 → 核心流程 → 输出与验收方式`。
- **难点项**：`关键问题：……；拟采取方案：……；验证方法：……`。
- **工作条件项**：`开发/测试条件 → 已有证据 → 缺口 → 获取或替代办法`。
- **周计划项**：`第X周--第Y周：具体任务（阶段产出或检查节点）`。

上述括号中的提示在生成正文时改为自然语言，不把这些写作标签当成报告实文。

## 3. 写作质量控制：只学优点，不传递范本的缺陷

**可以学习：** 以课题问题为中心层层展开；同一节分段、局部列点；任务—关键问题—可行性—进度相互对应；研究现状、文献、论点相互支撑；对现有技术做适用性分析。

**必须纠正的示例问题：**

- 示例章题 `1.1 课题来源`、`1.3 研究意义` 等具体分节不是官方模板强制格式；当前统一预设优先用 `1.1 课题背景`、`1.2 研究目的和意义`，不从示例照抄标题。
- 示例周次连接为单连字符，有较多周次；不以其周次作为新项目计划，生成新报告一律 `--` 并服从共享资产计划。
- 示例中的市场预测、夸大式行业数据、技术性能数字，除非重新找到权威数据来源，否则不得写入新报告。
- 示例某些文字采用“已经实现、成功验证”完成式语气；如果本次技术文档没有测试证据，必须改为计划式或基于已有证据的审慎表达。
- 示例参考文献不等于已核验资料，不能复制作者、题名或编号来凑数。先检索、逐条核验、再排正文首次出现编号。
- 示例文本中的硬件型号、品牌和交互功能是旧课题内容，即使脱敏后仍**绝非当前课题事实**。
- 示例的 Word 页面/表格/页边距、字体和段落样式都不能移植到官方模板。仅在生成副本的官方书写区按照学校说明写入正文。

## 4. 生成器应如何消费这个范本

1. **先**看官方空白模板及其哈希，检查官方七项要求；不用示例做版式基线。
2. **再**读本次技术文档及共享资产，整理事实矩阵、功能边界、阶段计划和文献核验表。
3. 从本文件读取七部分「论证角色」，需要更深模仿文风时才打开脱敏 DOCX 示例，观察各章如何起、承、转、合。
4. 对新项目写**独立的完整提纲和初稿**；不能照搬示例中的成段文字或技术论点，不可复制其引用。
5. 检查文体：课题背景、研究现状、任务、可行性、难点、条件、周计划、参考文献之间要能够互相追踪。
6. 只用 `scripts/build_report.py` 写入官方模板的授权空白区，再运行 `check_report.py` 和逐页渲染目视核验。
7. 发现示例与官方/用户当前资料不同，采用更高优先级资料；若仍无法判定且会影响实际结论，询问用户；不以示例项目填充缺失事实。

## 5. 匿名化约束与版本维护

- `assets/reference-samples/sample-a-smart-interaction-anonymized.docx` **只供阅读**，不用于构建 `output.docx`、不进项目共享事实库，不触发 `record-use`。
- `scripts/sanitize_reference_sample.py` 仅供维护时从用户授权的已填写 DOCX 构造脱敏副本。**原文件不得被捆绑入 Skill**；不许把个人姓名、学号、导师、联系电话、邮件、个人日期、文档作者元数据留在输出范本。
- 新增 `scripts/check_reference_example.py` 对内置范本执行脱敏检查；发现敏感字段立即 FAIL，不允许打包。
- 如未来替换示例，要先取得用户授权，重做逆向内容提取、脱敏检查与测试，不覆盖学校官方模板。
