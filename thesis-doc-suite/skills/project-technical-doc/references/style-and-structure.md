# 技术文档范本的写作规范

## 定位与边界

内置范本：`references/技术文档范本.md`。它是**与具体项目无关的写作和章节参考**，规定技术文档应如何组织、用什么形式解释技术事实；**绝不是项目功能、型号、参数或测试结果的证据来源**。每次生成时，只把本次用户指定的项目资料作为事实输入。

默认写作主线：**场景与目标 → 功能 → 架构 → 平台与资源 → 核心技术 → 模块 → 关键流程 → 数据 → 测试 → 速查**。典型为 10 个编号主章；可根据项目类型与已知事实调整标题、数量与篇幅，不机械套写，但不得突破排除问题/改进类章节的正文边界。

## 每章的编写重点

| 章 | 必须回答的问题 | 首要项目证据 | 建议呈现方式 |
|---|---|---|---|
| 1 项目概述 | 为谁解决什么问题？当前系统范围是什么？ | README、需求、设计总述 | 场景说明、定位、规格表 |
| 2 功能说明 | 哪些功能？谁触发？输入、输出和结果是什么？ | 需求、交互、代码 | 功能树、功能行为表、实现映射 |
| 3 系统总体架构 | 组件怎样连接？数据/控制怎样流转？ | 架构设计、调用链 | 分层说明、数据流图 |
| 4 平台与资源 | 采用什么技术栈或硬件？资源如何分配？ | 构建配置、原理图、BOM | 选型表、接口/资源映射 |
| 5 核心技术 | 系统如何完成关键任务？主要机制和异常是什么？ | 算法、协议、驱动、服务 | 机制解释、参数表、协议示例 |
| 6 模块详解 | 每个模块做什么、依赖谁、怎么处理与失败？ | 模块代码、API、设计 | 职责/输入/处理/输出/异常 |
| 7 关键流程 | 初始化、主业务、异常分支如何运行？ | 状态机、调用关系 | Mermaid 流程图与步骤 |
| 8 数据与存储 | 重要字段、结构、约束、持久化是怎样的？ | Schema、结构体、迁移 | 数据字典、关系/契约说明 |
| 9 系统测试方案 | 怎样验证？预期和实际测试证据各是什么？ | 测试文件、报告 | 编号用例，预期/实测分列 |
| 10 附录 | 有哪些适合速查的协议/参数/术语？ | 项目已提供的规范 | 配置表、字段表、参考资料 |

## 文本与图表规则

**禁止新增正文内容**：已知问题与改进建议、存在的问题、优化方向、风险对策、后续规划、技术展望等评审/规划性质的独立章、节、结语。实际已实现的异常分支、运行约束可在相关技术与模块章节内如实解释。

- **先作用，后机制**：一段关键技术说明优先覆盖“用途/输入 → 处理方法 → 输出/消费者 → 异常与约束”。
- **避免重复**：功能章讲对外行为，核心技术章讲实现机制，模块章讲依赖，流程章讲顺序与分支。
- **具名而有据**：具体芯片、平台、协议、字段、表名、算法、频率、单位、阈值都由用户的项目资料决定；无法核实就标记“待确认”。
- **图表服从证据**：只有在能说明真实架构/关系时才绘制架构图、功能树或 Mermaid；不能凭空画出并不存在的组件和分支。
- **示例标识**：JSON、配置、命令、数据记录等需区分“真实值 / 项目资料示例 / 为解释而造的示意”，最后一种不得假冒事实。
- **技术深度优先于篇幅**：有充分证据时展开机制和错误路径；没有证据时以清楚、准确的有限内容代替模板填充。

## 常见真实性与一致性问题

- 示例数据与告警/状态字段逻辑不符；参数阈值方向与范围冲突。
- 同一字段在接口、数据结构、数据库、附录里使用不同名称或不同单位。
- 同一功能在不同章节出现互相矛盾的已实现/仅设计状态。
- 只有测试用例、目标指标或预期结论，却写成实测成功。
- 模板中出现某硬件/数据库/通讯模块，但当前项目并未使用，仍被机械沿用。

遇到冲突：记录来源、在文档中恰当表述不确定性，并在执行汇报列出待确认项；不能通过猜测偷偷“修正”。

## 写作深度示意（不是新项目事实）

**不合格**：“该模块负责传输数据，稳定可靠。”

**合格**：“根据当前项目的接口定义，该模块从【实际来源】读取【实际消息】，通过【实际传输方式】发送至【实际消费者】。对超时和失败的处理以源码与协议说明为准；无资料支持时明确标记对应机制待确认。”
