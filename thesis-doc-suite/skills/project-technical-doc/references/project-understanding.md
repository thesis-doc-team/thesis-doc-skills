# 项目理解工作手册（资料/源码 → 技术事实）

## 一、通用理解框架

必须建立八个视图：

1. **范围**：项目目标、对象、部署环境、外部依赖与系统边界。
2. **功能**：按场景罗列用户/系统操作及其触发、执行和结果。
3. **结构**：子系统、模块、依赖、资源以及交互关系。
4. **运行**：入口、初始化、调度模式、状态管理与关键业务时序。
5. **数据**：来源、格式/结构、换算/处理、持久化与传输。
6. **实现**：代码位置、调用关系、配置项、未完成实现和防错措施。
7. **测试**：计划、用例、实际执行记录、未覆盖范围。
8. **边界核对（内部）**：记录运行依赖、已知缺口及未实现计划，仅帮助判断系统当前能力与证据；不把缺陷清单、升级路线、改进建议写入最终技术文档。

## 二、根据项目类型分析

### 嵌入式 / IoT / 硬件
- 芯片完整型号和封装（资料存在时）、主频、内存及供电约束。
- 传感器/执行器/人机交互单元、物理接口、引脚资源、时钟/中断/DMA 分配。
- 固件入口、循环/任务调度、驱动层、应用层、中断和缓冲数据流。
- 协议帧/CRC/指令与应答、上下行和错误处理、云平台/串口链路。
- 部署条件：电源、通信网络、传感器标定、硬件版本。
- 代码中的 HAL/FreeRTOS 等必须以实际包含的工程和调用路径为据；不能因芯片型号而推断调度框架。

### Web / 后端 / 全栈平台
- 前后端代码入口、框架版本依据、路由/API 层、业务服务、持久层、鉴权与权限边界。
- 数据库迁移、表关系、异步任务与缓存、外部服务、环境和部署配置。
- 核心用户旅程：请求 → 验证 → 处理 → 状态变更/存储 → 响应/事件。
- 区分前端页面“存在”与接口“已接通”，接口“定义”与服务“可用”，迁移“存在”与云数据库“已部署”。

### 算法 / AI / 数据处理
- 输入信号/样本、预处理、模型/算法、主要参数、推理/训练链路、结果格式。
- 数据流与批处理/实时处理的路径，依赖库、硬件环境、异常与性能瓶颈。
- 评价方式、基线、测试数据集、量化指标的真实记录；不可伪造准确率/帧率。
- 如果模型推理依赖第三方 API，分清本地业务和外部模型服务的职责。

### 桌面 / 原生 UI / 单机工程
- GUI 框架、窗口/事件循环、交互状态、后台任务、设备通信与展示。
- UI 线程和数据接收/处理线程间的调用边界、刷新机制、异常恢复、配置持久化。
- 区分 UI 原型与真实驱动接入。

## 三、代码探索顺序

1. 仓库根目录、README、构建/依赖配置文件（CMakeLists.txt、Makefile、*.ioc、package.json、pyproject.toml 等按实际情况）。
2. 真正的入口（`main`、启动脚本、服务路由注册、GUI 主程序等）。
3. 每个核心业务流程的上游输入、中间处理、下游输出。
4. 与流程有关的数据结构、配置、接口和边界。
5. 对应测试、日志记录、未实现标识。
6. 补充了解非核心模块，完成系统版图。

大型项目优先确定功能覆盖，再按关键链路深度分析；执行汇报列出未审到的范围，不要声称“已完整理解全部代码”。禁止读取密钥或扩大到未经授权的项目。

## 四、功能实施状态用词

- **需求提出**：只存在需求描述。
- **已有设计**：存在架构/协议/功能方案，但不确定已编写代码。
- **代码实现**：有可定位实现路径和调用证据，尚不等于运行通过。
- **已测试**：可提供真实运行/测试结果。
- **待确认**：材料缺失、版本冲突或发现实现差异。

对于“源文件里有一个函数但没有调用”不能直接写“功能可用”；对于“测试文件存在”不能写“测试通过”。
