# 从真实项目生成 Markdown 技术文档 + 用户展示 HTML（project-technical-doc）

## 0. 任务定位：这是「项目理解 → 文档生成」Skill

当用户说“理解我的项目并生成技术文档”“按技术文档范本生成项目说明书”“根据代码/技术资料整理技术说明”等时，**立即按以下流程工作，不要先要求用户提供另外一份范本，不要默认先输出逆向分析报告**。

```
用户本次指定的项目目录 / 源码 / 技术资料
    ↓
输入盘点与只读项目理解
    ↓
功能—模块—流程—数据—实现状态梳理，建立可追溯证据
    ↓
按内置技术文档范本编写当前项目的完整 Markdown 技术文档
    ↓
检查 MD 结构、事实与内容边界，必要时修订
    ↓
只读取最终 MD，提取网站首页摘要、功能卡、技术参数、阅读路径
    ↓
按通用 HTML 布局自动渲染正文、目录、表格、流程图、移动端交互
    ↓
检查 HTML 与 MD 内容对应、离线资源与交互/视觉状态
    ↓
同时交付 MD + 单文件 HTML + 执行汇报（用户最终验收）
```

**主交付必须是两个互相对应的文件：`<项目名>-技术文档.md` + `<项目名>_用户展示.html`。** 后者严格从刚生成的 MD 转换，绝不能独立凭源码另写一份技术说明，防止两处表述漂移。证据台账、配置与报告是辅助成果，不能取代两份主产物。不得只做提纲或转化建议就停止。

内置范本：`references/技术文档范本.md`。它只规定**章节组织、写作深度、图表形式与表达方法**，不包含可直接套用的新项目技术事实。写作规范见 `references/style-and-structure.md`。默认不需要每次重新“逆向分析范本”。

### MD 与 HTML 共用的内容边界：不可突破的硬性规则

- **主技术文档只描述当前项目的已知业务、功能、组成、实现原理、数据、流程、测试与必要的协议配置。**不得单独生成“已知问题与改进建议”一章。
- 不得用“存在的问题”“不足与优化”“风险与对策”“未来展望”“后续规划”“升级建议”“技术演进”等名称**变相添加同性质内容**，也不得在结尾另附一段建议清单。
- 即使用户输入资料含有改进计划、技术债、待开发路线或原始示例中有此类内容，**也不复制进入主技术文档**；仅在确有必要时，于`执行汇报.md`的“未纳入内容”记录这类资料未被写入正文的事实，不主动展开优化方案。
- 已存在的超时、重试、错误码、运行依赖等**实现机制或真实运行条件**仍可在对应技术、模块、流程章节正常说明，它们不是独立的评审建议。不要因为排除改进章节而隐瞒对正确理解系统必要的工程事实。
- **同一边界适用于 MD、HTML 首页、正文、导航和页面脚注。** HTML 不能换名增加“风险/缺陷/整改/展望”独立模块，也不能把已排除的章节复制进可折叠区域。必要的功能状态说明（未实测、接口预留、未接入、安全适用边界）属于事实，不是主动提供改进建议，可以如实保留。出现越界章节视为 FAIL。


### 当前项目的资料优先级

1. 用户在**当前任务**中的明确说明和特别约束（命名、覆盖范围、时间、术语、输出要求）。
2. 当前项目的源码、配置、测试产物与真实可见行为（用于判断“是否已经实现”；还需考虑环境与运行限制）。
3. 当前项目的技术手册、设计稿、需求文档、接口协议、硬件资料（用于说明设计、预期和声明的功能）。
4. 内置范本与本 Skill 写作规则（仅用于编排文字）。

注意：第 2 与第 3 类有冲突时**保留冲突并指出**，不能根据个人偏好悄悄选一方；用户当次说明也不能替代缺失的实测证据。外部知识只能在用户允许检索/补充时作为标注来源的背景信息，不得冒充项目事实。

## 1. 项目级共享资产（project-assets）：一个项目一个数据资产库，强制先读后写

本 Skill 与 `thesis-taskbook-write`（任务书）、`opening-report-writer`（开题报告）及后续论文/答辩 Skill **同属一套文书系统**：一个真实项目只有一份共享数据资产 `<PROJECT_ROOT>/project-assets/`，由多个 Skill 共同维护。**本 Skill 是项目技术事实（FACT-xxx）的主要提炼者**：把从源码/技术资料核实的事实写入共享库，后续任务书、开题报告、论文按稳定 ID 直接复用，不再各查一遍、各写一套。完整契约见 `references/shared-project-assets-contract.md`；命令用本 Skill 自带的 `scripts/project_assets.py`（协议兼容副本，所有权常量已归属本 Skill）。

### 1.1 存储位置与红线

- 唯一持久化根目录：`<PROJECT_ROOT>/project-assets/`，含 `project.json`（项目标识、用户确认的稳定元信息）、`references.json`（REF-xxx 文献库）、`facts.json`（FACT-xxx 项目事实）、`schedule.json`（周计划基线）、`activity.jsonl`（审计流水）。
- **绝不能**把 `project-assets/` 放在 `.claude/skills/`、`.agents/skills/` 或本 Skill 安装目录内；**禁止**向本 Skill 的 `assets/`、`references/`、`examples/` 保存项目论文或项目事实（内置文件只放通用规则与范本）。共享资产、用户原始资料、最终交付**永不删除**。
- `project_id` 唯一且持久：读到的 store 与本次任务 project_id 不一致时**立即停止合并**，防止串项目。store 不存在时才允许 `init`，并向用户说明已新建。

### 1.2 稳定 ID 与事实状态映射

- 技术事实用 `FACT-xxx`，文献用 `REF-xxx`，周计划阶段用稳定 stage ID；跨文书关联**只通过稳定 ID**，正文 `[1]` 之类编号只是各文书内部临时序号。
- 本 Skill 证据分类 → `facts.json` status 的固定映射（入库即定状态；**文书体裁不改变事实状态**）：

| 本 Skill 证据分类 | facts.json status | 说明 |
|---|---|---|
| VERIFIED | implemented | 有源码/测试直接证据 |
| DECLARED | declared | 资料声明，未验证实现 |
| EXAMPLE | declared | notes 注明“示例/默认值” |
| DESIGN / PLANNED | proposed | 设计决策或拟完成 |
| UNKNOWN | unverified | 信息缺失/冲突，source 记录疑点 |

- 每条 FACT 必须带 `statement` 与 `source`（文件 + 章节/行号定位）；**不为复用而生造**。本次证据否定已有 FACT 时属“更新已有记录”：`--replace --reason` 显式覆盖，并在执行汇报写明影响的下游文书。

### 1.3 固定执行顺序（每次运行必走）

1. **识别项目**：确定 `<PROJECT_ROOT>` 与 `project_id`，`python scripts/project_assets.py status --root <PROJECT_ROOT>` 读取现有 FACT-xxx/REF-xxx/周计划基线。
2. **先读后写**：阶段 B 事实门禁产出的结论先对照已有 FACT-xxx——可复用的直接引用稳定 ID、不重复入库；仅补充**缺失且有证据**的条目（`merge --kind facts|references`）。
3. **只经稳定 ID 关联**；变更已有条目须 `--replace --reason`，**禁止默默覆盖**其他 Skill 已审定的资产与用户原始资料，**禁止为了复用而生造**。
4. **本份文书独立验收**：阶段 D/E 的结构、事实、边界与一致性检查照常执行，资产库有内容 ≠ 可跳过检查。
5. **使用记录（强制）**：交付后 `record-use --file <项目名>-技术文档.md --doc-type technical-doc [--ref-ids REF-xxx,…]`；HTML 派生页可另登记一条 `--doc-type technical-doc-html`。
6. **安全清理**：过程文件只写自己的 `<PROJECT_ROOT>/.skill-tmp/project-technical-doc/<run-id>/`（由 `workdir` 命令创建，带所有权标记）；报告完成后 `cleanup --run-id` 只删本 Skill 自己的运行目录，**不得**删除其他 Skill 的 `.skill-tmp`、共享资产、用户资料与最终交付。

```bash
# 命令速查（compose 是任务书专用装配命令，本 Skill 不使用）
python scripts/project_assets.py status  --root <PROJECT_ROOT>
python scripts/project_assets.py workdir --root <PROJECT_ROOT>            # 建本轮运行目录
python scripts/project_assets.py merge   --root <PROJECT_ROOT> --kind facts --input <run目录>/new-facts.json
python scripts/project_assets.py record-use --root <PROJECT_ROOT> --file <项目名>-技术文档.md --doc-type technical-doc
python scripts/project_assets.py cleanup --root <PROJECT_ROOT> --run-id <run-id>
```

### 1.5 项目资产包（bundle）布局与版本意识

一个项目 = 一个**资产包目录**（按项目分类，插件化后项目间互不串扰，整包可拷贝/归档/迁移）：

```text
<PROJECT_ROOT>/                        # 项目资产包根；--root 就指向这里
├── project-assets/                    # 共享数据资产（多 Skill 共写，见 1.1）
├── deliverables/                      # 成品集中区，按文书类型分目录
│   └── technical-document/……技术文档-v1.md / ……用户展示-v1.html /
│       physical-modules.json（实物模块清单）/ content-index.json（内容分类索引）
└── .skill-tmp/<skill-name>/<run-id>/  # 各 Skill 运行目录（自动清理）
```

- **成品集中**：本 Skill 的最终文书交付到 `<PROJECT_ROOT>/deliverables/technical-document/`，不散落其他 output 目录；查一个项目的全部产出只看这一个包。
- **版本意识**：项目内容变更或调用 Skill 重新生成时，产出 `-v2`、`-v3`…**新文件绝不覆盖历史版本**；每个版本单独 `record-use` 登记（路径 + sha256），`activity.jsonl` 自然形成变更史。数据层（计划/事实/文献）变更走 `--replace --reason`，与成品版本史互相印证。
- 历史版本属于持久成果，**不在清理范围**；清理只针对 `.skill-tmp` 运行目录。
- **最终版本唯一（每次执行只交付一份最终版本）**：执行内发现缺陷需修复时，修复完成后生成修正版（如 `-v2`），随即将其**改名为本轮应交付的版本名**（如 `-v1`，先删缺陷稿再改名，同一版本的 MD/HTML/汇报等配套文件一起删旧换新）；一次执行结束时交付目录里本次成品只保留一份最终版，过程稿、缺陷稿不与最终版并存。缺陷稿不是历史版本，按此回收不算违反"绝不覆盖"；若缺陷稿曾 `record-use` 登记，回收后以最终定名文件 `--replace --reason` 补登记。跨次执行不受影响：内容变更或用户要求重新生成时仍递增产出 `-v2`、`-v3`…并各自登记。
- **两段式出片（失败稿不进交付区、不占版本号）**：MD/HTML/汇报先在**本轮运行区暂存**构建与验收——`publish.py --out-dir` 指向运行区暂存目录，E4 自动检查与 E5 截图逐张目检都对暂存件执行；**全部 PASS 后**才整体移入 `deliverables/technical-document/` 定 `-vN`（N=交付目录已有最大版本号+1，预检目录、禁止覆盖历史文件）。失败/缺陷稿留在运行区随 `cleanup` 删除，**不进交付区、不烧版本号**；交付后才发现缺陷按上条"最终版本唯一"改名回收。（真实事故：发布直接落交付区 `-vN`，截图目检才发现缺陷，v2 永久留档。）

## 2. 输入识别——用户只需给项目本身

支持三种常见情况，**自动适配，禁止因只提供一种材料就放弃任务**：

| 用户给什么 | Agent 做什么 | “已实现”可如何表述 |
|---|---|---|
| 只给项目技术手册/MD/DOCX/PDF 等 | 按文档的具体事实还原项目，整理技术文档，明确资料声明和预期 | 未核实源码时写“资料描述/方案设计”，不写“代码已证实” |
| 只给源码仓库/工程目录 | 只读理解目录、构建、入口、模块、数据流、接口、状态与测试，生成工程技术文档 | 可写“代码包含/实现了某逻辑”；没有执行验证不写“实测通过” |
| 手册 + 源码 + 测试资料 | 将业务描述、实现证据、测试结果交叉核对后生成，按实际实现解释设计差异 | 能分别说明“设计”“代码实现”“测试验证” |

**只分析用户本次明确授权的路径或上传的材料**。如用户说“当前项目”，使用当前工作区，先确认工作区实际目录；若读不到项目，清楚报告缺少的输入，不要把范本当作用户项目生成一份假稿。资料不够完整但已足够写有依据的部分时，先完成可证实范围，未确认部分在正文/汇报标注。

### 默认输出

若用户未指定目录，在项目资产包内建立 `<PROJECT_ROOT>/deliverables/technical-document/`（见 1.5），只创建新产物：

- **必须**：`<项目正式名称>-技术文档.md`（工程技术原文，也是 HTML 的唯一正文数据源）。
- **必须**：`<项目正式名称>_用户展示.html`（完整正文 + 适度首页摘要，所有 CSS/JS/SVG 内嵌，单文件离线查看）。
- **必须**：`执行汇报.md`（明确两种成果的生成路径、校验状态、待确认事项）。
- **必须**：`physical-modules.json`（实物模块清单 v1；与 MD 同级，定名不加版本号）。
- **必须**：`content-index.json`（内容分类索引 v1；与 MD 同级，供网站按 category/group_id 分组展示，不改变正文）。
- **生成器附产物**：`<项目正式名称>_用户展示.report.json`（可追溯检查状态）；必要时生成 `展示配置.json`，后者的具体信息必须来自当前 MD。
- **建议**：`项目事实与证据台账.md`（大型项目必须，支持事实追溯）。

只写生成目录，不编辑项目源码、配置、用户原资料或内置参考范本；已有同名成果默认不覆盖，创建带版本号的新文件（`-v2`、`-v3`…递增，不覆盖历史版本；用户明确要求更新则按授权处理）。**过程性临时文件**（解析缓存、调试脚本、草稿中间件）写入本轮运行目录 `<PROJECT_ROOT>/.skill-tmp/project-technical-doc/<run-id>/`（`project_assets.py workdir` 创建），交付前 `cleanup` 删除。即使没有项目根目录写权限，也要尽力给出完整 Markdown 正文内容及本次无法写入文件的说明。

## 3. 阶段 A：自动读取、盘点、理解项目

执行以下操作，直到能**独立说清项目如何工作**：

### A1. 盘点输入，判断项目形态

- 明确项目名称、目标用户/场景、文档类别（嵌入式/IoT/算法/后端/前端/全栈/桌面/软硬件一体）。
- 搜集用户明确给的说明书、README、需求文档、协议、原理图/BOM、模块手册、测试记录、构建及部署说明。
- 有代码仓库时先建立目录树与技术栈概览，再沿入口追踪，不因项目较大就随意全量读取无关代码；默认排除本 Skill 所在目录、其内置参考范本，以及既往 `output/technical-document/` 生成结果，不把这些文件当作本项目资料。
- 阅读 `references/project-understanding.md`，按不同项目形态决定必须识别的技术事实。
- **共享资产基线（第 1 章）**：确定 `<PROJECT_ROOT>` 与 `project_id`，`project_assets.py status` 读取已有 FACT-xxx/REF-xxx；理解阶段的结论优先对照既有事实，可复用的引用稳定 ID，不重复入库。

### A2. 源码只读理解路径（如有源码）

1. **入口和构建**：识别可证实的运行入口、目标平台、依赖、编译/启动配置、编译宏与环境变量名称（不读取变量值中的秘密）。
2. **模块和依赖**：依目录、接口、调用关系识别模块职责；查明谁产生数据、谁处理数据、谁消费结果。
3. **核心运行链路**：追踪一条或多条端到端业务路径，例如“采集 → 处理 → 告警 → 上传”或“请求 → 业务服务 → 数据库存储 → 响应”。
4. **协议与数据**：读接口/消息/结构体/数据表/序列化字段，整理方向、字段、单位、异常机制；标注代码路径、符号、行号（工具可准确得到时）。
5. **实现状态**：以代码和测试证据判断具体能力，不因目录名存在就认定功能实现；识别 TODO、mock、stub、未接入路径及失效分支。
6. **测试和限制**：识别已有测试文件与实际输出，区分“存在测试用例”“实际运行通过”“未执行”。未经用户授权不执行可能影响外设、网络或数据的命令。

只读范围内可使用目录树、文本搜索、源文件阅读和安全静态检查；排除 `.git/`、`node_modules/`、虚拟环境、编译产物、日志大文件、缓存和与任务无关的目录。**不主动查看或输出** `.env`、密钥、Token、私钥、密码、个人信息或其他秘密。不要为了写文档修改工程或运行破坏性命令。

### A3. 技术资料理解路径（如有文档）

提取：定位场景与痛点；功能清单；硬件/软件组成；主控、传感器、通信、算法、服务与接口；任务/线程/状态机；数据结构和数据库；时序、阈值与参数；部署与维护；测试结果；版本状态。资料中的缺陷与扩展计划只用于辨别“当前已实现”和“尚未实现”的界线，不作为新增问题/建议章节的素材。**保留原资料给出的数字、术语、单位和边界**，不要自动替换或纠错，发现矛盾只记录“待确认”。

### A4. 建立“我理解的项目模型”

内部先整理下列内容再动笔写正文：

- 一句话系统定位：谁在什么场景下解决什么问题，输出什么价值。
- 系统边界：有哪些硬件/软件子系统；外部平台或人员是什么关系。
- 完整功能树与实现状态：功能 → 对应模块 → 技术手段 → 输入输出 → 当前证据。
- 至少一条真实的主数据/主业务流程；存在关键异常时补充失败/恢复路径。
- 重要接口/协议、关键参数及数据字典。
- 已证实、仅设计、仅示例、待确认四类可用于正文的信息；计划改进另行识别但不进入技术文档正文。

如发现“资料说已实现而代码不存在”“通信协议字段不一致”“阈值与判断方向冲突”等，应汇总冲突，正文谨慎表述，不私自发明最合理的版本。

## 4. 阶段 B：写作前的事实门禁

使用 `templates/evidence-register.md` 的轻量证据格式；材料较多时写入成果目录。每项关键结论至少具备一个定位信息：`文件路径 + 标题/函数/行号`、用户当次描述、可读测试记录；如不能定位，则降低表述确定性。

| 分类 | 意义 | 允许写法 |
|---|---|---|
| VERIFIED | 已有直接实现/测试证据 | “代码中由 ... 模块实现 ...”；测试完成需附真实测试证据 |
| DECLARED | 项目手册明确写过、但尚未验证实现 | “设计文档规定 ... / 系统方案包括 ...” |
| DESIGN | 本项目已有设计决策或参数目标 | “设计为 ... / 计划采用 ... / 目标是 ...” |
| EXAMPLE | 原项目材料中的示例、默认值、演示数据 | “示例 ... / 默认配置 ...”，不等于实际运行 |
| UNKNOWN | 信息缺失、材料冲突或证据不足 | “待确认 ...”，不杜撰细节 |

表格、流程图、接口示例也要遵守。不得从范本或通用知识中自动补造具体芯片型号、传感器、协议、阈值、数据表、接口字段与测试结果。

**本阶段确认的关键结论按第 1.2 节映射形成 FACT-xxx**（statement + source 定位 + status），交付前 `project_assets.py merge --kind facts` 写入共享库（先读后写，仅补缺失；变更已有条目须 `--replace --reason`）；正文引用共享事实时保持其 status 口吻，不因本次成文而升格。

**素材不足时优先保留真实技术深度**：例如能完整追溯 4 个模块，就深入写 4 个模块，别为凑出 10 个相同体量的章节发明 8 个模块。对某章仅有需求而无实现时写“方案/待确认”；若本项目完全无此概念则调整章题或说明“不适用”，绝不捏造。

## 5. 阶段 C：依据通用技术文档范本直接写成正文

内置写作风格见 `references/style-and-structure.md`；章节底稿见 `templates/technical-document-skeleton.md`。通常采用以下顺序：

### 分章分批写入与一次终检（硬性，禁止一次性整篇生成）

- **分章分批写入**：MD 正文不得在一个写作动作里整篇倾倒。第一步只写骨架（各章标题 + 每章 2～4 条要点提纲）并保存；之后**逐章**成文——每章用独立的写入动作落盘，一章定稿后再写下一章，按第 1→10 章顺序推进；单章内容多时再分 2～3 批（概述段→要点段→小结段）追加写入。
- **落盘后再续写**：一批内容没有写入文件之前，不开始下一批；不把多章合并成一次超长写入。
- **响应异常自愈**：单次超长输出会超出稳定响应窗口（真实事故：822 行 10 章整篇写入致响应长时间等待直至中断）；响应等待明显变长或中断时，**立即自行切更小批次（半章/单节）续写**，不必等用户指示——续写前先读文件现状对齐断点，不重写已落盘内容。
- **定点修订，不推倒重写**：中途发现已定稿章节有误，只定点修订该处并在执行汇报留痕；不因后文调整回炉重写全文。
- **一次终检**：全部章节落盘后进入阶段 D，做**一次且仅一次**端到端终检；阶段 D 即唯一终检，写作过程中不反复全文重查。终检发现的问题定点修正后进入 HTML 阶段。
- HTML 由脚本从最终 MD 一次性派生（阶段 E），`展示配置.json` 按条目逐项填写；不在 HTML 阶段回写或重写 MD。

1. **项目概述**：场景/需求痛点 → 系统定位 → 总体方案 → 技术规格汇总。
2. **功能说明**：功能树 → 各功能输入、行为与输出 → 角色和使用场景 → 功能/模块/实现状态映射。
3. **系统总体架构**：分层架构/组件拓扑 → 各层职责 → 运行时数据流。
4. **硬件平台与资源分配 / 软件技术栈与资源设计**：依据项目类型说明选型、接口、硬件引脚或运行部署资源。
5. **核心技术解析**：挑选最重要的技术机制，解释原理、处理链、关键参数、算法、协议、边界、可靠性。
6. **模块详解**：模块职责、输入/输出、依赖、接口、关键处理、故障边界；与第 2 章“对外能力”不同。
7. **关键流程**：启动流程、主业务流程、数据/交互流程、异常和恢复流程；用 Mermaid 辅助多分支逻辑。
8. **数据与存储设计**：真实结构体、JSON/协议字段、数据库表/文件存储；无数据库则不生造数据库。
9. **系统测试方案**：测试环境、场景、操作、预期结果、**已有实测**分别列出；若无记录只写方案与预期。
10. **附录：协议与配置速查**：关键参数、接口、字段、术语与参考资料；没有就只保留必要附录。

“10 章”是默认结构，而非无证据也必须写满；有必要时调整章名或合并不适用内容，并在执行汇报说明；但不得因此恢复被排除的章节。**生成的是有细节的成稿，不是小节占位符**。技术深度尽量接近参考范本，实际长度由项目材料支撑程度决定，不强行指定字数、表格数、流程图数或页数；范本/模板的篇幅仅是参考，不得为凑足或压缩到某个篇幅而增删事实、稀释或堆砌文字（实质性分页门禁同源原则）。

### 图示硬性要求（强制：MD 必须自带图，HTML 才可能有 SVG）

- 技术 MD **必须**包含 Mermaid 图（` ```mermaid ` 流程图/框图）：**「系统总体架构」章至少 1 幅、「关键流程」章每个关键流程至少 1 幅、全文至少 1 幅**；文字描述不能替代图。
- 这是 `check_markdown.py` 的**硬门禁**（ERROR）：0 幅 Mermaid、或"总体架构/关键流程"章缺图 → 判 FAIL，**禁止进入 HTML 阶段**。原因：HTML 从 MD 单向派生，MD 无图 = HTML 无图无 SVG，事后补不进交付链。
- 图只画**有证据的**结构/流程（与正文一致，不虚构模块）；图形引擎缺失时降级为可展开源码回退 + WARN（见 E4 预检），但图源在 MD 中**必须存在**。

### 分章写法与内容质量

- 第 1 章强调“项目是什么、为什么要做、核心组成”，不要堆算法细节。
- 第 2 章强调“用户/外设能感知到哪些行为、触发与结果”，每项能对应后文模块。
- 第 3 章强调结构关系和数据流图，不把功能树画成架构图。
- 第 4/5 章要说清具体接口、机制、单位、关键配置和技术约束；资料不支持的参数不补造。
- 第 6 章每个重要模块至少回答**职责、输入、处理、输出、依赖、异常**，可简洁整合表述。
- 第 7 章不能把互不相关的业务机械串成一个假主循环；并行、异步、分支依实际架构表达。
- 第 8 章对字段名、类型、单位、映射关系保持一致，JSON 可解析且示例自洽。
- 第 9 章明确区分“应当如何测试”与“已经测出了什么”。
- 第 10 章是速查，不要重复全文大段叙述；若项目完全不需要附录可删减。
- 不得追加问题清单、改进建议、优化方向、技术展望等越界章节或段落。

### 形式表达（遵循范本规则，但不是机械填空）

- `# 项目名称 — 技术文档`；引用块说明适用范围与版本；数字编号的 H2/H3；正文开始前有目录。
- 用表格写技术规格/资源分配/字段定义/功能映射/测试用例。
- 用文本树展示功能层次，用 ASCII 或 Mermaid 画系统架构/流程；多分支流程优先 `mermaid`。
- 需要演示协议时用 `json` / `c` / `text` 代码块；示例必须注明性质，不伪造真实运行结果。
- 中文工程文风：先说明用途，再讲工作方式、边界和异常；名词、单位、字段、角色名称统一。
- 避免每章都重复相同一段功能说明；项目没有的页面、短信、云平台等绝不出现。

## 6. 阶段 D：先检查与修订 MD，再进入网页生成

全部章节分批落盘后，做**一次且仅一次**端到端终检（本阶段即唯一终检，写作过程中不反复全文重查），至少执行以下检查：

1. **文档结构**：目录、标题编号、Markdown 表格与代码围栏闭合、JSON 示例解析、内部锚点。可运行 `python <skill-root>/scripts/check_markdown.py <生成的技术文档.md>`。
2. **依据真实性**：关键断言有项目资料支持；实现/设计/目标/待确认区分清晰；没有借用范本事实或伪造实测值。
3. **跨章一致性**：功能 ↔ 模块 ↔ 流程 ↔ 测试；资源/接口 ↔ 架构；参数/单位/阈值方向 ↔ 示例；字段 ↔ API/结构体/数据表 ↔ 附录。
4. **工程可理解性**：读者不看原资料也能理解项目的组成、主要技术与流程，未知之处可辨识。
5. **安全与边界**：未暴露机密；原项目源码及资料未被改动；所有不确定和不适用内容如实披露；没有生成问题/改进/未来规划等越界内容。
6. **实物模块清单（physical-modules.json）**：运行 `python <skill-root>/scripts/gen_physical_modules.py <生成的技术文档.md>` 从正文「模块详解」章自动生成与 MD 同级的 `physical-modules.json`（固定定名、不加版本号；契约见下方「实物模块清单契约」）。生成器只收录传感器、执行器、显示、按键输入、通信模组等**具备实物形态**的模块，自动排除 `uart_comm` / `Warn` / `main` / 全小写下划线软件名。随后 `check_physical_modules.py` 必须 PASS；FAIL 修订后复检。`publish.py` 会再次强校验。
7. **内容分类索引（content-index.json）**：运行 `python <skill-root>/scripts/classify_content.py <生成的技术文档.md>` 生成与 MD 同级的 `content-index.json`（固定定名、不加版本号；契约见下方「内容分类索引契约」）。它把每张表、每个 Mermaid 图、每个实物模块按类型分类并归并相似组，供网站按 `category` / `group_id` 分组；**不改变正文、不渲染网站**。`check_content_index` 必须 PASS（覆盖所有表/图/实物模块，缺失或多余即 FAIL）。`publish.py` 会再次强校验。

发现问题应先按原始证据修订一次，再重新检查。**无法凭来源消除的疑点保留“待确认”，不凭猜测修复**。检查参考 `references/quality-gates.md`。

### 实物模块清单契约（physical-modules.json v1）

**文件位置与命名固定**：与交付的技术文档 MD（`<项目名>-技术文档.md`；用户执行器以 `out/` 为输出目录时即 `out/physical-modules.json` 与 `technical-技术文档.md` 同级）**同级**的 `physical-modules.json`，不加版本号、不改名；随 MD 一起交付/移动（交付区同名件随最新交付版本同步更新）。数据契约：

```json
{
  "schema_version": 1,
  "generated_by": "project-technical-doc",
  "modules": [
    {"code": "D1", "name": "粉尘模块", "hardware": "D1 粉尘传感器（TTL 串口输出）",
     "category": "sensor", "source_files": ["D1.c", "D1.h"], "pins": "USART2",
     "note": "周期性读取，帧同步校验"},
    {"code": "OLED", "name": "显示模块", "hardware": "0.96寸 OLED（软件 I2C）",
     "category": "display", "source_files": ["OLED.c"], "pins": "PB8/PB9", "note": ""}
  ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| code | ✅ | 模块标识，必须与正文「模块详解」章的小节标识一致（如 D1、SHT40、RS485），全文件唯一 |
| name | ✅ | 中文模块名 |
| hardware | ✅ | 对应实物/器件描述；没有具体器件就写该模块对应的外部硬件 |
| category | 建议 | sensor / actuator / display / input / communication / other |
| source_files | 可选 | 该模块相关源文件名数组（裸文件名，不写目录/绝对路径） |
| pins | 可选 | 引脚/接口（如 I2C1、PB14） |
| note | 可选 | 一句话说明 |
| section | 可选（生成器附加） | 该实物模块所属「模块详解」H3 小节标题；子模块（如 6.1 内的 D1/SHT40/火焰/土壤）用它映射到章节 |
| section_line | 可选（生成器附加） | 所属小节在 MD 中的起始行号，供网站定位 |

**判定规则（本 Skill 保证；脚本机械校验可查部分）：**
- **只列具备实物形态的模块**：传感器、执行器、显示、按键输入、通信模组等；
- **排除软件模块**：通信抽象层（如 `uart_comm`）、纯逻辑（如 `Warn`）、主程序（`main`），以及模块间关系章节；
- code 必须能在「模块详解」小节标题中找到——脚本按词边界匹配（防 `D1` 误配 `D10`），找不到的条目下游会拒绝，必须修正；
- **按正文出现顺序排列**（脚本校验单调不减；同一小节并列多个模块如「OLED / Buzzer / LED」允许）；
- 项目没有任何实物模块时 `modules` 为 `[]`（字段不得省略）；
- 只给元数据：不输出图片、base64 或路径引用（脚本拒绝绝对路径/内嵌图片，`source_files` 只许裸文件名）；
- 命名形似软件模块（全小写下划线 / main / warn）时脚本给非阻断警告，人工确认后保留或删除。

### 内容分类索引契约（content-index.json v1）

**文件位置与命名固定**：与技术文档 MD 同级（`out/content-index.json` 或 `<项目名>-技术文档.md` 同级），不加版本号、不改名。它只是**分类元数据**，不替代原文表格/流程图，也不负责网页渲染。

```json
{
  "schema_version": 1,
  "generated_by": "project-technical-doc",
  "source_md": "technical-技术文档.md",
  "source_md_sha256": "……",
  "items": [
    {
      "id": "TBL-001",
      "kind": "table",
      "title": "8.1.1 SHT40_DataTypeDef（SHT40.h）",
      "chapter": "8 数据结构",
      "section": "8.1.1 SHT40_DataTypeDef（SHT40.h）",
      "line_start": 123,
      "line_end": 131,
      "category": "data-structure",
      "group_id": "GRP-XXXXXXXX",
      "group_title": "SHT40 数据结构",
      "module_code": "SHT40",
      "headers": ["字段", "类型", "单位"],
      "row_count": 3,
      "caption": "表8-1  SHT40 数据结构",
      "content_sha256": "……",
      "keywords": ["SHT40", "字段", "类型", "单位"]
    }
  ],
  "groups": [
    {"id": "GRP-XXXXXXXX", "title": "SHT40 数据结构", "category": "data-structure",
     "item_ids": ["TBL-001", "TBL-002"], "count": 2}
  ],
  "summary": {"items": 10, "tables": 7, "diagrams": 3, "modules": 8,
              "groups": 5, "by_category": {"data-structure": 4}}
}
```

**类别（category）**：`data-structure`、`protocol`、`interface-pin`、`parameter-config`、`hardware-resource`、`specification`、`function`、`schedule`、`technology`、`terminology`、`index`、`materials`、`appendix`、`test`、`flow`、`architecture`、`excluded`、`other-table`、`other`；模块另用 `sensor/actuator/display/input/communication/other`。

**归并规则**：
- 分组键不再带章节前缀；按 `category` 或 `category+模块/协议 code` 归并（如 `SHT40 数据结构`、`RS485 数据结构`、`Modbus 通信协议`、`规格与选型`、`功能与场景`）；
- 引脚/接口表归并为「引脚与接口」；参数/阈值/配置表归并为「…参数与配置」；
- 流程图按章归并为「…流程图」，架构图按章归并为「…架构图」；
- 分类以**表头/题注内容**优先，章节标题只作弱信号：如「测试与结果」章下的 `模拟量/表达式/取值范围` 表归为参数配置，「附录」章下的 `器件/地址`、`返回码` 表分别归为接口/数据结构；
- 规格/选型表归并为「规格与选型」；功能/场景/角色表归并为「功能与场景」；任务/周期表归并为「任务与调度」；技术解析表归并为「技术说明」；
- 架构/组成/职责表归并为「架构与组成」；中断/优先级/缓冲区/DMA 表归并为「硬件资源与分配」；状态/转移/异常表归并为「状态与流程」；术语/缩写表归并为「术语与定义」；索引/目录表归并为「索引与目录」；资料/文档/标准表归并为「资料与参考」；附录/模板/速查归并为「附录与速查」；`excluded` 归入「已排除章节（不应展示）」；
- 实物模块按类别归并为「传感器模块 / 通信模块 / 显示模块 / 交互输入模块 / 执行器模块 / 其他实物模块」；
- **只归并展示分组，不合并/删除任何原文数据**；相同 `content_sha256` 只提示网站可去重。

**覆盖门禁**：`check_content_index` 比对 MD 中实际表格数、Mermaid 数、实物模块数；索引缺一项或多一项即 FAIL。`publish.py` 发布前强制调用。

待 HTML 阶段执行完毕再完成 `执行汇报.md`：除项目与 MD 检查信息外，还需列出 HTML 路径、章节/表格/流程图数量、SVG/回退数量、MD/HTML 对照状态、离线依赖情况、浏览器检查是否实际执行，和用户需要验收的事项。使用 `templates/execution-report.md`。

**用户最终验收**：Agent 不自行宣称业务正确/最终验收通过；用户修改 Skill、范本或资料后，只按本次最新版本重新生成或局部修订，并报告变动。

## 7. 阶段 E：必须从最终 MD 自动生成用户可视化 HTML（本次新增）

> **重要依赖**：先生成并检查 `<项目名>-技术文档.md`、`physical-modules.json`、`content-index.json`，才能执行 HTML 阶段。**禁止先写 HTML 再倒推 MD；禁止同一份项目资料分别驱动两套内容生成逻辑。** 这样 MD 是唯一事实正文，HTML 是派生展示层。

### E1. 页面结构与视觉风格（参考用户提供的 HTML 页面，只提取通用范本）

读取 `references/html-layout-and-content.md`，复用 `assets/layout.html` 固定页面框架：

1. **侧边目录**：桌面固定侧栏、H2 章节和 H3 小节自动导航、搜索匹配章节、滚动高亮、顶部阅读进度条。
2. **首页 Hero**：真实项目名称、1～2 句来自 MD 的简介、3 个有效章节跳转入口、抽象科技卡通示意图；示意图不得冒充实拍或程序运行截图。
3. **核心能力卡**：优先从 MD 真实功能提取 2～4 项能力、简要说明及实现状态；证据不足改为“章节速览”，绝不虚构功能以凑数。
4. **工作过程与参数**：至多 4 步业务流程与 4 项可追溯参数；无可靠数据改为“阅读路径 / 文档结构速览”。
5. **完整正文**：每一章独立的白色圆角卡片，保留原文的技术段落、H3、列表、表格、代码块、Mermaid、引用与实际实现状态；页面长滚动，非宣传性删减摘要。
6. **移动及打印**：手机端抽屉导航、响应式表格和流程图、打印样式，原生 CSS/JS，无互联网依赖。

风格锁定为**浅色紫蓝 + 淡青薄荷点缀的科技卡通风**；不要按新项目擅自改成深色仪表盘、商业落地页、营销宣传页。示例 HTML 和页面工具包只是**布局与交互参考**，不得从中复制具体项目的参数、功能、名称、状态到新项目。

### E2. 内容映射（以生成好的 MD 为唯一依据）

- `#` → 网站名称；前言/引用块 → 来源说明与必要事实边界； `##` / `###` → 章节卡/子章节导航，按 MD 实际数量生成。
- 段落与列表 → 原意完整保留；表格 → 每行每列保留并允许表格区域横向滚动；JSON/C/其他代码 → `pre/code` 原样展示。
- Mermaid → 自动按源文本节点与分支尝试生成**内嵌 SVG**，并保留可展开源码用于核对；不支持的语法必须以原始 Mermaid 代码块回退并报告，不能声称已完成图形化。**图区全局显示**：流程图完整呈现，禁止内层滚动条、`max-height` 高度压缩与 `min-width` 溢出（模板规则与自动拦截见 E4/E5）。
- 设计/实现/待验证状态 → 保持原有证据等级，不将“有代码”改写成“已实测通过”。网页首页如需展示范围说明，应简短、中性，**不是改进建议板块**。
- HTML 不独立添加任何新的功能、统计量、医疗效果、技术参数或测试结果；首页精简文案是**来源支持的摘录**，不能改变事实。技术正文不因视觉美化而删掉重要细节。

### E3. 从 MD 填写首页配置

建议 Agent 先复制 `examples/showcase-config.example.json`，以**刚生成的完整 MD**填写 `title`、`summary`、`features`、`process_steps`、`facts` 和 `notice`，保存到输出目录 `展示配置.json`。每条首页内容都先在 MD 中找到对应段落/表格/流程；缺乏证据就删掉该条配置，脚本自动用章节目录或文档统计填充，不得填示例占位文字。

如果资料不足以提取业务摘要，**仍然必须生成 HTML**，使用脚本的保守降级首页，不把 HTML 当可选交付。

### E4. 一条命令完成 HTML 发布和自动检查

首次使用若缺依赖：`python -m pip install -r <skill-root>/requirements.txt`。只从信任的软件源安装依赖；无法安装时如实报告障碍，尝试已有本地环境。

**图形引擎预检（每次进入本阶段先做，别等交付才发现图没转）**：

```bash
python <skill-root>/scripts/diagram_svg.py engine
```

`svg_capable=true` 才能期待 Mermaid 转为离线 SVG；为 `false` 时**立即告知用户**（不是交付时才说）：本次流程图将保留可展开源码回退、执行汇报记 WARN，并给出安装命令（`npm i -g @mermaid-js/mermaid-cli` 或 Graphviz）。**安装前先说明并征得同意**：讲清缺的是"Mermaid 文本→SVG 转换器"、要装什么、体量多大、走哪个源，经用户确认再执行，或把命令交给用户自跑——winget/npm 全局安装会触发 UAC/权限提示，用户不知情时容易被取消（真实事故：Graphviz 弹 UAC 被取消、npm 安装被用户中止）。预检也可提前到写作阶段做一次，让用户尽早决定装不装；至少不得晚于本阶段开工。用户装好引擎后重跑 `publish.py` 会自动生成**新版本** HTML 补上 SVG，不覆盖旧版。`publish.py` 本身也会做同样的预检并写入报告的 `svg_engines` 字段。

```bash
# 两段式（见 1.5）：--out-dir 先指向本轮运行区暂存目录；E5 全部 PASS 后才移入 deliverables/technical-document/ 定 -vN
python <skill-root>/scripts/publish.py "$WORKDIR/staging/<项目名>-技术文档.md" \
  --config "$WORKDIR/staging/展示配置.json" \
  --out-dir "$WORKDIR/staging"
```

没有配置时删除 `--config` 参数。发布程序依次：**检查 MD → 解析 Markdown → 转换 Mermaid 为离线 SVG（Mermaid CLI 优先，简单 flowchart 可用 Graphviz 回退）→ 填入用户页面模板 → 输出 HTML → 按 MD 对照全文 → 逐图渲染内容断言（样式闭合 / 标签存活 / 字号可读性代理，防"SVG 渲染损坏却全绿"）→ 生成 JSON 报告**。校验默认落盘同名 `<html>.audit.json` 证据文件，作为 record-use 登记凭证。MD 检查 FAIL 时禁止进入 HTML 阶段；HTML 检查 FAIL（含渲染内容断言失败）时不得以完成状态交付。默认创建带版本号新 HTML，防止覆盖已有成果；按 1.5 两段式出片，发布输出先落运行区暂存，E5 通过后才移交付区定版号。

生成网页后也可以独立复查：

```bash
python <skill-root>/scripts/validate_html.py "output/technical-document/<项目名>_用户展示.html" \
  --md "output/technical-document/<项目名>-技术文档.md"
```

### E5. 交付前检查（自动 + 实际浏览器）

- **正文一致性**：MD 的章标题、小节标题、表格单元格、长段落、列表项、代码/协议、Mermaid 定义在 HTML 中均可找到；检查页面内的值、单位、状态和文字，没有新编造。
- **内容边界**：目录、卡片、正文、页脚都不能出现单独的已知问题/改进/展望章节；页面展示必须保留真实的功能状态与必要适用范围。
- **图形**：SVG 数量、流程图源码数量与 MD 一致；仅源码回退计为 WARN，并说明转换能力限制；不能以空白图替代。**HTML 中 Mermaid 图为 0 属 FAIL**（阶段 C/D 的 MD 图示硬门禁已保证 MD 必须有图）。**逐图渲染内容断言**（`validate_html.py` 自动执行）：`<style>` 与 `url(#…)` 引用必须闭合命中本图 id、Mermaid 源标签必须 100% 存活于 SVG 文本、估算最小字号 <9px 报 WARN——断言失败即 **FAIL**，不得降级为 WARN；图区出现内层滚动条/高度压缩/最小宽溢出同样 FAIL（流程图必须全局显示）。
- **本地静态**：无必须联网才能使用的 CSS/字体/图片/JS；单个 HTML 文件双击可打开。
- **结构/交互**：检查全部导航锚点、章节搜索、滚动进度、移动抽屉、技术表格横向滚动和图容器；链接无死链。
- **截图验证分析（Screenshot Verification Analysis，交付前硬性环节）**：可用浏览器时对**首页、关键章节、搜索/抽屉交互态**在 1440px、768px、390px 三种宽度截图并**逐张分析**，固定三步——
  1. **截图**：三宽度全页/关键屏截图，只存本轮运行目录，不进交付目录；截图集必须过**覆盖矩阵** `screenshot_audit.py coverage --manifest <shots.json>`（1440/768/390 × 首页/含图章节/交互态 9 格齐全且字节互异），缺格或字节级重复 = 拍摄失败，补齐前不得进入分析；
  2. **逐张分析**（缺一张即未完成）：重叠、全页横向溢出、空白图/破图、导航锚点/章节搜索/滚动进度/移动抽屉、技术表格横滚、Console 错误、Mermaid SVG/回退显示；
  3. **留痕汇报**：执行汇报固定填写截图工具、截图张数、实看张数、逐张结论 PASS/WARN/FAIL 与问题清单、返工复检次数。
  浏览器不可用则明确记录**未执行截图验证分析**，不能谎称通过；自动校验不等于截图验证分析。
- **截图伪象防护（防误判的硬规则，细则见 `references/browser-verification-notes.md`，工具 `scripts/screenshot_audit.py`）**：
  1. **量测先于定性**：判定"横向溢出/布局错位/内容截断"FAIL 之前，必须先跑 `screenshot_audit.py probe` 拿量测数据（`body.scrollWidth` vs 视口宽）；目测截图得出的溢出结论不作数。Windows 无头 Chrome 有约 512px 最小布局视口，`--window-size=390` 的截图是 512 布局**裁**成 390 的图——右缘被切可能只是裁切伪象，不是页面 bug。
  2. **截图字节级查重**：逐张分析前先 `screenshot_audit.py dupcheck`；两张"不同状态/章节"的截图哈希相同 = 锚点未滚动或状态未切换导致**拍摄失败**，必须重拍，不得解释为"两处一致"。
  3. **窄视口与章节截图用 iframe**：390px 移动端验证用固定宽度 iframe 强制真实布局视口；章节截图用负偏移 iframe 切片（`screenshot_audit.py harness`），因为 `--screenshot` 永远从文档顶部开始、锚点/`scrollIntoView()` 无效；全页长图有高度上限，超出部分靠章节切片补齐。
  4. **探针脚本红线**：注入 JS 不用带反斜杠转义的 heredoc（会层层转义成语法错误静默失败），用独立 `.js` 文件由 Python 读取；探针立即执行不等事件、只测一次写一次结果；出错先抓浏览器 Console/dump-dom 报错，不对着截图猜。
  5. **动效如实声明**：滚动高亮、阅读进度条等无法逐帧截图时写"代码审查确认，未逐帧实测"，不算截图验证通过项。
  6. **交互态截图先构造可达状态**：抽屉/搜索/交互态截图必须先把状态真实构造出来（抽屉打开、搜索框可见、目标章节滚动到位）再拍；拍到的不是目标状态＝拍摄失败，按第 2 条重拍，**不得把"拍不到"写成"功能缺失/页面没有"**（真实事故：搜索框在抽屉内、抽屉没开就拍，险些误判）。

如需手工修正布局，只能改 HTML 展示层或通用模板的安全副本；若发现技术事实错误，先依据项目资料修订 MD，再从 MD **重新生成** HTML，禁止直接改 HTML 技术正文形成双版本漂移。

### E6. 交付与失败处理

- MD 成功但 HTML 失败：保留有效 MD，报告 HTML 阶段失败及原因；不得把任务整体报为完成。
- 生成成功但有 SVG 回退：HTML 可阅读但图形化部分有 WARN，说明真实数量及原因。
- 同时生成两份文件后，再完成最终 `执行汇报.md`，列出 MD 与 HTML 的对应路径和检查结果，由用户最终验收。
- **交付移动（两段式收口）**：E5 全部 PASS 且汇报完成后，才把暂存区的 MD/HTML/`.audit.json`/`.report.json`/`执行汇报.md`/`physical-modules.json` 整体移入 `deliverables/technical-document/` 并定 `-vN`（N=已有最大版本号+1；`physical-modules.json` 保持定名不加版本号，随最新交付版本同步更新）；失败稿留运行区随 `cleanup` 删除，不进交付区、不占版本号。

## 8. 一次性交付和停止条件

本 Skill 的正常运行不是问答式教学：除非项目完全不可读取，否则直接读取资料、理解项目、组织内容、完成文档、执行检查并汇报。不得反复询问模板、章数、段落语气、是否可以开始等已由 Skill 决定的事项。

完成标志：**存在一份与当前项目证据一致的完整 MD、由该 MD 派生的单文件 HTML 用户展示页、与 MD 同级且契约校验通过的 physical-modules.json 与 content-index.json，以及注明双产物检查情况的执行汇报**；关键设计事实不以已验证口吻出现；用户能够审查并提出修订。交付前按第 1 章执行 **`record-use` 登记**（成品路径、REF-xxx、sha256）与 **`cleanup` 清理**本轮运行目录；**HTML 派生页登记必须已存在同名 `<html>.audit.json` 校验证据（publish/validate 默认生成），无证据不得登记**；共享资产与用户原始资料任何情况下不得删除。如果实际材料缺失造成不能执行，明确说明具体缺口，不从内置参考范本捏造新项目。

- `scripts/screenshot_audit.py`：截图字节级查重（dupcheck）、真实布局量测（probe）、章节切片 harness 生成（harness）、图区渲染/像素探针（renderprobe、pixelprobe）、截图覆盖矩阵核对（coverage）。
- `scripts/viewport_probe.js`：布局量测探针（由 screenshot_audit.py 注入，单次执行）。
- `scripts/diagram_probe.js`：图区渲染探针（高度比/容器滚动条/填充色/文字色对比，由 screenshot_audit.py renderprobe 注入，单次执行）。
- `references/html-layout-and-content.md`：用户提供的可视化页面所提取的通用布局、样式和内容映射规范。
- `assets/layout.html`：通用离线 HTML 页面视觉/交互骨架，不含示例项目业务。
- `examples/showcase-config.example.json`：可选首页配置字段示例（必须替换真实项目内容）。
- `scripts/publish.py`：MD、physical-modules.json、content-index.json 均检查通过后，完整生成 HTML + JSON 检查报告的一键发布入口。
- `scripts/render_html.py`：从当前 MD 自动填充通用网站布局。
- `scripts/diagram_svg.py`：Mermaid 流程图离线 SVG 自动生成与原文回退；`diagram_svg.py engine` 输出图形引擎预检 JSON（exit 2=无引擎）。
- `scripts/validate_html.py`：HTML 结构、离线依赖、章节与 MD 内容对应检查 + 逐图渲染内容断言（样式闭合/标签存活/字号代理）与模板 CSS lint（未作用域元素选择器、图区压缩/滚动禁令），默认落盘 `<html>.audit.json` 证据。
- `requirements.txt`：HTML 阶段的本地 Python 解析依赖。
