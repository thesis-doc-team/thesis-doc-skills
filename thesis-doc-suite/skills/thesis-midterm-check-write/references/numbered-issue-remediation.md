# 问题与整改分点配对规则（强制，v1.3）

## 正式成品的结构（官方同一个单元格，不能新增表格栏目）

在官方“存在的问题及整改措施：（学生自述，不少于200字）”的原有正文空间内，依次填写：

```text
存在问题：
（1）……问题的对象、现象、影响；标明已出现还是尚待验证。
（2）……问题的对象、现象、影响；标明已出现还是尚待验证。
整改措施：
（1）……针对问题（1）的具体改法，附测试或验收办法。
（2）……针对问题（2）的具体改法，附测试或验收办法。
```

- **位置固定**：先问题后措施；两个小标题单独成段、首行缩进0；（1）（2）等编号段各自成段、缩进24pt。
- **一一对应**：问题数量与整改数量完全相等，编号均从（1）连续到（N），顺序必须一致；整改（i）只能回答问题（i），不引入无关内容。
- **字数与篇幅**：两组正文连同栏目内的小标题共不少于200有效字符；建议2—3对，最多4对。官方该格只有10个写字占位（2标题 + 2N条）；如果问题超过4项，应优先按同因同果归并，不得一段塞多号；归并会损害事实时报告容量冲突。
- **事实边界**：实际故障与未验证的潜在风险必须区分；没有证据的误差、成功率、时延和故障率不得编造。措施须具有可执行动作和可核验的观察/测试，不写“加强研究”“继续努力”之类套话。
- **默认来源**：技术文档与项目 `facts.json/progress.json`；参考样本仅用于体裁学习，不以范本项目的问题充数。

## 推荐结构化输入（逐对写作，不需要人工数编号）

```json
{
  "issue_pairs": [
    {
      "problem": "数据采集与异常过滤模块尚缺长时间连续运行测试，无法据此确认异常数据保护措施是否稳定。",
      "action": "补充传感器断连、异常值及连续采样测试，逐项记录原始数据、错误处理状态与恢复效果。",
      "verification": "对照测试记录检查无效数据是否被隔离及恢复过程是否可靠"
    },
    {
      "problem": "远程通信链路在信号变化条件下尚缺充分的可靠性证据，断线时的数据完整性仍待验证。",
      "action": "构造弱网与断网重连工况，核查缓冲重发、消息时间顺序与重复上报情况，整理统计数据。",
      "verification": "核验连续上传日志及掉线恢复后的数据完整性"
    }
  ]
}
```

上述仅是**假设性的写法示例**，不能直接作为某课题事实或作为完成度证明。`issue_pairs` 为优先输入形式；程序会自动生成 `issues_paragraphs` 内的双标题和编号，避免编号遗漏。也可输入已按格式排好的 `issues_paragraphs`，但必须经过同一结构校验；如果两者同时存在，需完全一致，否则停止。

## 失败触发器

以下情况都视为 FAIL，不允许以“学校模板没指定”来绕过：①问题和措施混在一段；②只列问题；③编号断裂/跳号/重复；④整改项数量与问题项不等；⑤将四份样本中的真实问题挪来当当前项目结论；⑥单条内容空泛或全栏少于200字；⑦以缩字/改模板的方式硬塞超过四对。

通过自动结构检查仍不能证明技术措施准确。AI 必须做“问题i→措施i→验证i”的语义核对，逐条向执行汇报说明是否存在证据空白。
