# <项目名称>｜工程实施方案

> 版本：V1.0  
> 方案状态：拟实施 / 基于既有技术资料 / 基于静态源码（按实际标注）

## 目录

## 1. 项目范围与设计基线

用户确认功能、设计侧重（成本/性能/功能/均衡，注明用户选择或拟定）、不可妥协的约束、关键假设、运行环境与最小闭环。

### 1.1 方案权衡与技术选型依据

围绕真正影响目标的 2～3 条有实质区别的可实施候选路线，先核对必需功能、预算、最低性能与安全兼容门槛，再简要对比成本（含持续成本）、关键性能、已确认功能完整度、开发维护复杂度；选择**唯一一个最终基线**，写清“偏好如何影响该选择”“舍弃其他路线的哪项优势”“这一决定使后续哪些模块或验收指标不同”。**不要为填模板而制造不存在的备选方案**；只有一个有效候选时说明门槛与同解理由。没有已核实报价或性能数据时用定性等级/待验证，不虚构数值。介绍文档不出现此类评分和价格对比。

## 2. 系统架构与数据流

系统组成、谁产生什么数据、谁处理、谁显示/上传/报警；对双向通信写明双端收发责任。

## 3. 硬件/运行环境选型与资源核算

MCU/传感器/供电/接口/电平；或 CPU/内存/系统版本/进程/端口；附选型依据与硬限制。

## 4. 外设、连接或服务配置

芯片封装已知才写精确 GPIO；LoRa/RS485/DTU 电气连接；Linux 服务/ASR/AI API 必要参数。

## 5. 软件/固件模块架构

目录、模块职责、输入输出、真实数据/模拟数据、公共驱动/服务接口。

## 6. 核心功能实现

逐功能写算法/状态机/定时/按键/交互/TTS/音乐等适用逻辑，说明输入/输出/异常。

## 7. 通信协议与数据结构

发送端、接收端、帧边界、字段/单位、合法样例、无效值与超时、校验/确认；API/WS 则用请求与事件契约。

## 8. 调度、状态管理与可靠性

裸机 Tick 或 RTOS/服务周期；错误、掉线、旧数据、并发、重连或故障降级；只覆盖影响真实需求者。

## 9. 分阶段开发实施步骤

每阶段：先决条件 → 操作 → 可观察结果 → 验收门槛。不要写虚假的实际完成状态。

## 10. 测试验收与排障

正常、异常、断线、错误帧、恢复、必要性能验证；区分计划、Mock 与实测证据。

## 11. 技术依据

仅列真实查核过且与工程实现直接相关的来源；未知不捏造链接。
