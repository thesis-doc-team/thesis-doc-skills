# 选题信息混合输入与动态路由（入口仅内部使用）

## 目标

本 Skill 的“专业探索 / 技术关键词选题 / 已有项目方案”是三类**内部信息来源**，而不是互斥的信息收集表格。允许同时提供专业、STM32/语言/算法、行业兴趣、项目想法、实物条件与设计偏好。**全部有效条件一起参与推荐与设计，不得只命中关键词就丢掉专业/实物约束。**

## 首次触发

- 只有“使用 project-solution-write”：直接问“你想找什么方向的毕设/课程设计题目？专业、技术偏好、已有的开发板或传感器都可以告诉我。”不要问“你选哪种入口”，入口只在内部路由用。
- 只有专业：进入专业探索，**先发散真实不同的项目领域与候选方向**，不给用户预设 STM32；随后生成符合条件的候选项目。专业必填、其他信息非必填。
- 只有技术关键词（如 STM32、Qt、AI、管理系统），或“专业 + 技术”：进入技术选题，围绕所有输入做候选；识别“学过”与“必须使用”的区别。
- 已有题目想法：若用户明确要求直接规划，走正式方案的题目/功能门禁；若用户仍在比较几个想法、要求推荐或探索，则进入推荐，**不得强迫正式立项**。
- 已有项目题目和功能、且要求写方案：直接走原有正式设计；不额外推送候选。
- 任何模式都允许后来增加信息、退回方向探索、换技术路线；不得无故丢弃用户此前已确认的限制。

## 语义分类与门槛

| 用户措辞 | 识别 | 操作 |
|---|---|---|
| “我学过 STM32” | 能力信息 | 可优先该领域，但不是强制 |
| “必须用 STM32” | 硬约束 | 排除纯软件项目作为最终方案 |
| “最好用 STM32” | 偏好 | 可展示替代路线并解释取舍 |
| “我想做某种……但是还没想好” | 项目意向 | 可围绕想法做候选、补功能，不能自动 confirmed |
| “我就选 PROJECT-0002，确定名称和功能” | 明确确认 | 状态先 interested 后 confirmed，再正式方案 |

推荐阶段**不要求已有项目题目和功能清单**，用户只给专业就应有可用结果。正式方案阶段仍严格执行旧的题目与功能门禁；不能因为用户仅有专业，就把某候选当作已确认项目。

## 毕设/课程设计选题专向边界

本 Skill 主要服务于**毕业设计 / 课程设计**场景，候选题目必须满足以下硬性偏好（不可擅加经费/工期等评审式问项；均通过 constraints 表达）：

1. **功能必须多且闭环**：每个候选核心功能至少 7 条；具体数量由题目发散研究决定（通常 8–12 条，最多 15 条）；每条描述一个完整的触发→行为→可观察闭环（如“检测到重量低于阈值时蜂鸣器鸣叫并状态页标记缺货，按消音键后静音”），不是只写“重量监测”。
2. **有具体场景**：overview 必须包含至少一个具体的服务场所或用户类型（如“温室大棚”“宿舍楼道”“实验室货架”“家庭厨房”）；不能只有“环境监测系统”而不说在哪儿用。
3. **模块化组件、单板小规模**：默认使用市面上可购的传感/通信模块；**不要求用户自绘 PCB、手工焊接、设计数模电路**；所有验证应在单板或小装置上可独立完成，不依赖实验室大型设备、多点架设或服务器集群。
4. **禁止假大空**：不得出现“大规模部署”“全自动生产线”“城市级”“完全覆盖”“首创”“世界一流”等无具体工程依据的修饰；不得把候选写成“智慧城市治理平台”等超纲项目。
5. **技术边界**：区分“学过”与“必须用”；若用户已有开发板/传感器/实验室设备，优先按既有条件筛选；未声明的设备和能力不作默认假设。
6. **不把编制工期、经费、难度作为推荐输出字段**；只通过 constraints 表达“不超过一块板、不涉及数模自研、限购现成模块”。`profile.json` 不接受 `budget`/`timeframe` 字段。
7. **题目向上泛化**：题目写成“应用场景 + 核心能力”（如“面向温室大棚的环境监测与预警系统”），不要把单一作物/病害/算法/型号写进题目（如“番茄叶片病斑识别系统”“基于 YOLO 的…”），也不要把题目泛成“智慧农业平台”。具体对象、算法、型号放在 overview/功能/场景里；题目过长（>45 字）先压缩再推荐。

**功能发散研究法**（每个候选都先做一轮，再落库）：按“用户 / 场景 / 对象 / 物理量 / 交互 / 告警 / 通信 / 配置 / 异常 / 数据”十个维度列候选功能 → 合并同类、剔除超出单板/模块边界或不可验证的项 → 保留 7–15 条完整闭环功能，并至少覆盖采集、显示、告警、通信、配置、异常、统计中的 4 类。不要用 7 条同类“采集 X”凑数；也不要为了数量硬加与场景无关的功能。

候选生成后应运行 `scripts/validate_discovery.py --batch-file ... --purpose graduation_capstone` 做静态选题 QA；发现问题先修候选再落盘。

## 交互节奏

主动推理并给用户 3～6 个不同方向的文本概览，然后根据用户意愿生成该轮候选资产；如果用户直接要求推荐就不必强制多一轮探索。每轮候选 ≤ 10；没有必要达到上限。模块偏好、规模边界与资源信息只在筛选/内部资产中使用，不塞入候选正文为“推荐理由”。重大冲突一次聚焦询问；其它设计由 Agent 自己负责。

## 信息遗忘防护

启动新一轮之前先读 `<WORKSPACE>/discovery/profile.json`、`catalog.json`、`rejected-projects.json` 和 `history.jsonl`，合并当前消息的更新；优先最新的用户明确修订。不得把多次回话的猜测写成 confirmed。用户若要求不记个人条件，应仅保存项目必要约束，不永久保存个人敏感资料。
