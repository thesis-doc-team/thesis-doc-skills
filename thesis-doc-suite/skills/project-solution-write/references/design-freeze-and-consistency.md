# 设计冻结与跨文档一致性（写正文前的防线）

## 一、问题来源

静态校验一次 PASS，并不等于方案内部一致。一次实际复盘中，草稿在自动检查通过后仍出现连锁修改：页面数量在两份文档与需求/决策资产中不一致；同一字段在结构体里是 16 位、在协议里是 32 位；无效数据示例的总体状态与刚定义的状态优先级矛盾；Flash 双槽配置漏了链接脚本保留区和 CRC 序列化范围；上传状态机没有区分“写入 DMA 缓冲”和“DMA 发送完成”；按键短按与长按之间存在未定义死区；服务端对 QoS 1 重复消息刷新在线时间，可能掩盖离线。

根因不是文笔，而是**跨文档不变量没有先冻结**：写正文时边写边定，任何一处改动都会牵动另一份文档、协议、状态表或测试编号。本文件把“先冻结、再动笔”固化为写前门禁。

## 二、冻结时机与位置

- 完成 `requirements-matrix.md`、`decisions.md` 之后，写 `draft-introduction.md` 之前。
- 在 WORKDIR 生成 `design-freeze.md`（模板：`../templates/design-freeze.md`）。
- 冻结表是内部草稿，不进入 `deliverables/`，不作为第三份交付物；`cleanup` 时随本轮运行区删除。
- 冻结表不是对用户的额外问询；未确认项在表中标 `待实物/待现场确认`，不得标成已确认。

## 三、八类必须冻结的不变量

1. **术语与默认值**：项目全称、简称、六个功能名、状态名、默认周期、示例值；说明哪些是 `confirmed`、哪些是 `proposed`。两份文档与需求/决策资产只使用这一套名称和值。
2. **页面/交互映射**：页数、页 ID、页名、每页显示字段、该页可用的按键动作；介绍文档的页面表与实施文档的页面表必须逐项对应。
3. **数据结构与配置布局**：结构体字段名/类型/宽度、Flash 槽地址/页大小、记录长度、CRC 覆盖范围、链接脚本保留区、写入与回读顺序。字段宽度必须与协议字段和数据库列一致。
4. **协议契约**：物理通道、帧边界、字段名/类型/单位/范围、null/无效语义、超时/重试、去重键、送达证据层级；发送端字段与接收端解析必须能逐项对上。
5. **状态枚举与优先级**：系统/货位/上传/报警状态集合、优先级顺序、到显示与协议的映射；不得在不同章节出现不同枚举或不同优先级。
6. **资源与接口**：MCU/外设/引脚/方向/电平/模块端子，或 Linux 服务/端口/进程；供电预算、保留调试口、DMA/中断/缓冲归属。未确认项标条件，不伪造“最终引脚”。
7. **失败分支与边界**：断网、断传感器、超载、配置损坏、掉电、重复消息、按键死区、页面切换；每个分支的判定、显示/报警、上传/记录、恢复条件必须唯一。
8. **需求/测试/验收追溯**：`REQ-ID → 验收场景 → 测试编号 → 证据方式 → 实施章节`；测试编号与场景编号不得混用，模拟与实测分开。

## 四、冻结后的写作纪律

- 两份草稿的跨文档引用只能来自冻结表中的唯一来源；介绍文档不展开实施细节，实施文档不引入介绍未覆盖的用户可见行为。
- 冻结后任何一项改动，必须先在冻结表的“变更记录”登记（变更项/原因/影响章节），再**一次性**改完所有受影响章节，最后重跑 `validate_docs.py` 并做人工一致性复核。
- 禁止“先改一处、看到下一处再改”的边写边定；这会把审查变成连锁返工。
- 静态校验 PASS 只代表格式、边界与需求名称覆盖通过；不代表协议、电气、配置布局或状态优先级正确。

## 五、一次性复核对单（按顺序，不跳步）

1. 双文档术语、页数、默认值、状态名一致。
2. 协议双端：发送字段与接收解析、null/无效、超时/重试/去重一致。
3. 配置与资源：Flash 地址/长度/CRC/链接区、引脚/电平/供电预算一致。
4. 失败分支：断网、断传感器、超载、配置损坏、掉电、重复消息、按键死区逐项覆盖。
5. 需求覆盖：每个 `confirmed` 功能在介绍与实施均可追踪，测试编号能回到 `REQ-ID`。
6. 边界：无禁章、无收费/交付、无后续扩展建议；介绍无实施泄漏。
7. 证据状态：拟实施、模拟、实测分开；不把测试计划写成通过结果。
8. 冻结表与草稿同步：没有“文档已改、冻结表未改”的漂移。

## 六、通过标准

- 八类不变量均有值或明确标注“待实物/待现场确认”，没有空项。
- 两份草稿的所有跨文档引用都能在冻结表中找到唯一来源。
- 冻结后的变更记录完整，`validate_docs.py` 与人工复核均已通过。
- 任何一项不满足，不进入成品发布；先修冻结表，再改文档。
