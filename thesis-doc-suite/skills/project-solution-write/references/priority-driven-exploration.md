# 设计侧重驱动的方案探索与决策追踪（V1.2）

本文件是 **Agent 内部推理规则**，不是第三份正式交付文档。只用于根据用户选定方向，在满足所有已确认功能和硬约束后，找出最合适的技术实施路线。

## 1. 首次对话的唯一选择

- 若本项目之前没有确定偏好，按 `templates/priority-choice.md` 一次性询问成本/性能/功能/均衡四选一。若已有答案，不重复提问；用户要求立即生成时采用 `balanced/proposed`。
- 可允许用户自然语言表达，例如“能省就省”→成本优先，“识别要快且准”→性能优先，“所有交互都要好用”→功能优先；由 Agent 记录来源，不要求输入标准英文枚举。
- 已有明确预算上限属于硬约束，不自动等价于成本优先；设备必须满足关键延迟也不等价于性能优先。无法推断偏好则问一次。
- 除非功能含义根本不同，不继续追问接口、按键、芯片型号或评分权重。

## 2. 用项目实际需求定义偏好，而不是套用口号

| 方向 | 对同一个项目真正需要探索的问题 | 可验证的取舍点 |
|---|---|---|
| 成本优先 | 哪些元件、授权、流量、能耗、开发与维护开销属于必要成本？成熟模块能否替代自研？ | BOM、持续费用、开发调试投入；必需功能和最低可靠性不变 |
| 性能优先 | 性能瓶颈究竟是准确率、响应延迟、丢帧、通信可靠性、功耗，还是系统启动与恢复时间？ | 选 1～3 个有单位或可操作测法的核心指标；不把高端器件直接视为高性能 |
| 功能优先 | 已确认每项功能的正常、失败、交互、恢复流程是否完整？互相冲突怎么办？ | REQ-ID 覆盖与端到端场景；**不增加新功能** |
| 均衡方案 | 哪条路线满足全部硬条件，同时减少多余规格、费用、维护负担和实施风险？ | 关键性能余量、成本区间、功能完整度、可实现性 |

## 3. 有实际差异的候选，而不是堆砌

1. **确定硬门槛**：已确认用户功能、现有器件/固件兼容、电气安全、法律/频段、预算上限、必须性能、部署环境。先剔除明确不合格者。
2. **识别主矛盾**：例如通信成本 vs 丢包恢复、语音响应 vs 本地算力、低价粉尘模块 vs 可验证精度。围绕主矛盾挑选候选，而非列举所有器件。
3. **生成 2～3 条可执行路线**：各候选应至少在关键硬件/通信/服务/算法/复杂度中的一项有实质区别；不能把更换相同规格的品牌当成不同路线。
4. **逐项建立事实来源**：数据手册、供应商可核实价源、实际负载或项目既有证据。未知则标 `unknown/conditional`，并写验证方法。
5. **分方向做反事实检验**：若把当前侧重改为另一类，哪一项主要决策最可能改变？若没有明显变化，记录“同解”及原因，不强行改变方案。
6. **选择并落地**：明确最终一条路线；被弃方案的突出优势、最终路线承担的代价，均应写明。后续资源表、模块、通信、里程碑和验收均引用同一选定路线。

## 4. 一条决策可追溯链（内部模板字段）

| 字段 | 应填写内容 |
|---|---|
| `decision_id` | DEC-xxx（稳定 ID） |
| `requirement_refs` | REQ-xxx（一个或多个） |
| `hard_gates` | 本决策必须符合的功能、安全/电源/预算/最低性能限制 |
| `objective` | 主目标 + 可选次目标、确认来源 |
| `alternatives` | A/B/C 的可实施差异及来源状态 |
| `selected` | 明确选定的基线 |
| `reason` | 为什么更符合主目标而非仅凭感觉 |
| `sacrifice` | 放弃的好处、付出的成本/性能/开发代价 |
| `impact` | 后续硬件/协议/软件/实施阶段究竟如何不同 |
| `verification` | 怎样测量关键指标或核实关键假设 |

**最重要的核查问题**：把“成本优先”替换为“性能优先”后，若技术决策、指标和阶段验收全部一模一样，却没有论证同解，说明 Agent 没有真正响应用户选择。

## 5. 跨领域的轻量对照（只示范决策方法，不移植器件或功能）

### LoRa 环境节点（仅示意）

- 成本导向：评估成熟串口透传模块、既有主控与少量驱动；验收是全部既定传感数据完整收发与总成本核算。
- 性能导向：如果用户的关键指标是传输可靠性，则探索帧序号、确认策略与缓存资源是否合理；不能未经需求论证便宣称必须使用更贵的芯片。
- 功能导向：对已有“本地数据页/远端数据页/告警”逐项检查失效显示与离线行为，不新增云平台。

### Linux 智能交互设备（仅示意）

- 成本导向：比较复用现有主机、云服务费用和音频设备需求；不为省钱删除既定语音功能。
- 性能导向：选声学响应/问答时延/首屏启动等真实瓶颈并设计测法，不能把更贵 AI API 当作已被测证实更快。
- 功能导向：保证已确认的唤醒、连续追问、退出、播放、暂停、天气等闭环与异常互不干扰；不擅自增加摄像头。

以上都是**生成方案的方法示例**，不能当作当前项目现有硬件或实际测试证据。

## 6. 文档呈现边界

- 《项目介绍与功能说明》只展示最终项目给用户的功能和体验，不展示加权矩阵、竞品报价或优先级选项。
- 《工程实施方案》选型章节按需要提供**简洁**的关键候选对照表、明确选择理由、主要代价和实施影响；不额外增加“方案改进建议”“交付说明”或其他元内容。
- 运行区矩阵/完整追踪记录不是成品，按项目资产规则处理；用户仅要求一份文档时也遵守对应边界。
