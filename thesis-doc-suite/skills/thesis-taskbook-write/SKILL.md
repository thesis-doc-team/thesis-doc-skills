# thesis-taskbook-write｜从真实技术资料编写毕业设计任务书

## 0. 任务边界（先读）

**唯一文书主交付：使用官方空白模板原位填充的 `<课题简称>-毕业设计任务书.docx`。**

**新增跨 Skill 共享契约**：`<PROJECT_ROOT>/project-assets/` 是项目**长期资产**（参考文献、统一周计划、技术事实、使用记录），不是文书交付物、更不是中间文件。其他 Skill（如开题报告、中期检查 Skill）可读取同一套项目资产；本 Skill 不代替它们写文书。详见 `references/shared-project-assets-contract.md`。

本 Skill 不是 `proposal-write`（开题报告）、`project-technical-doc`（项目技术文档）、学位论文撰写、系统开发、参考文献综述或 HTML 展示工具。**用户有时会在一句话里误说“开题报告”，若同时明确说“只编写任务书”且上传任务书模板，以后者为准。**如用户明确改变交付类型，再切换到相应 Skill，不能偷换官方模板。

```
用户本次指定的技术资料/技术 MD（真实事实）
                       │
用户指定的官方任务书 DOCX（版式及固定文字的权威来源）
                       │
                只读盘点与模板结构识别
                       │
              提取技术事实与任务化映射
                       │
          优先读取 project-assets/ 已核验参考文献、共享周计划、技术事实
                       │
         缺的才补：有来源地查证论文 / 补充事实 / 更新周计划
                       │
          文书特有内容撰写 + 引用 ID 选择 + 教师意见拟稿
                       │
         原官方模板副本：只写可填区域，不重画框架
                       │
              OOXML 结构审计 + 逐页渲染复核
                       │
                 任务书 DOCX + 执行汇报
                       │
       登记共享资产使用关系 → 清理本轮中间文件（成功/失败）
```

**不得：**
- 以 Markdown/PDF/HTML 重新造一个“视觉相近”的任务书，或重画 Word 表格；不能把原始技术文档的结构硬塞进任务书。
- 在任务书中另起“研究背景综述”“技术细节”“系统架构”“已知问题与改进建议”“未来规划”等官方模板不存在的独立栏目。
- 写与项目无关的技术功能、编造数据/成绩/文献、假装导师已签字、假装使用 WPS 实际检查过。
- 强迫填充后的任务书保持官方空白模板相同页数，或为了少几页删减关键内容、缩小字号/行距/页边距。
- 修改原官方模板文件；永远从**复制副本**写出新文件，保留原文件备查。

## 0.1 项目级共享资产与中间文件（强制执行）

1. **先识别项目，不先生成文书**：明确本项目根目录及唯一 `project_id`。若 `project-assets/` 已存在，先读取 `project.json`、`facts.json`、`references.json`、`schedule.json`；`progress.json` 如存在也需识别并保护，但不得用它替代任务书的拟定周计划。如果 project_id 不符，必须拒绝混用；如果不存在，才创建空资产库。**任何项目特定资产都不可保存在 Skill 安装目录。**
2. **先复用，后补充**：已核验且与当前课题相关的论文直接按稳定 `REF-xxx` 引用；项目级周计划已有基线则直接提取或做文体措辞调整；技术事实以有出处的 `FACT-xxx` 为共同依据。禁止每份文书重搜并重写同一批来源。缺少、失效或与当前课题不符时才增补/更新。
3. **共享资产不是不可更改的死文档**：需要更新已有引用元数据、周计划或技术事实时，提供实际证据和变更原因，显式执行更新，记入 `activity.jsonl`；不允许后生成的开题报告/任务书悄悄覆盖前一个 Skill 的结论。周计划 `draft` 是建议稿；`confirmed` 仅在用户/正式安排实际确认后使用。
4. **稳定 ID 与文书编号分离**：项目文献 `REF-001` 跨任务书/开题报告保持不变；任务书的 `[1]...` 只在本次按所选 ID 重新排序。每份文书独立判断选用是否相关、出处是否足够、引用数量是否符合学校要求。
5. **中间文件必须删除**：渲染 PNG/PDF、临时 DOCX、文献导入草稿、结构审计 JSON、生成输入 JSON 等仅位于 `.skill-tmp/thesis-taskbook-write/<run-id>/`，成功或失败终止时，在保留最终成品/共享资产/必要失败摘要后删除本轮目录。**绝不清理用户原始资料、官方模板、共享资产和最终文件，也不对不属于本 Skill 的目录执行删除**。
6. **项目目录与接口规范**：详见 `references/shared-project-assets-contract.md`，清理安全规则见 `references/intermediate-cleanup-policy.md`。以上契约供之后其他 Skill 独立复用，当前仅实施任务书。

## 0.2 项目资产包（bundle）布局与成品版本意识（-vN）

一个项目 = 一个资产包目录，按项目分类、整包可迁移：

```text
<PROJECT_ROOT>/
├─ project-assets/    # 数据层：project/facts/references/schedule/activity，跨全部文书 Skill 共用
├─ deliverables/      # 成品层：taskbook/ technical-document/ opening-report/ midterm/，每类文书一个子目录
└─ .skill-tmp/        # 运行层：各 Skill 自己的 <run-id> 目录，用完即清理
```

- **版本意识**：成品文件名自带版本号（如 `<课题简称>-毕业设计任务书-vN.docx`）。重新生成时新建 `-v2`、`-v3`…，**永不覆盖、永不删除历史版本**。
- 每个版本验收后**单独** `record-use`（不同路径、不同 sha256），`activity.jsonl` 即项目成品的变更史。
- 历史 `-vN` 版本与共享资产、用户资料、官方模板原件一样属于永不删除项；`.skill-tmp` 清理只针对本轮自己的运行目录。
- **最终版本唯一（每次执行只交付一份最终版本）**：执行内发现缺陷需修复时，修复完成后生成修正版（如 `-v2`），随即将其**改名为本轮应交付的版本名**（如 `-v1`，先删缺陷稿再改名）；一次执行结束时交付目录里本次成品只保留一份最终版，过程稿、缺陷稿不与最终版并存。缺陷稿不是历史版本，按此回收不算违反"永不覆盖、永不删除"；若缺陷稿曾 `record-use` 登记，回收后以最终定名文件 `--replace --reason` 补登记。跨次执行不受影响：内容变更或用户要求重新生成时仍递增产出 `-v2`、`-v3`…并各自登记。

## 0.3 内置匿名范本（新增：逆向复现的材料，不是当前项目事实）

- 首先读 `assets/reference-samples/README.md`，按课题结构选择 SAMPLE-A～D 的**匿名 DOCX** 观察写作及 Word 段落的共同点；使用 `references/anonymized-sample-text.md` 复现文字节奏，用 `references/sample-style-audit.json` 核对已测量的首行缩进/行距差异。
- 不得从匿名范本继承人物、年份、项目标题、功能技术、进度日期、导师意见结论、示意文献。范本是风格样本，不是新项目资料，也不能写入 `project-assets/`。
- 采用“共性优先，差异有理据”的裁决，固定框架只听官方空白 DOCX；参考文献只来自实际检索或当前项目核验资产。若范本原有不合格做法（如漏写导师意见、未核验或重复文献），只作负例。
- 四份样本 DOCX 已清理个人信息和隐藏元数据；新增或更新样本时必须先去标识化、扫描包内 XML、渲染逐页检查并更新 SHA-256，禁止直接将用户原件入包。

## 1. 证据与规则优先级

1. **用户本轮明确要求**（包含先前反馈中仍有效的约束）决定交付对象和填写偏好。
2. **本轮官方空白任务书 DOCX** 决定物理结构、固定栏目、字号/行距/合并关系/签名/附注；如标签存在不一致，保留原样，不私自改字。
3. **本轮指定技术 MD / 技术手册 / 可读源码** 决定功能、模块、应用场景和状态；从样本文本提炼**写法**，不继承样本事实。
4. **同项目已登记的共享资产**可复用已核验文献元数据、项目计划和带证据的技术事实；这些资产并不取代本轮技术资料真实性核对和官方模板规范。若与本轮证据冲突，停止自动复用并记录冲突。
5. 已填写范本只提供**表达习惯、篇幅节奏、任务化写法和进度安排方式**。存在分歧时先看官方约束，官方未规定时求同存异，结合多数与合理性；不继承已填范本的个人信息、参考文献或错误。
6. AI 的一般知识只辅助组织，不可冒充项目实现证据。确实拿不准且会实质影响论文任务、官方合规或时间时，请用户决定；无关紧要的风格差异可自主判断并汇报。

阅读：`references/template-boundary-and-layout.md`、`references/genre-reverse-engineering.md`、`references/technical-input-and-writing.md`，并按需阅读匿名范本文字镜像及样式审计。

## 2. 用户输入与缺失处理

必要输入：①技术资料或技术 MD；②官方 `.docx` 模板（本包内备有本次官方模板**原样只读副本**）；③当前课题题目（可从真实资料拟稿，但需在汇报里标明）；④当前项目根目录（用以定位同项目的持久资产）。可选：多篇已填任务书范本、院系/班级/姓名/学号/导师/职称、起止日期、专业/当届工作安排、已核验的参考文献。

**空缺信息策略：**
- 姓名、班级、学号、导师、职称、学院若未明确给出，留空，不套用别人的个人信息；“学院”也不默认继承已填样本。
- 日期应根据**本轮明确提供的时间**填写。历史参考范本里的 `2024—2025（共 30 周）` 只是旧样本，**不能作为未来项目的默认日期**。
- 若仅得知“30 周”，但无起始日期，保留官方日期占位并列出待填写；进度可以先按第 1 至 30 周拟排。
- 签名和真实签署日期必须留空；任务下达人意见是**拟稿**，最终需要指导教师审核。
- 任务接受人意见默认留白；只有用户明确要求或提供原文才填写。

用户给出新的任务书官方模板时，**以新文件为权威**。先运行 `scripts/inspect_template.py`，对照既有 9×4 框架；若结构不同，本包硬编码填充脚本应拒绝，不可绕过校验强灌。需基于新模板做新的**只填位置映射**，并更新验证器；不得动新模板固定框架。

## 3. 正式执行流程（必须从头至尾）

### 分批写入与一次终检（硬性，禁止一次性整篇生成）

- **分栏分批起草**：任务书草稿内容分批写入本轮工作区草稿文件——①`thesis_content`（研究对象与场景段 → 核心任务条目 → 调试验证收束段）至少分 2～3 批；②`issuer_opinion` 单独一批；③进度与文献选用清单各自一批。一批落盘后再写下一批，**禁止一次性倾倒全部栏目**。
- **一次成型**：全部栏目草稿落盘后才执行 `compose` 汇总与 `fill_taskbook.py` 一次性填入模板；随后 G 双重检验即**唯一终检**，写作过程中不反复全文重查。终检问题只定点修可填区内容后重新填充复检，不推倒全部草稿。
- 执行汇报注明分几批写入、每批栏目与一次终检的结论。

### 运行前｜建立隔离工作目录、读取共享资产

- 使用 `scripts/project_assets.py init` 初始化资产库（已有则不覆盖），或使用 `status` 检查。`project_id` 必须由当次项目身份确定，不从示例课题、其他模板自动套用。
- 使用 `workdir --root <PROJECT_ROOT>` 建立**当前运行唯一**的 `.skill-tmp/thesis-taskbook-write/<run-id>/`；本次构建材料和视觉渲染均放在此处。
- 读取 `references.json`、`schedule.json`、`facts.json`。先列出可复用的记录和缺项；再按本次项目与模板决定需新增的论文、任务与周计划。**不要无条件重建已有资产。**

### A｜先锁定模板，再逆向写作范式

- 识别官方 Word 的**页面及段落属性**、表格 grid、合并单元格、行高规则、书签/域/页码、固定栏目、附注及可填区域。**填充前先校验 `assets/template-lock.json` 的官方模板 SHA-256**；模板文件更新时须重新审计且修订填充坐标，不能只靠相同 9×4 行列数。
- 记录 `SHA-256`，并把官方原件单独保护；尤其检查相同视觉标签是否实为一张合并表格。
- 如本轮有多份填好的范本，把可迁移特征划为：固定格式 / 常用文字结构 / 可变项目量 / 模板之间非一致的地方；凡范本与官方冲突，以官方为准。
- 不把旧课题名称、专业、时间、导师、硬件型号或旧参考文献写入本次任务。

### B｜对技术文档进行“任务化”改写

先做内部证据提取：**对象与场景 → 解决问题 → 项目总体目标 → 要求实现的功能 → 关键技术及模块 → 验收/测试任务 → 不确定事项**。

把技术报告中的“系统已经怎样做”转化为任务书中“要求完成哪些设计、开发、调试和验证”。表达应能让教师理解工作量，**形似参考范本的叙事与条目方式**，但绝不机械套项目内容或不相干的实现细节。

毕业论文（设计）内容建议遵循：

> 研究/设计对象与应用场景（1 段） → 总体方案与技术载体（1 段） → 3—7 个核心任务（按项目适配） → 系统调试、验证及交付要求（收束）

不是必须 3—7 条，用户/官方范本若有更合理写法可以使用。**技术充实优先于篇幅一致**，不为固定页数压缩。

### C｜工作进度（以周为单位）

**先读取共享 `schedule.json` 项目级基线**：已覆盖当前要求且未与新资料冲突时，直接复用阶段范围与实质任务；根据任务书需要可压缩/展开语言，但不得私改基线。若尚无计划，根据当前课题真实安排提出 `draft` 基线并写入共享目录；若用户已明确确认过计划，依据该证据标注 `confirmed`。后续开题报告优先使用同一基线，不需要从头设计周计划。

按任务关联的真实工作安排：调研/综述 → 开题准备 → 架构与技术准备 → 模块开发与系统集成 → 调试/验证 → 论文写作/修改/答辩。可合并阶段，不机械照搬硬件项目或 Web 项目的阶段。周次**从 1 连续覆盖到总周数、不重叠、不缺失**；若指导教师另有计划，以真实安排为准。

### D｜参考文献真实检索与共享复用（硬门槛）

- **先查 `project-assets/references.json`，不要重新抄写已查证的文献**。只选与本任务书相关的真实文献（以 `REF-xxx` 稳定 ID 选择），正文按本次选用顺序生成 `[1]` ～ `[N]`；后续开题报告亦可选择同一个 ID 的不同子集。
- 需要新文献时正常检索、核实、去重，**先写入共享库并记录来源证据，再在本份任务书中引用**。发现条目错误或新文献版本，需要有理由地显式变更，不能直接覆盖旧条目；文献仅保存在本项目库，不保存到 Skill 自带参考范文中。
- 原模板：**“主要参考文献：（不少于10篇）”**。原则上搜集**至少 10 条正式、真实、相关且可追溯的学术文献**，并按 `references/citation-policy.md` 记录检索地址、核验状态和元数据。
- **中文文献占比 ≥60%（硬性）**：本次选用文献中中文文献（以**正式发表的正文主要语言**判定：中文期刊论文、国内学位论文、中文专著/标准；中文译本按原著语种计）≥60%（10 篇至少 6 篇）。检索期就按**约 65% 收**（留余量：终检剔除未核验/重复条目后重新点数仍不得跌破 60%）：中文库（知网/万方/维普/国内学位论文库）先检索成池，再以外文补前沿与国外对照；执行汇报写"中文 X / 总 Y = Z%"。中文池确实稀缺时（检索留痕：库/检索词/命中量）**不为凑比例伪造中文文献、也不静默降比例**，如实向用户报告并请其决定。
- 优先：中国知网（CNKI）、万方、维普，及出版商/学协会/高校学位论文库、Crossref/DOI 等；CSDN、开发者博客、官方技术文档**允许作技术补充来源**，但必须标示其为网页/技术资料，**不得伪装成期刊论文**，且不宜以大量博客代替正式论文。
- **禁止依靠语言模型记忆凭空拼接作者、论文名、卷期、页码、DOI**。若无法访问来源，`verified=false`，不得写成“已核实”；需继续检索或在执行汇报列为未完成门禁。不能把旧范本的参考文献复制进新课题。
- 可用真实文献标题、作者、出版年份、期刊名/卷期/页码/DOI 或有价值的记录页面核对；每条保留 `source_url` 和实际核验时间。文内按学校要求或通行 `GB/T 7714` 格式组织；**学校版式优先于任意外部格式化习惯**。

### E｜下达人意见及其他栏目

- 下达人意见至少 50 字，针对当前项目的研究价值、工作内容、可行性与完成要求，**是导师意见拟稿**。
- **教师意见拟稿统一规范（跨文书共用写法）**：意见栏一律是供指导教师审定的拟稿，不代签、不写签署日期、不写“优秀/良好”等等级。五要素逻辑链一段成文（本栏≥50字，一般120～220字收放）：①主体与选题`该生围绕<课题名/技术栈关键词>选题，…`→②能力`能够查阅并整理<领域1、领域2>等相关文献，对国内外研究现状有较为系统的把握；`→③文书质量`任务书结构完整、条理清晰，引用文献真实可查，写作规范；`→④针对性`任务内容涵盖<具体模块1>、<具体模块2>，进度与验证节点明确，工作量适当；`（必须来自本次实际写出的内容）→⑤收束`同意下达任务书并按计划开展课题工作。`（**不加"最终评价以指导教师审定为准。"等元话语尾巴——画蛇添足**）红线：不夸大、不虚报、不只替换项目名照搬范本句式。意见正文到收束句为止，不写拟稿声明/审定声明等元话语（fill/validate 对 `本栏为拟稿`/`供教师审定拟稿`/`供指导教师审定`/`教师审定为准` 报错，“审定结果为准”等插字变体同拦——**禁语以意图为准：正确处置是删尾巴收于实质句，不得插字绕过**），拟稿属性由执行报告与签字留空体现。
- 按官方固定位置填充；接受人意见、签名及签署日期按第 2 节默认留白，未经用户授权不填。
- 明显不属于当前项目或用户未确认的结论不写入正文，不新增“问题与改进”等独立章节。

### F｜在原 DOCX 框架中填写

1. 先根据 `templates/shared-asset-input-examples.md` 在本轮临时目录撰写任务书特有草稿（`title/thesis_content/issuer_opinion/selected_reference_ids`）。通过 `scripts/project_assets.py compose` **从共享资产生成本轮临时 taskbook-input.json**；验证文献不少于 10 篇、已核验，周次无重无缺。不把本轮临时 JSON 作为永久项目资产。
2. 用 `assets/official-taskbook-template.docx` 的**复制副本**（或用户当前指定的同结构模板）填入正文，不能新建 `Document()` 仿制。
3. 任何最终输出的 `-vN` 路径若已存在必须拒绝覆盖，新版本另起文件名。填写字段不改变固定标签、页面尺寸/边距、表格 `tblGrid`、`tblPr`、各行 `trPr`、单元格合并/边框/内边距 `tcPr`、表格外附注与签名语句。
4. 只允许在**可填区域**增减普通正文段落、文字和合理的换行。大段正文自然跨页；不为了“模板原有 3 页”压缩到 3 页。
5. 首页**每个可见单元格**（不按被合并的底层网格）检查水平、垂直居中；消除可填文本的段落多余空段、缩进及制表位影响，不靠空格制造“假居中”。原有标签居中不改变。真实项目题目超长、固定行高裁切时**报告冲突并按用户确认处理**，不能擅自缩放行高/字号/列宽。
6. 正文按官方附注：**五号宋体、1.5 倍行距；英文和罗马字符 Times New Roman 正体**；官方自带的标题/标签若与正文有局部样式差异，保留其原样，不做全局统一。
7. 本包脚本中的 `fill_taskbook.py` 实现该版本模板的**限定位置写入**；它不负责根据技术 MD 自动生成语义内容，AI 必须先理解资料并填入真实 JSON 数据，再调用。绝不拿演示输入当正式事实。

**自然分页与视觉质量门禁：** 页数只是内容自然排布的结果，**不得对照官方空白模板的3页基准设置上限，也不得以“未经授权超过基准页数”为 FAIL**。无论 2、3、4 页或更多，只需检查实际文字是否完整、页码/栏目是否连续、是否存在**相较官方原件新增**的异常整页空白或孤立签名、边框/表格是否破裂。官方原件可能将第 4 条附注独立置于末页，不能把这种原样继承的现象误判成必须压缩正文的错误。若异常：只在可填正文范围内调整多余空段和合理措辞/段落，不删核心任务、不压缩字体行距/页边距；必要时报告版式限制，由用户决定是否授权改固定结构。`render_visual.py` 只发出可疑孤页提示，不以页数拦截。详见 `references/template-boundary-and-layout.md`。

### G｜双重检验与用户最终验收

- **结构检验**：比对官方副本与交付文件的节属性、表格/网格、行列、每格 `tcPr`、固定标题、表格外附注、签名日期；调用 `scripts/validate_taskbook.py`。
- **事实与文体检验**：核心技术任务齐全、时间进度自洽、文献≥10 条且全部可追溯、下达人意见≥50 字、无旧课题/姓名/功能残留，未把拟开展写成“已测试成功”。
- **截图验证分析（Screenshot Verification Analysis，交付前硬性环节，缺一不可）**：成品先渲染成页面截图、**逐张分析**，才能写“视觉检查通过”、才能登记 record-use。固定三步——
  1. **截图**：用可用 Word 兼容渲染器对**每页**输出 PNG（必要时加 PDF 全览）；截图只放 `.skill-tmp/thesis-taskbook-write/<run-id>/`，不进交付目录。
  2. **逐张分析**（缺一张即未完成）：首页横纵居中（非空格/空段假居中）、文字截断/溢出/重叠、表格断裂/边框错位、参考文献断行、签名/日期及附注、标题孤立、异常空白页、字体替代。
  3. **留痕汇报**：执行汇报固定填写截图引擎/工具、截图张数（=页数）、实看张数、逐张结论 PASS/WARN/FAIL 与问题清单、返工复检次数、WPS 实测边界声明。
  红线：未逐张分析不得宣称排版/视觉验收通过；无法截图时如实报“截图验证分析未完成”；版面问题只改新写入内容解决，绝不改动官方固定版式“修图”；截图是验证手段不是交付物，结论写入执行汇报后随本轮中间文件清理。
- **WPS 实测边界**：用户的实际 WPS 展示是重要反馈；只有真正用 WPS 打开过才能写“WPS 已验证”。若只用 LibreOffice/Word 兼容工具渲染，必须写明“未在 WPS 客户端实测，需用户进一步复核”；绝不谎报。
- **最终验收属于用户**，Agent 交付时直接报告已完成事项、实际检查环境、尚存问题与需补填信息，不要求用户替 AI 做常规检查。

### H｜最终归档与清理（无条件尾步骤）

- 官方模板原件仍只读；最终 DOCX 放到**用户指定交付路径**（未指定可用 `<PROJECT_ROOT>/deliverables/taskbook/<课题简称>-毕业设计任务书-vN.docx`，新版本新文件、不覆盖历史），不会混入 `.skill-tmp/`。
- 写简短执行汇报：复用/新增了多少参考文献，使用的 `REF-ID`，周计划来源/版本，有哪些冲突、新变更、核验缺项，实际做了哪些结构/视觉/WPS 检查。
- 使用 `project_assets.py record-use` 写入**最终文书**采用的引用 ID 和校验值，保留可追溯性；每个 `-vN` 版本单独登记；失败时不记录为成功成品。
- **成功与失败均执行** `project_assets.py cleanup --root ... --run-id ...`；先把必要失败摘要持久化或写进对话，删除本次结构报告、构建 JSON、渲染图片和测试文书。失败清理时不得删除原稿、共享资产或最终文书（含各历史 `-vN` 版本）；若清理未完成，明确汇报残留路径和原因。

参见 `references/quality-gates.md`、`references/intermediate-cleanup-policy.md` 与 `templates/execution-report.md`。

## 4. 一次性执行命令（本地 Codex / Claude Code）

所有命令在安装好的 `thesis-taskbook-write/` 目录内执行。以下环境变量是示意：实际运行时应按当前项目填写正确的项目绝对路径与唯一 ID，**不要直接复制示例 ID 成为真实项目标识**。

```bash
python -m pip install -r requirements.txt

# 1. 共享项目资产：首次初始化，已经存在则不覆盖
python scripts/project_assets.py init --root "$PROJECT_ROOT" --project-id "$PROJECT_ID" --name "$PROJECT_NAME"
python scripts/project_assets.py status --root "$PROJECT_ROOT"

# 2. 单独创建本轮有所有权标记的临时工作目录（记录其输出的运行 ID）
python scripts/project_assets.py workdir --root "$PROJECT_ROOT"
# WORKDIR = 上述命令实际输出的绝对路径，RUN_ID = 最后一级目录名称

# 3. 只读扫描原模板，审计 JSON 放在 WORKDIR
python scripts/inspect_template.py assets/official-taskbook-template.docx --json "$WORKDIR/template-audit.json"

# 4. Agent 先从共享项目资产获取已核验论文与周计划，再补充真实缺项：
# 只在 WORKDIR 中生成需新增的 references/facts/schedule 导入 JSON；
# 分别使用 project_assets.py merge --kind references|facts|schedule；
# 旧条目变更必须 --replace --reason “真实理由”，且记录用户/证据状态。

# 5. 在 WORKDIR 写 taskbook-draft.json（只含本次任务书特有文本及所选文献 ID）
python scripts/project_assets.py compose --root "$PROJECT_ROOT" \
  --draft "$WORKDIR/taskbook-draft.json" --out "$WORKDIR/taskbook-input.json"

# 6. 只修改官方模板副本，产物写到用户指定的 FINAL_DOCX 路径
python scripts/fill_taskbook.py --template assets/official-taskbook-template.docx \
  --data "$WORKDIR/taskbook-input.json" --out "$FINAL_DOCX"
python scripts/validate_taskbook.py --template assets/official-taskbook-template.docx \
  --file "$FINAL_DOCX" --data "$WORKDIR/taskbook-input.json" \
  --report "$WORKDIR/structure-report.json"
python scripts/render_visual.py --file "$FINAL_DOCX" --outdir "$WORKDIR/render"
# Agent 必须打开并逐页查看全部 page-*.png；预检查 JSON 不能代替人工视觉复核

# 7. 使用 `scripts/render_visual.py --file "$FINAL_DOCX" --outdir "$WORKDIR/render"` 生成全部页 PNG，逐张检查并出具执行报告后，才登记真实成品
python scripts/project_assets.py record-use --root "$PROJECT_ROOT" \
  --file "$FINAL_DOCX" --doc-type taskbook --ref-ids REF-001,REF-002

# 8. 成功或失败的最后一步都执行；仅删除本轮临时目录
python scripts/project_assets.py cleanup --root "$PROJECT_ROOT" --run-id "$RUN_ID"
```

这里的 `REF-001,REF-002` 是**命令示意**，实际需要把本次所选文献 ID **全部列出**，而不能只记录两个。运行中应当用 `try/finally` 或等价的 Agent 执行规则确保错误情况下也清理；如果生成失败但最终文件尚未验收合格，不可写成功使用记录。**执行结果只交付最终任务书和必要汇报，临时结构报告/图片/JSON 不保留。**

`fill_taskbook.py` 只负责按现有官方模板的固定栏位填入已准备的结构化内容；`project_assets.py` 负责共享资产读写、组合与安全清理，不替代 AI 的论文检索、内容真实性或 WPS 视觉验收。

## 5. 与 `project-technical-doc` 的接口（只复用事实，不混任务）

- **上游**：`project-technical-doc` 负责项目理解，输出完整且带事实边界的 Markdown 技术文档（可能同时另行输出 HTML）。
- **本 Skill**：只读取其中的**技术事实和状态限定**，转换成任务书要求，并负责文献检索与官方 Word 填写。
- 不需要再次从代码开始重做完整技术文档；如技术 MD 证据不足，仅针对相关事实追溯用户提供的资料。
- **两个 Skill 共同读写的只有 `<PROJECT_ROOT>/project-assets/` 内的标准资产**；上游可以贡献有来源的 `facts.json`，任务书 Skill 可贡献文献与周计划。之后的开题报告 Skill 读取相同稳定 ID，并反馈有依据的更新。共享资产变更必须透明、可追溯，不应由下游擅自改写上游正式技术 MD。
- **不能把上游 HTML 作为任务书版式依据**，也不能让本 Skill 输出额外技术文档或 HTML；避免两个 Skill 互相覆盖目标或合并后角色混乱。
- 可共用“输入盘点 / 事实证据登记 / 执行汇报”框架，但要保持各自的主交付、质量门禁、内容边界独立。

## 6. 异常与失败原则

- 官方模板不是可识别的 9×4 结构：**停止使用固定定位脚本**，先分析新的官方文件并适配映射，不修改其框架。
- 只有图片或 PDF 的模板而无可编辑官方 DOCX：不可冒充“原 DOCX 保真”，说明限制并请求正确底稿（若本包内的已授权官方模板符合本轮要求，可使用内置副本）。
- 参考文献不足/元数据无法查证：不伪造；明确告警，继续真实查找。证据不够时只可交付标注为待完成的草稿，不可声称正式通过。
- 未知日期/人员信息：保留官方留白，执行汇报列示；旧样本的日期不得默认延续。
- 模板文字与用户希望改动的固定栏目发生冲突：先征求用户明确授权，未获授权保留官方原样。
- 兼容渲染正常≠WPS 已实际验收；只报告实际执行过的检查。
- 共享项目不存在：先初始化空目录，不向其他项目借引用或进度；项目 ID 冲突：拒绝合并；已有资产修改：无变更理由不覆盖。
- 运行结束：不管 PASS/WARN/FAIL 都按所有权标记清理本轮临时文件；如果安全检查拒绝删除，报告具体原因，不扩大删除范围。

**终局判断：结构保真、技术事实真实、任务表达有分量、参考文献可验证四者均成立，才算生成质量达标；是否最终采用，以用户审查为准。**
