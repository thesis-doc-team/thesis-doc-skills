# 问题和整改建议逐条匹配规则（强制）

输入推荐使用结构化 `issue_pairs`：每个元素恰好包含 `problem` 和 `action`，可选 `verification`；记录级另有 `topic`/`evidence_note`。**三者均为草稿元数据**：仅作写稿参考，**不写入 DOCX、不是新表格栏目**（Word 无主题栏目，第4行 `指导内容` 是官方固定标题），成品看不到它们属预期、不是内容丢失。

1. 问题包含：明确模块/对象、具体需要解决/验证的事项、造成何种影响（若未实际发生则不要说“已发生”）。
2. 修改建议包含：如何修改、涉及哪个数据/接口/图纸/流程、如何自测/验证。
3. 输出时，先连续列出问题1…N，再列出建议1…N，**编号相同、数量相同、顺序相同**。
4. 每个编号独占 Word 段落，带首行缩进；标签“指导教师指出存在问题：”“指导教师提出修改意见：”也要独立段落，避免压成一行。
5. 禁止空泛句：“认真研究”“继续完善”“多查资料”“提高质量”；必须改成技术动作。
6. 若仅有技术规格、没有实际教师指导/错误证据，写“尚需检查”“建议验证”“需要补充”，不写成“教师现场发现”“某功能失败”。
7. 字数以行高和可用空间为边界；遇到多条问题优先保留高价值2~3组，而非挤爆表格；不缩改官方表格。

## 行数预算（硬几何：内容格行高 265.6pt，hRule=exact，实测约 18~19 行 @10.5pt/1.1 行距）

行高是**固定值**：正文超出不会撑高行，而是被裁切并压盖下一行（真实事故截图）——按估算行数硬拦，**上限 17 行**（留 1~2 行安全余量）。估算：全角 2 单元、半角 1 单元，首行 54 单元、续行 60 单元，逐段累加；`fill_guidance.py` 生成时必拦，`validate_guidance.py` 文档侧复核。

| 组数 | 典型行数（含标签段） | 判定 |
|---|---|---|
| 1 组 | 约 6~7 行 | 宽裕 |
| 2 组 | 约 13~14 行 | 稳（实测 8 次每组恰好一页、零跨页） |
| 3 组 | 约 17~19 行 | 贴上限：压到 17 行内，或精简/分次记录 |
| 4 组 | 常超 17 行 | 大概率超容被裁切：优先压到 2~3 组，或每条压到 1 句（只删冗余措辞，不删问题/建议实质） |

预算与 `references/official-template-layout.md` 的几何同源；超预算先精简/分次，不得缩字号、改行高或改页边距硬塞。

## 具体性三要素（强制，但"具体"≠堆实现细节）

每条问题和修改意见写清三件事，**点到对象与方向即止**：

1. **对象**：哪个模块/链路/参数类别/数据字段/器件（如"串口时钟与波特率配置""温湿度阈值""上报 JSON 字段"），而不是"通信流程""相关参数"这类无对象表述；
2. **动作**：对它做什么（核对/补充/校准/回放/记录）；
3. **可观察结果**：什么现象/口径算通过（误差在容差内、字段齐全、记录可复核），写判定口径即可。

**粒度红线（用户复盘："太细节反而不真实"）：指导记录是教师手写式的概括记录，不是实现手册。**
- **不展开实现细节**：寄存器名与配置链（HSI/PLLMUL/SYSCLK/APB 之类）、引脚电平、时钟分频、波特率数值、逐条指令序列与逐项期望返回、函数名/文件名清单——这些属于技术文档；指导记录只写到"核对时钟配置一致性、按实际时钟核算串口波特率误差并记录超差项"这一层。
- **单条约 30~80 字**（超过 90 字 `validate_guidance.py` 给非阻断提示）；每次记录整体压进行预算（硬上限 17 行，超出必被裁切并压盖下一行）。
- 细节越堆越满，记录越不像真实教师语言，也越容易挤爆官方固定行高。

**禁止清单**（出现在成品正文即视为意义不明）：

- **内部章节/附录引用**："按§5.5""对照§8.1""见附录11.4"——指导记录是独立文书，导师审阅时看不到你的技术文档目录，须改写成独立可懂的概括表述；
- **无内容的元动作**："设计分步检查表""记录返回码""建立对照机制"后面没有具体对象和判据；
- **裸编号引用**：只写"（用例T07）"而不写独立可懂的动作描述；
- **套话**："认真研究""继续完善""多查资料""提高质量"；
- **实现细节倾倒**：寄存器级配置链、逐指令期望返回清单、函数/文件名清单——概括改写或删去，明细留在技术文档。

**反例 → 正例（先例均为实际踩过的两种极端；正例为概括口径）：**

| 反例（过度细节 / 意义不明） | 正例（对象+方向+判定口径） |
|---|---|
| 把 HSI 8 MHz→PLLMUL16→SYSCLK 64 MHz、AHB 64 MHz、APB1 32 MHz、APB2 64 MHz、Flash Latency 2 逐项写入时钟一节的参数表，再逐条打开 usart.c 三个 UART 的 BaudRate 字段与对应 APB 时钟核对（真实事故原句，过长被裁切）。 | 核对系统时钟与外设时钟配置的一致性，把时钟树参数补入参数表，按各串口实际时钟核算波特率误差并记录超差项。 |
| 逐条执行 AT 握手、ATE0 关回显、AT+CMGF=1 切 Text 模式、AT+CMGS+Ctrl+Z 发送，记录每步实际返回（OK/ERROR/超时）…… | 补齐短信发送链路的弱信号与无卡场景验证：模拟信号中断，确认重试与本地告警切换正常，并记录恢复时间。 |
| 按§5.5指令时序设计分步检查表并记录返回码。 | 按发送流程梳理关键环节，补充发送失败与超时场景的处理要求。 |
| 建立断线缓存机制并进行验证。 | 补上断线重发的处理说明，模拟断连恢复后核对数据是否补齐。 |
| 对照附录11.4整理阈值表并核对告警条件。 | 核对各监测阈值的含义与告警方向，把阈值表补入参数说明。 |

问题一侧同样适用：写清**哪个模块/哪条链路缺什么、影响什么**（对象+缺口+影响），不写"系统尚不完善""设计不够规范"，也不罗列寄存器/参数级细目。

**配对反例：** 问题1“通信模块上报失败”，修改意见1“界面字体调整” → 无关，必须FAIL。

**配对正例（匿名泛化）：** 问题1“串口数据帧缺少校验处理”；意见1“按协议校验帧头、长度及校验和，并记录异常帧日志进行验证”。
